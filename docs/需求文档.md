## 1. 背景与问题

### 1.1 现状

现在用手机操控 DSH 的方式是：手机浏览器打开 `dsh-remote-web-ui` 提供的远程入口（配对后进入官方 Web GUI 的 SPA）。`src/client/mobile-adapt.ts`（1254 行）在**官方桌面 SPA 之上**注入一层 CSS + 手势补丁来做竖屏适配——它并不提供一套真正的移动端 UI。

### 1.2 用户痛点（原话）

> 「每一次重新打开网页都要加载一遍插件，相当于重启，加载时间非常的长，而且还需要渲染 UI，整体交互性感觉很差」

拆解为四条根因：

| 痛点 | 根因 | 证据 |
| --- | --- | --- |
| 重开即"重启" | 页面级 SPA 生命周期；凭证存在 `sessionStorage`，关页即丢 | `src/routes.ts:302` `APP_DEVICE_STORAGE_KEY = 'dsh-remote-device'`，由 `appShellCaptureScript` 写入 `sessionStorage`（`routes.ts:304-320`） |
| 加载时间很长 | 每次都要下载并执行整个桌面端 SPA bundle + 全部插件 bundle | `routes.ts:953-993` 每次 `/pair-app` 都返回完整官方 index |
| 还要渲染 UI | 浏览器下载 → 解析 → 布局 → 绘制完整桌面 UI，再由 `mobile-adapt` 二次改写 | `mobile-adapt.ts` 注入 `dsh-remote-web-ui/mobile-adapt.css`，依赖 CSS-Modules 哈希类名（如 `pI_x6G_centerCol`），对官方改版脆弱 |
| 交互性差 | 移动端适配是"打补丁"：把桌面三栏压成 0 宽、悬浮鲸鱼按钮当侧栏入口、长按代替右键 | `mobile-adapt.ts:143` `[class$="_frame"][data-sidebar-collapsed]{grid-template-columns:0 minmax(0,1fr) 0 !important}` —— 正是这条规则把会话列表挤没了 |

> 附带事实：因 `codex-ui` 禁用了官方 `ui-sidebar` 组合插件，`mobile-adapt` 又把侧栏压到 0 宽，**当前手机上根本没有会话选择侧栏**；且 `dsh-remote-web-ui` 未暴露自定义 CSS 钩子，只能改 `node_modules` 才能修。这本身就是做原生 App 的强动机。

### 1.3 结论

放弃"在手机上跑桌面 Web UI"，改为**原生 Android App**，直接以 **Typert RPC** 协议访问 DSH 真实接口。App 不需要加载任何 SPA、任何插件、不需要渲染 Web UI。

## 3. 已核实的接口契约（本方案的地基）

> 以下全部来自真实源码，附文件与行号。**这是本需求文档的核心资产**：后续开发不需要再猜接口。

### 3.1 传输层：Typert RPC，不是 REST

DSH 的 HTTP/WS 接口是 Typert RPC 网关。单次调用形如：

```
POST /api/<namespace>/<method>
Content-Type: application/json

{ "type": "client-request", "rpcId": "<uuid-v4>", "method": "<namespace>/<method>", "payload": { "args": { ... } } }
```

响应：

```json
{ "type": "server-response", "rpcId": "<same-uuid>", "result": { "ok": true, "value": { ... } } }
```

失败：`result = { ok: false, error: { code, message, details: { issues: [] } } }`

证据：
- `dsh-client-connection\lib\client.js:1209-1239` —— 请求封装与 `rpcId` 校验（`:1230` 不匹配即抛 `rpcId mismatch`）
- `dsh-client-connection\lib\index.js:504-509` `clientRequestSchema`、`:511-515` `serverResponseSchema`
- `dsh-client-connection\lib\index.js:673-702` —— 必须 POST + `content-type: application/json`，否则 415/400；`method` 必须与路径推导出的 endpoint 一致
- `dsh-api-gateway\lib\index.js:1447-1448` `endpointOf(ns, method)` → `` `${namespace}/${method}` ``
- `dsh-api-gateway\lib\index.js:1225-1237` `remoteRequest` —— payload 必须**只含一个 `args` 键**且其值为普通对象
- 二进制响应：`content-type: multipart/form-data`，`metadata` 字段装 JSON 信封 + `attachments:[{codec:'bytes', part:'bytes-N', path:[...]}]`（`client.js:1240-1287`），用于图片/附件字节

### 3.2 流式：一条 WebSocket 多路复用

- 路径：`/api/remote.mux`（`dsh-api-gateway\lib\client.js:106`，`lib\index.js:12`）
- 一条连接承载**所有**逻辑流（`session/control`、`session/follow`、`workspace/follow`、`$events`）
- 客户端 → 服务端帧：`{type:"open", streamId, endpoint, payload}` / `{type:"item", streamId, value}` / `{type:"end", streamId}` / `{type:"cancel", streamId}`（`client.js:325-624`）
- 服务端 → 客户端帧（键名精确）：`{type:"item", streamId[, value]}` / `{type:"end", streamId}` / `{type:"error", streamId, error:{code,message,details}}`（`client.js:160-179`）；收到未知帧 → 客户端以 **4002** 关闭，原因 `invalid Remote stream frame`
- `streamId` 为随机 UUID

### 3.3 远程通道：`/remote` 前缀 + 设备头

配对设备通过插件自己的 `/remote` 通道访问被围栏保护的 `/api`：

| 项 | 值 | 证据 |
| --- | --- | --- |
| 前缀 | `/remote` | `src\remote-methods.ts:16` |
| API 前缀 | `/remote/api` | `src\remote-methods.ts:19` |
| 流多路复用 | `/remote/api/remote.mux` | `src\remote-methods.ts:31` |
| 设备凭据头 | `x-dsh-remote-device` | `src\remote-methods.ts:61` |
| WS 上的设备凭据 | 查询参数 `?device=<deviceId>`（握手带不了头） | `src\remote-methods.ts:62`、`remote-api.ts:199-211` |
| 映射规则 | `/remote/<x>` → `/<x>`，拒绝路径穿越 | `remote-api.ts:100-110` |
| 未配对 | HTTP 403，`error.code = 'unpaired'` | `remote-api.ts:88-94, 150-155` |
| 本地专用（远程拒绝） | `/api/pair`、`/api/update`、`/api/plugin-manager` | `src\remote-methods.ts:71-75` |
| 安全模型 | 配对设备 = **完全控制**凭据；网关会用自己的浏览器鉴权 cookie 回放请求（鉴权放大器），闸门**无条件**生效 | `remote-api.ts:1-27` |

**含义**：App 只要拿到 `deviceId`，就能以
`POST https://<host>/remote/api/<namespace>/<method>`（带头 `x-dsh-remote-device: <deviceId>`）
调用所有业务接口，并用 `wss://<host>/remote/api/remote.mux?device=<deviceId>` 承载所有流。**无需任何浏览器 cookie。**

### 3.4 配对流程（原生 App 视角）

1. 桌面端 `POST /api/pair/issue`（loopback-only，`routes.ts:688`）→ `{ ok, url: "<base>/pair-accept?pair=<token>", token, expiresAt, lanAddresses[], publicBaseUrl? }`（`routes.ts:704-721`）
   - `base` = 配了公网基址则用公网（隧道）URL，否则用第一个局域网地址；带 `address` 参数则强制为局域网字面量
   - 失败：400 `bad-payload` / `unknown-address`，409 `lan-required`
2. 手机扫码得到 `https://<base>/pair-accept?pair=<token>`；App 解析出 `token`
3. App 直接 `POST <base>/api/pair/accept`，body `{token}` → `200 {ok:true, deviceId}`（`routes.ts:733-769`）
   - 围栏：`lanFence(req)` 或 Host 为私有/本地地址；**公网隧道基址也在 `lanFence` 的白名单内**（`routes.ts:583-595` 把 `publicHostOf(service.publicBaseUrl)` 并入 trusted hosts），因此 App 走公网隧道也能完成 accept
   - 失败：403 `forbidden`、429 `rate-limited`、404 `{ok:false, code}`（token 过期/未知/已停止）
   - 注意：App 不发 `Origin`、不发 `sec-fetch-site`，正好满足 `isTrustedApiRequest` 的"无 Origin 视为通过"分支（`routes.ts:47-61`）
4. App 本地持久化 `deviceId` + `baseUrl`
5. 之后全部走 `/remote` 通道

> 备选（无扫码）：用户在桌面端 `POST /api/pair/issue` 后把 `token` 或整条 URL 手动抄进 App；或 App 直连局域网地址 `http://<lan-ip>:19387`。

**心跳与失效**：`POST /api/pair/heartbeat`（`routes.ts:807-824`）读 cookie 而非头，App 侧不适用；改为通过任意一次 `/remote` 调用返回 403 `unpaired` 来判定凭据失效，并提示重新配对。

**文件读取**（namespace `workspaceFiles`，服务 `workspaceFiles`）——**"点击文件查看"就靠这一组**

| 方法 | args | 返回 |
| --- | --- | --- |
| `workspaceFiles/read` | `{workspaceFileScopeId, path, range:{offset?,limit?}}` | `{offset, text, lines, eof, absolutePath, version, bytes?}` |
| `workspaceFiles/readBytes` | `{workspaceFileScopeId, path, options:{range?,baseFile?}}` | `{offset, data:Uint8Array, eof, absolutePath, version, bytes?}` |
| `workspaceFiles/stat` | `{workspaceFileScopeId, path}` | `{absolutePath, version, bytes?}` |
| `workspaceFiles/list` | `{workspaceFileScopeId, path}` | `{path, entries:[{name,type:'file'\|'directory'\|'other',size?}], truncated}` |

**文件地址语法**（`@deepseek-ai/util/workspace-path`）：`dsh-resource://file/session/<sessionId>/<path>` 与 `dsh-resource://file/absolute/<path>`（Windows 盘符 `C:` 按段处理）。App 解析会话内提到的 `dsh-resource://file/...` 链接时按此语法拆出 sessionId + 相对路径。

### 3.7 改动文件（"已编辑 N 个文件"卡片的数据来源）

桌面端那张"已编辑 2 个文件 +722 -0"的卡片不是从回复正文里猜出来的，它来自 Host 插件 `@deepseek-ai/dsh-workspace-changes`（服务名 `workspaceChanges`）：

- 每个有 `cwd` 且非 subagent 来源的会话，在 `turn/start` 打 git 工作树快照、`turn/end` 再打一次并 diff；对 git 覆盖不到的路径（非 git 仓库、被 ignore、workspace 之外），在每个 `write`/`edit`/`str_replace_editor` 执行**前**整文件抓一份做对比。
- 结果以**只带 `{turn}` 的 `workspace/changes` 会话事件**写进日志——**摘要本身不在日志里**，而是放在 Host 进程内存中，通过 `workspaceChanges.summary(sessionId, seq)` / `.diff(sessionId, seq, index)` 提供。
- 摘要结构：`{turn, files, total, added, deleted}`，每个文件 `{path, display, added, deleted, binary?, oversized?}`；`total` 是完整数量，`files` 受 `maxFiles`(500) 截断。
- 对比结构：`{kind:'text', path, display, before, after, hunks, coarse}` 或 `{kind:'binary'|'oversized', path, display}`；hunk 带 3 行上下文，超 `diffTimeoutMs`(100ms) 退化成整文件替换并标 `coarse`。
- 这些数据由客户端插件 `@deepseek-ai/dsh-client-ui-deliverables` 用三个**已鉴权的普通 HTTP 路由**暴露（不是 Typert RPC）：`GET /api/changes.summary?sessionId=&seq=`、`GET /api/changes.diff?sessionId=&seq=&index=`、`POST /api/changes.open?sessionId=&seq=&index=`。经 `/remote` 通道时同样是 `GET /remote/api/changes.summary?...` 带 `x-dsh-remote-device` 头。
- **必须知道的限制**：摘要/快照/对比只活在**同一个 Host 进程内的那个会话**生命周期里——Host 重启后，旧轮次既没有卡片也没有 diff（路由返回 404）。非 git 仓库里只列文件工具改过的文件，纯 shell 改动看不到。单文件 >2 MiB 只列不计行数。

### 3.8 会话事件里"改了什么"长什么样

- 会话日志**没有** `file/…`、`patch/…` 这类事件类型。文件改动只能从 `tool/call`（`{turn,step,callId,name,arguments}`，**`arguments` 是 JSON 字符串**）与 `tool/result`（`{turn,step,message,error?,meta?}`）推出来。
- 因此 App 侧"看到编辑的文件"有两条路，建议**都做**：
  1. **工具卡片**：解析 `tool/call.name ∈ {write, edit, str_replace_editor}` 的 `arguments` 取出 `file_path`/`path`，渲染成可点行——这是实时的、不依赖 Host 进程状态。
  2. **权威清单**：会话中出现 `workspace/changes` 事件时，用其 `seq` 调 `changes.summary` 拿权威的行数统计，按卡片渲染；点行调 `changes.diff` 展示 diff、调 `workspaceFiles/read` 看当前全文。
- `assistant/message` 的正文是 `content: ContentBlock[]`，`ContentBlockMap = {text, reasoning, image, file, 'tool-call', 'tool-addition', 'tool-removal'}`；`TextBlock = {type:'text', text}`。**所以助手回复的 markdown 是纯文本字符串，渲染与否完全是客户端决定。**
- 流式增量另有 `AssistantStreamRecord`：`{type:'text-chunks', time0, index, dt:number[], texts:string[]}`、`{type:'reasoning-chunks', …}`、`{type:'tool-call-chunks', …, id, name?, args:string[]}`、`{type:'chunk', time, chunk}`。`session/follow` 带 `assistantStream:true` 时用它做逐字上屏。

### 4.2 场景

**S1 首次配对（一次性）**
打开 App → 空状态引导 → 点「扫描二维码」→ 扫桌面端配对二维码 → 自动 `accept` → 落盘凭证 → 直接进工作区列表。全程 ≤ 15 s。

**S2 冷启动继续工作**
打开 App → 直读本地凭证 → 立即渲染上次的工作区/会话骨架 → 常驻 mux 连上后补全并转实时。**不出现任何加载插件/白屏转圈。**

**S3 查看工作区与会话**
工作区列表 → 点开某工作区 → 展开其会话 → 未读/运行中状态可见。

**S4 继续对话**
进入会话 → 看历史（`session/follow` 快照 + 增量）→ 输入框发消息（`session/prompt`）→ 回复逐字流式上屏 → 可中止（`session/cancel`）。

**S5 断线/换网**
WiFi 切 4G、隧道重连 → mux 自动重连 + 断点续传（`session/page` 补历史）→ 顶部条显示连接状态。

**S6 凭据失效**
桌面端撤销配对 → App 任意请求收 403 `unpaired` → 全局提示「配对已失效」→ 引导重新配对（不清空本地历史缓存）。

### 7.2 模块划分

```
app
 ├─ core:protocol    TypertClient（unary + mux）、信封、错误码、rpcId
 ├─ core:pairing     配对流程、二维码解析、凭证存储
 ├─ core:session     会话仓库（follow/control/page 流 → Flow<UiState>）

 └─ ui               Compose 界面（工作区/会话/聊天/文件查看/设置）
```

### 7.3 关键实现要点

1. **URL 前缀改写**：业务调用统一为 `POST {base}/remote/api/{namespace}/{method}`；`base` 为配对时记录的地址。
2. **请求体**：`{"type":"client-request","rpcId":<uuid>,"method":"{ns}/{method}","payload":{"args":{...}}}`；必须校验响应 `rpcId` 一致。
3. **WS 握手**：`wss://{host}/remote/api/remote.mux?device={deviceId}`；`device` 参数由插件在转发前删除。
4. **流复用**：一条 WS，多个 `streamId`；`open` 后收 `item`/`end`/`error`。收到未知帧按协议应主动以 4002 关闭（客户端实现需对齐）。
5. **未定义参数不发送**：`prepareInvocation` 会省略 `undefined` 的参数，App 侧同样只放非空字段。
6. **`projections` 为松散结构**：用 `JsonObject` 承接，按需解析已知 key，避免因服务端新增 key 而崩溃。
7. **`/api/pair/accept` 不走 `/remote`**：它在 `LOCAL_ONLY_PREFIXES` 中，必须直连 `{base}/api/pair/accept`。
8. **`changes.summary` / `changes.diff` 走普通 HTTP GET**，不是 Typert RPC：经 `/remote` 通道时为 `GET {base}/remote/api/changes.summary?sessionId=&seq=`，带 `x-dsh-remote-device` 头，返回普通 JSON（不是 `{type:'server-response'}` 信封）。这与 RPC 调用是两套解析路径，实现时不要混。
9. **`workspaceFileScopeId` 传 sessionId**，不是 workspaceId；且该参数是 Typert `lookup`，Host 侧才解析成工作区根。
10. **流式 Markdown 的增量解析**：桌面端 `MarkdownText` 的做法是"除末尾两个块外全部冻结为缓存元素，每个分片只重新解析尾部"，并把末尾未闭合的顶层 fence 交给同一套 GFM grammar 处理最后一个完成行 + 当前未完成行。Android 侧建议照此实现，否则长回复会 O(n²) 重排。

### 7.4 请求时序（首次配对 → 首屏）

```
App                    Desktop(DSH)          remote-web-ui 插件
 │ 扫码/粘贴 token         │                        │
 │──POST {base}/api/pair/accept {token} ─────────────────────────▶│
 │◀──────────────────── 200 {ok:true, deviceId} ──────────────────│
 │ 持久化 deviceId         │                        │
 │──POST /remote/api/workspace/follow ───────────────────────────▶│
 │                        │◀─ 回放为 loopback /api 请求 ──│
 │──WS  wss://…/remote/api/remote.mux?device=… ──────────────────▶│
 │◀─ open{workspace/follow} → item{baseline} ────────────────────│
 │◀─ open{session/control} → item{baseline} ─────────────────────│
 │ 渲染列表（实时）        │                        │
```

## 11. 风险

| 风险 | 影响 | 缓解 |
| --- | --- | --- |
| Typert 协议随 DSH 版本变化 | 接口失效 | 协议层独立模块；版本探测；错误码集中处理 |
