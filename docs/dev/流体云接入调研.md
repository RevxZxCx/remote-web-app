# 流体云（ColorOS Live Update）接入可行性报告

> 本文件是 R059 的调研产出。结论均来自**真机实测**（OnePlus PKG110 / ColorOS 17 / SDK 37），
> 不是文档推测。文中所有「实测」标注均可复现，方法见第 6 节。

**日期**：2026-11-09
**调研人**：Lead + 用户
**调研目标机型**：OnePlus PKG110，`ro.build.version.release=17`，`ro.build.version.sdk=37`，
`ro.build.version.oplusrom=V17.0.0`，`ro.build.display.id=PKG110_17.0.0.105(CN01)`
**结论**：✅ **可行**，用 Android 16 官方 promoted ongoing notification API，**不需要 root、不需要 Xposed、不需要厂商白名单**。

**核心事实**：ColorOS 的「流体云」是它对 **Android 16 Live Updates**（AOSP 名称：promoted ongoing notification /
progress-centric notification）的**渲染层实现**。App 侧只使用公开 API，系统决定是否、以及如何把它画成胶囊。

## 2. 协议与 API 契约（可直接照抄的实现要点）

### 2.1 权限

```xml
<uses-permission android:name="android.permission.POST_NOTIFICATIONS" />
<uses-permission android:name="android.permission.POST_PROMOTED_NOTIFICATIONS" />
<uses-permission android:name="android.permission.FOREGROUND_SERVICE" />
```

- `POST_PROMOTED_NOTIFICATIONS` 在真机上实测存在：`prot=normal|appop`、`sourcePackage=android`。
- 它**不是运行时权限**，不需要 `requestPermissions`。
- 但它背后挂着一个 **AppOp**，默认模式是 **`ignore`**。这就是「为什么我的通知没变成胶囊」的最常见原因。

### 2.2 通知必须满足的条件（缺一即不提升）

实测 + 官方文档交叉确认，全部为硬性要求：

1. 样式必须是 `Standard` / `BigTextStyle` / `CallStyle` / `ProgressStyle` / `MetricStyle` 之一。
2. 必须 `setOngoing(true)`（等价于 `FLAG_ONGOING_EVENT`）。
3. 必须设置 `contentTitle`（**不得为空**，否则不提升）。
4. 必须请求提升：
   ```kotlin
   builder.addExtras(Bundle().apply { putBoolean("android.requestPromotedOngoing", true) })
   ```
5. **不得**设置 `customContentView`（不支持 RemoteViews）。
6. **不得**是 group summary。
7. **不得** `setColorized(true)`。
8. 渠道重要性**不得**为 `IMPORTANCE_MIN`。
9. 必须设置 `setShortCriticalText(...)`，否则状态栏胶囊上没有文字。

### 2.3 实测通过的完整调用链

```kotlin
val channel = NotificationChannel(CHANNEL_ID, "名", NotificationManager.IMPORTANCE_HIGH)

val progress = Notification.ProgressStyle()
    .setStyledByProgress(false)   // false 时进度由 setProgress 驱动
    .setProgress(3)               // 当前步骤

val builder = Notification.Builder(this, CHANNEL_ID)
    .setSmallIcon(...)
    .setContentTitle("正在执行任务")
    .setContentText("第 3 步 / 共 5 步")
    .setContentIntent(contentIntent)
    .setDeleteIntent(deleteIntent)     // 感知用户划掉
    .setOngoing(true)
    .setOnlyAlertOnce(true)
    .setShowWhen(false)
    .setCategory(Notification.CATEGORY_PROGRESS)
    .setProgress(5, 3, false)
    .setStyle(progress)
    .setShortCriticalText("执行中")
    .addAction(Notification.Action.Builder(null, "批准", approvePendingIntent).build())
    .addAction(Notification.Action.Builder(null, "拒绝", denyPendingIntent).build())
    .addExtras(Bundle().apply { putBoolean("android.requestPromotedOngoing", true) })

val n = builder.build()
// 诊断：这两个值决定成败
Log.i(TAG, "promotable=${n.hasPromotableCharacteristics()} canPost=${nm.canPostPromotedNotifications()}")
nm.notify(NOTIFICATION_ID, n)
```

**`canPostPromotedNotifications()` 的价值**：它是「用户到底给没给这个权限」的唯一可靠探测点。
实测：权限未开时它返回 `false`，开了立刻变 `true`，且胶囊随即出现。

### 2.4 实测数据（真机）

| 阶段 | `hasPromotableCharacteristics()` | `canPostPromotedNotifications()` | 状态栏表现 |
|---|---|---|---|
| 刚装上，用户未开开关 | `true` | `false` | 只有普通小图标 |
| 用户在设置里开「流体云显示实时活动」后 | `true` | **`true`** | 出现黑色胶囊「执行中」 |

→ **`promotable=true` 只说明「通知构造合规」，`canPost` 才是「系统放不放行」**。
两者必须都看，只看前者会误判成「我们代码写错了」。

### 3.2 用户开关的实际位置（重要）

ColorOS 17 **没有**暴露 AOSP 的 `android.settings.MANAGE_APP_PROMOTED_NOTIFICATIONS` 设置页
（`cmd package query-activities` 返回 `No activities found`）。

真正的入口是 ColorOS 自己的通知设置：

```
设置 → 通知与状态栏 → 流体云 → 应用提醒 → <你的 App> → 「流体云显示实时活动」开关
```

实测该开关**直接对应 `POST_PROMOTED_NOTIFICATIONS` 这个 AppOp**：
打开前 `cmd appops get <pkg> POST_PROMOTED_NOTIFICATIONS` → `ignore`，
打开后 → `Uid mode: ... allow`。

**可编程入口**：标准深链能直达该页面，实测落到 `com.oplus.notificationmanager/.AppNotificationSettingsActivity`：

```kotlin
startActivity(Intent(Settings.ACTION_APP_NOTIFICATION_SETTINGS).apply {
    putExtra(Settings.EXTRA_APP_PACKAGE, packageName)
})
```

→ **引导用户去开开关的最佳做法**：检测 `canPostPromotedNotifications() == false` 时，
在 App 内显示一行提示 + 「去设置」按钮，用上面这个 Intent。

**展开态（卡片）**：点击胶囊后展开，实测显示：

- 副标题「第 3 步 / 共 5 步」（来自 `setContentText`）

**点击回调**：点「批准」后 logcat 出现

### 3.5 流式输出与图标按钮的二次实测（针对 m00818 / m00956 的要求）

用户提出两点改造诉求：① 执行中的卡片要能显示流式输出并随更新滚动；② 批准/拒绝按钮改成
图标而非文字。两项都撞在系统渲染层，故专门补做真机实验。

**A. 多行文本（BigTextStyle）**

| 验证项 | 结果 |
|---|---|
| `BigTextStyle` 在流体云卡片上生效吗 | **生效**，卡片正文区从 1 行扩为多行 |
| 最多显示几行 | **2 行**，第 3 行起以 `…` 截断（实测 6 行 bigText 只渲染前 2 行 + 省略号） |
| 换一次 `notify` 会自动滚动 | **不会**。卡片不滚动，只静态展示当前文本的前 2 行 |
| 只给「最近 3 行」滚动窗口 | 显示第 1、2 行 + `…`，**即显示的是文本开头，不是结尾** |

**结论**：不能用「不断追加整段文本」的方式做滚动。要让用户看到最新输出，必须**自己维护一行
「当前状态」文本，用 `setContentText` 覆盖**，把累计历史留给点开 App 看。可以做的增强是：
`bigText` 放「最近 2 行」（换行拼接），`contentText` 放最新 1 行，两者都不超长。

**B. action 图标**

| 验证项 | 结果 |
|---|---|
| `Action.Builder(icon, "", pi)` 空标题 | **可行**，卡片渲染为纯图标按钮，无占位文字 |
| 系统内置 `android.R.drawable` | `android.R.drawable` 只公开 **139** 个（`total=176 nonzero=176`，其中 139 个可用 id），且**没有干净的勾/叉配对**：只有 `checkbox_on_background`(复选框方块)、`ic_menu_close_clear_cancel`(菜单里的叉)、`ic_delete`(垃圾桶) |
| 自带 Material 矢量图（`Icon.createWithResource(R.drawable.ic_check)`） | **渲染清晰**，勾是细线条矢量，叉同样清晰，与系统图标观感一致 |
| action 数量 | 上限仍是 **3 个**，图标化不改变这个上限 |

**结论**：**不要依赖系统 drawable**（风格不统一、配对缺失、各厂商 ROM 可能改），应在本项目
`res/drawable/` 里自带 Material Symbols 矢量图（`ic_check` / `ic_close` / `ic_more` 各 24dp）。
矢量 path 数据用 Material 官方标准路径即可，无需引入新依赖。

**C. 卡片布局的第三轮实测（针对 m01212 的诉求）**

用户看完 v2 原型后提出三点：① 汇报行要显示在流式内容上方、每汇报一次就刷新；② 回答类
问题用对错按钮不合理；③ 进度条想按 todo list 设总步数，且进度条下方要显示实际步骤名。

针对 ③ 专门做了三组真机实验（截图 `F:\bot\_fcprobe\t_sub.png` / `t_sub2.png` / `t_seg.png`
/ `t_combo.png` / `t_segsub.png`）：

| 验证项 | 结果 |
|---|---|
| `setSubText(...)` 能否多占一行 | **能**。位于正文下方、进度条上方，卡片从「标题+2 行正文」变四层 |
| `ProgressStyle.Segment` 分段进度条 | **正常渲染**。5 段中前 2 段绿、后 3 段灰，段间 3px 间隔 |
| `Segment` 能否带文字标签 | **不能**。`javap -p` 反编译 `android.jar` 确认 `Segment` 只有 `Segment(int)`/`getColor/getId/getLength`/`setColor/setId`，**没有 setLabel**；`Point` 同样无文字 |
| `BigTextStyle` 与 `ProgressStyle` 能否共存 | **不能**。用 `BigTextStyle` 时进度条消失（`setStyle` 只能是一个） |
| `ProgressStyle` + `contentText` + `subText` | **三者共存**（`t_segsub.png` 已验证） |

**由此确定的最终布局**（这是唯一能同时满足"汇报 + 当前动作 + 步骤说明 + 进度"的组合）：

```
setContentTitle(汇报内容)          → 最多 2 行，每汇报一次原地刷新
setContentText("▸ 当前正在做的事")  → 1 行
setSubText("第 3 步 / 共 5 步：步骤名") → 1 行，位于进度条上方
setStyle(ProgressStyle()...)      → 分段进度条，一条 Segment 对应一个 todo 条目
setProgress(5, 2, false)          → 总步数 / 已完成数
```

**取舍**：因为 `BigTextStyle` 与 `ProgressStyle` 互斥，"2 行流式输出"与"分段进度条"只能二选一。
既然用户更看重进度条下的步骤说明（③），选择 `ProgressStyle` 路线，把流式信息压进

> **⚠ 已被 H 节取代**（见 3.7-H）：后续实测发现 `setUsesChronometer(true)` **会整体接管 `setContentText` 那一行**，因此 `contentText` 不能再用来放「当前动作」。最终做法是把「汇报 / 当前动作」两行都塞进 `setContentTitle`（中间加换行符），`contentText` 让给计时器。下面这个代码块保留作为推理过程记录，不要照着写。
`contentTitle`（2 行汇报）+ `contentText`（1 行当前动作）——**既满足了"汇报行在流式上方"，
又保留了步骤进度**。步骤名只能放 subText，**无法做在每个分段正下方**（API 不支持）。

针对 ②（回答类不用对错按钮）：选项类问题不适合在卡片上直接选——图标表达不了
「src/ 和 docs/」这种语义，对勾/叉号更会误导。改为卡片只做提醒（`› 去回答 / ✕ 稍后 / ⋯ 详情`），
真正选择跳回 App。

**D. 进度条圆点错位（m01450 报告的问题，已定位根因）**

用户发现：分段进度条的绿色填充走到第 2 段末尾，但上面的小圆点却停在很靠左的位置，
**HTML 原型和真机 App 都会出现**。做了一轮专项像素测量（脚本 `F:\bot\_knob_measure2.py`
与 `F:\bot\_knob_sweep2.py`），量的是真机截图里「绿色像素的最右端」与「圆点圆心」相对
进度条左右端点（barA=98, barB=981，跨度 883px）的百分比。

| 配置 | 绿色填充末端 | 圆点位置 | 结论 |
|---|---|---|---|
| 5 段，`Segment(5)`，done=2 | 40.0%（第 2 段末尾，正确） | **10.1%** | **错位** |
| 5 段，`Segment(1)`，done=2 | 40.0%（正确） | **40.0%** | **对齐** |
| 3 段，`Segment(1)`，done=2 | 66.7%（第 2 段末尾，正确） | **66.7%** | **对齐** |
| 5 段，`Segment(1)`，done=5 | 100% | 100% | 对齐 |

**根因**：`ProgressStyle.Segment(length)` 的构造参数**不是「这一段占多长」这个比例，
而是「这一段代表多少个进度单位」**。

- 圆点位置 = `done / Σ(所有 Segment 的 length)`，即 `setProgress` 的当前值除以**所有段长度之和**；
- 绿色填充位置 = `已完成段数 / 总段数`。

当初按「每段长度 = 总步数」来写（`Segment(max)`），5 段时 Σlength = 5×5 = 25，
于是圆点 = 2/25 = 8%（实测 10.1%，差异来自进度条两端的内边距），而绿色填充仍是 2/5 = 40%
→ **两者分母不同，必然错位**。

**正确写法**：每段长度一律给 **1**，`setProgress` 的 max 给段数。

```kotlin
val total = steps.size              // 例如 5
style.setProgressSegments(
    steps.mapIndexed { i, _ ->
        Notification.ProgressStyle.Segment(1)          // ← 必须是 1，不是 total
            .setColor(if (i < done) COLOR_DONE else COLOR_TODO)
    }
)
builder.setProgress(total, done, false)                // max=段数
style.setProgress(done)                                // 当前进度
```

HTML 原型里同样有两个错位来源，一并修掉（脚本 `F:\bot\_r058_fixknob.py`）：

1. 原型给「当前段」画了半绿渐变（`.cur` 用 `linear-gradient(90deg,绿 50%,灰 50%)`），
   视觉上绿色延伸到了段中点，而圆点按 `done/segs` 算 → 圆点落在绿条中间。
   真机不会画半段，删掉 `.cur` 样式。
2. 原型用纯百分比 `left: (done/segs*100)%` 定位圆点，但分段之间有 3px 的 gap，
   4 个缝累计偏移，段数越多偏得越远。改为按真实段边界用 px 定位：
   `segW = (W - GAP*(segs-1)) / segs; px = done*segW + done*GAP`。

**E. 回答类问题的选项按钮（替代对勾/叉号）**

C 节把回答类做成了「› 去回答 / ✕ 稍后 / ⋯ 详情」的图标提醒，依据是「图标表达不了
『src/ 和 docs/』这种语义」。用户随后指出更直接的解法：**把前两个选项直接做成文字按钮**。

| 验证项 | 结果 |
|---|---|
| `Action.Builder(null, "仅 src/", pi)` 纯文字、无图标 | **渲染成文字胶囊按钮**，无图标占位 |
| 两个中文选项并排 | **各占一半宽**，完整显示不截断 |
| 中英混排（`src/ 和 docs/`） | 正常，字号自动适配 |
| action 上限 | 仍是 **3 个** |

**最终回答类布局**：

```
setContentTitle("有 3 个问题需要你回答")     ← 2 行，说明总量
setContentText("▸ 重建索引要包含哪些目录？")  ← 1 行，当前问题
setSubText("问题 1 / 共 3：选择一项即可")     ← 1 行，位置说明
addAction(text("仅 src/",        aPi))      ← 选项 1
addAction(text("src/ 和 docs/", bPi))      ← 选项 2
addAction(icon(R.drawable.ic_more, morePi)) ← 第 3 个按钮留给「更多」
```

超过 2 个选项时，第三个及以后跳回 App 里选。**不要用对勾/叉号**：那是一组二元语义，
放到「选目录」这种多选题上会误导用户以为在对整个问题表态。

### 3.6 原型侧与实现侧的圆点错位修复（针对 m01450）

m01450 报「进度条上的圆点和绿色填充末端错位」。根因与修法两边一样，但**落点不同**：

**实现侧（通知 API）**
`Notification.ProgressStyle.Segment(length)` 的构造参数是「这一段代表多少个进度单位」，**不是比例**。圆点位置用 `done / Σlength` 算，绿填充用 `已完成段数 / 总段数` 算，两者分母不同，必然错位。

| 写法 | 5 段 done=2 | 绿填充 | 圆点 | 结论 |
|---|---|---|---|---|
| `Segment(max)` 即 `Segment(5)` | Σlength=25 | 40% | 10.1% | 错位 |
| `Segment(1)` | Σlength=5 | 40% | 40.0% | 对齐 |
| `Segment(1)` × 3 段 done=2 | Σlength=3 | 66.7% | 66.7% | 对齐 |
| `Segment(1)` × 5 段 done=5 | Σlength=5 | 100% | 100% | 对齐 |

正确写法：每段长度一律给 `1`，`builder.setProgress(total, done, false)` 的 max 给段数，`style.setProgress(done)`。

**原型侧（HTML）**
HTML 没有「单位」概念，错位来源是另外两个：
1. 原来给当前段加了 `.cur` 半绿渐变（`linear-gradient(90deg, 绿 50%, 灰 50%)`），绿色视觉延伸到段中点，而圆点按 `done/segs` 算完整段边界 → 圆点落在绿条中间。**真机不画半段，原型也不该画**，已删。
2. 分段之间有 `gap:3px`，按百分比推算圆心会累计偏移。改为**把圆点元素直接 append 进第 `done` 个段元素**，用 `right:-6.5px` 贴住它的右边界——不在 JS 里算任何坐标，也就不存在坐标系不一致。

踩过的坑，写下来免得重犯：
- `offsetLeft` 的原点是「最近的定位祖先」，`knob` 的绝对 `left` 原点是 `.cseg`，两者不一定是同一个盒子，实测恒定差 6.5px（正好半个圆点）。
- `getBoundingClientRect` 换算后仍有 6~8px 偏差，且 `done` 越靠后偏差越大。
- 改 `renderCard` 时把 `const done = ...` 定义整行删掉，导致每轮抛 ReferenceError、五个状态渲染成同一个样子且不报错（截图只是「看起来没变」）。**改完必须 `node --check` 抽出来的 `<script>` 做语法自检**，并逐态截图对比，不能只看一张。

截图规范（新增）：URL 加 `?still=1` 会注入 `*{transition:none!important;animation:none!important}`，避免把过渡中间帧拍进去；展开态下胶囊是淡出的，**拍胶囊必须用 `&open=0`**，否则裁到的是一条空状态栏。

### 3.7 多会话、冻结与计时器（针对 m01968 / m02022 / m02387 / m02414）

这一组实验回答三个问题：多条 promoted 通知会怎么显示、App 在后台被冻结会怎样、
有没有办法让卡片在 App 冻结时仍然诚实地表达「这是多久之前的状态」。

#### A. 多条通知 ≠ 多个胶囊

同时 post 3 条独立 id 的 promoted 通知，`dumpsys notification --noredact` 确认三条
NotificationRecord 都带 `flags=...|PROMOTED_ONGOING`，各自的 `shortCriticalText`
是「执行中1/2/3」，`promotable=true`、`canPost=true`，全部合法。

但状态栏**只显示一条**（最后一条「执行中 3」）。`input swipe 750 65 320 65 250`
左滑切到「执行中 2」，继续滑到尽头**胶囊整体隐藏**——这正对应系统设置里那句
「在状态栏左右滑动可快速切换或隐藏实时活动胶囊」。

**结论：系统只给 App 一个胶囊展示位，多条通知是轮播不是并列。**
所以「每个会话一个胶囊」在系统层就不成立，多会话方案只能是
「焦点会话聚光灯 + 其余折叠成计数」。

#### B. 后台冻结（决定性，也是最容易测错的一项）

用 `mode=churn --ei ticks 40 --ei gap 1000` 每秒更新一次通知并写时间戳到
`filesDir/trace.txt`。前台跑完 40 次；退到后台后**停在 tick=11**。

**判定方法踩过的坑（重要）**：
- `dumpsys activity processes` 报 `isFrozen=false isPendingFreeze=false` —— **不可信**。
- `/proc/PID/stat` 的状态字 `S`（sleeping）—— **也不可信**，冻结的进程一样是 `S`。
- `pidof` 还能查到 —— 冻结不等于杀死。
- 唯一可信的是 `/sys/fs/cgroup/apps/uid_<uid>/pid_<pid>/cgroup.freeze` 的值是 `1`，
  再配两次采样 `/proc/PID/task/T/stat` 的 utime/stime 不增长做交叉验证。
- 对照组：`com.tencent.mobileqq` 同为 `freeze=1`，`com.android.systemui` 是 `0`。
  → 这是系统对所有普通 App 的默认行为，不是 App 自身的 bug。

#### C. 前台服务挡不住冻结，但系统设置能

`ChurnService`（`foregroundServiceType="specialUse"` + `PROPERTY_SPECIAL_USE_FGS_SUBTYPE`）
`startForeground` 成功（`isForeground=true foregroundId=4001`、`oom_score_adj=200`），
退后台 6 秒后**依然 `cgroup.freeze=1`、停在 tick=11**。

`cmd deviceidle whitelist +probe.fc` 加电池白名单（`dumpsys deviceidle whitelist`
能查到 `user,probe.fc,10283`）**依然冻**。

**真正的开关在系统设置里。** 用户在「设置 → 电池 → 应用电池管理」把 probe.fc 从
「智能优化」改成「完全允许后台行为」之后，同样的实验：
- 前台服务 60 次**全跑完**，`freeze=0`
- 200 次连跑 3 分钟到 190 次不停，`freeze=0`
- **不开前台服务的普通线程** 50 秒跑到 54 次，`freeze=0`

对照 QQ 仍 `freeze=1`。查得 `dumpsys deviceidle whitelist` 含
`user,probe.fc,10283`，`am get-standby-bucket probe.fc` = `5`（EXEMPTED）。

**三条结论**：
1. **冻结可以豁免**，但只能由用户手动在系统设置里开「完全允许后台行为」。
2. `cmd deviceidle whitelist` 加白名单**不管用**，它和「完全允许后台行为」不是一回事。
3. 豁免**跟着 App 走**，`am force-stop` 和 `install -r` 重装之后仍然保留。

新用户装完 App 默认是「智能优化」，即**默认会被冻**（用户 m02414 亲自确认）。
本项目已在通知引导流程里做过后台权限引导，这部分不用再补。

#### D. 计时器：冻结时唯一诚实的时间源（关键发现）

冻结最大的问题是**App 自己不会知道自己被冻了**，醒来才发现过了半小时。
如果在卡片上写「已运行 3 分钟」，冻住的那一刻数字就停在那里，用户看不出这是个
陈旧状态。

候选方案是 `setUsesChronometer(true)`：让 SystemUI 根据 `when` 时间戳自己渲染计时，
不依赖 App 进程是否活着。

**实测结果**：

| 位置 | 是否显示 |
|---|---|
| 胶囊（收起态） | **不显示** |
| 展开卡片 | **显示**，位置在 `setContentTitle` 下方、`setSubText` 上方，格式 `MM:SS` |

**决定性证据**：在 App 已退到后台、且 `logcat` 里自 19:48 之后**再没有任何
`notify` 调用**的情况下，`dumpsys notification` 里的 `when` 时间戳两次采样都是
`1794220204515`（一字节未变），而同一时间段的截图里计时器依次是
`07:21` → `08:07`（相隔 47 秒，走了 46 秒）。

→ **计时器完全由 SystemUI 根据 `when` 自行推算，与 App 进程的存活/唤醒状态无关。**
这正是冻结场景需要的「自证陈旧」能力。

`.setWhen(whenMs)` 的写法（`ago` 为「多少秒之前」）：

```kotlin
val whenMs = System.currentTimeMillis() - ago * 1000
builder.setWhen(whenMs)
    .setShowWhen(true)
    .setUsesChronometer(true)
    .setChronometerCountDown(false)
```

注意三条实测限制：
1. **只在卡片上显示，胶囊上没有**。所以「胶囊上看一眼就知道多久了」做不到。
2. 计时器是**从 `when` 起算的绝对时长**，不是「当前步骤耗时」。想表达
   「本步骤已耗时」就得每次换步骤时重置 `when`，代价是整个会话的总时长丢失。
3. `setWhen` 会被 `when=0` 覆盖成「不显示」，别在更新通知时漏传。

#### E. 由此对方案的两条修改

1. **冻结要能事后发现**：每次刷新记 `SystemClock.elapsedRealtime()`，醒来时若
   gap 远超自己的刷新节奏，说明中间被冻过，应立即补一次刷新而不是假设连续。
2. **卡片必须带计时器**：这是冻结期间唯一还在动的东西。它让「第 3 步 / 共 5 步」
   旁边有一个诚实的「已经 8 分钟了」，而不是一个看似正常的死状态。

#### F. 多会话焦点判定（配合 A 的结论）

既然系统只给一个展示位，就必须决定「此刻展示谁」。四层刚性顺序：

1. **有待处理**（approvals / questions 的 `agentId`）。层内按 FIFO 防饥饿。
   注意**不能用 `running` 判断**——挂起等回答时 `running` 仍是 `true`。
2. **用户正在看**（`CompletionLedger.currentSessionId`）。理由：胶囊是「我不在 App 里」
   的替代品，我在看的时候它不必抢镜。
3. **粘滞保持**（上一轮焦点仍 Ongoing 就不换）。这是**硬约束不是偏好**：
   ColorOS 轻打扰会把频繁变动的胶囊缩成气泡，且**气泡不会自动展开**。
4. **重新选举**：`unreadRank` 降序 → `updatedAt` 降序 → `sessionId` 字典序。
   第三段不能省，否则同样输入两次会算出不同焦点，表现为画面闪动。

升级到第 1 层不做迟滞（要即时），其余层做 2~3 秒迟滞。

**必须先复用** `core/session/SessionActivity.kt:84` 的 `unreadRank` 和 `:111` 的
`statusOf`，否则会出现「会话列表是红点、胶囊是绿点」的自相矛盾。

**安全约束**：卡片的勾/叉只作用于焦点会话。多会话时副行**必须写明作用对象**，
否则用户以为自己批的是另一个会话。

#### G. 后台会话拿不到 todo 进度（能力边界，必须提前说清）

`ChatViewModel.kt:2198` 的 `repository.follow(sessionId)` **只订阅当前打开的会话**。
后台会话只有 `session/list` 的粗粒度信息（`SessionSummary` 里的 `running`、
`awaitingAttention` 等），**拿不到 `projections.values.todos`**。

所以「后台会话显示它自己的进度条」是做不到的。可行的是：
- 正在看的会话 → 有真实分段进度条
- 后台会话 → 只能给 indeterminate 或按「有没有新增消息」粗估

#### H. 最终布局定稿：计时器占掉 contentText，标题靠换行符拆两行

这一节是 3.7 全部实测的收敛结果，也是原型与后续实现的唯一依据。

##### H.1 计时器占用的就是 contentText 那一行

一开始以为 `setUsesChronometer(true)` 是「在原有内容之外再插一行时间」。
**用对照组才发现不是**：除了计时器以外完全相同的两条通知

| 变体 | 渲染出的三行 |
|---|---|
| `mode=nochrono`（无计时器） | `对照组 无计时器` / `▸ CT行动行在这里` / `第3步 / 共5步` |
| `mode=chrono`（有计时器） | `对照组 无计时器` / `02:37` / `第3步 / 共5步` |

同一个位置，`setContentText("▸ CT行动行在这里")` 被 `02:37` **整体顶掉**，
不是挤到别处、也不是消失。也就是说：

> `setUsesChronometer(true)` 会**接管 `setContentText` 那一行**，
> 二者不能共存。想让时间出现，就必须放弃 contentText。

##### H.2 标题可以塞换行符强行拆成两行

`setContentTitle` 实测支持 **2 行**。既然 contentText 被计时器占了，
就把「汇报」和「当前动作」都塞进 title，用换行符强制断行：

```kotlin
builder.setContentTitle(
    "已完成登录页重构与接口联调" + "
" + "▸ 正在处理表单校验边界情况"
)
```

渲染出来就是两行，第二行用 `▸` 前缀与第一行区分。

**注意**：这是 2 行硬上限。标题第 1 行过长会自己折行占满两行，
把第二行的动作行整体挤掉（只显示 `…`）。所以第 1 行的字数必须压住。

##### H.3 真机渲染顺序（与原型 v3 不同）

```
已完成登录页重构与接口联调        ← setContentTitle 第 1 行：汇报
▸ 正在处理表单校验边界情况        ← setContentTitle 第 2 行：当前动作
08:07                            ← 计时器（占 contentText 行）
第3步 / 共5步：搜索调用点          ← setSubText
[分段进度条]                      ← ProgressStyle，Segment(1) × N
[图标按钮][图标按钮]              ← Notification.Action，上限 3
```

关键点：**`setSubText` 在进度条上方，不是下方**。
这一条我第一版原型画错了（放在进度条下面），已按真机改正。

##### H.4 完整构造代码（真机已验证）

```kotlin
val progress = Notification.ProgressStyle()
    .setStyledByProgress(false)
    .setProgress(done)
    .setProgressSegments(List(total) { Notification.ProgressStyle.Segment(1) })

builder
    .setSmallIcon(R.drawable.ic_stat_link)
    .setContentTitle(report + "
" + "▸ " + currentAction)
    .setSubText(stepText)              // 必须在进度条之前
    .setWhen(startedAtMs)
    .setShowWhen(true)
    .setUsesChronometer(true)          // 占用 contentText 行
    .setChronometerCountDown(false)
    .setStyle(progress)
    .setOngoing(true)
    .setOnlyAlertOnce(true)
    .setCategory(Notification.CATEGORY_PROGRESS)
    .addExtras(Bundle().apply {
        putBoolean("android.requestPromotedOngoing", true)
    })
```

`Segment(1)` 每段一律给 1 的原因见 3.6（给大了会让圆点与绿条错位）。

##### H.5 还有一个必须知道的取舍

因为计时器占了 contentText、标题只有两行，所以**一张卡片最多承载三层文字**：
汇报（title 1）、当前动作（title 2）、步骤说明（subText）。
流式输出的「滚动」在真机上做不到（BigTextStyle 只渲染 2 行且不滚动，
见 3.5），只能维护「最近一次汇报 + 当前动作」的快照。

## 4. 与本项目现状的差距分析

### 4.1 已有的基础（R056/R057 已完成）

- `core/notify/` 17 个文件：`NotificationCenter`、`NoticeChannels`（ASK/DONE/SERVICE 三频道）、
  `NoticeText`、`NoticeActionReceiver`、`NoticeIdPool`、`OutcomeNotice`、`AccountNotice`、`LinkNotice`。
- `core/service/` 9 个文件：`ForegroundLinkService`（specialUse 型前台服务）、
  `ServiceNotice`（`NOTICE_ID = 151_074`）、`LinkServiceController`。
- `AndroidManifest.xml:10` 已声明 `POST_NOTIFICATIONS`。
- 已有的审批链路：`RemoteEventsClient` 的 waterfall 审批订阅 → `NotifyCoordinator` → `NoticeActionReceiver`。

**这意味着流体云不是从零开始**：审批已经有一条完整的「事件 → 通知 → 用户点按钮 → 回调」链路，
流体云只是**换一个渲染层**，把这条已有的通知变成 promoting 的即可。

### 4.2 必须新增的东西

1. `AndroidManifest.xml` 增加 `POST_PROMOTED_NOTIFICATIONS` 权限声明。
2. 新增一个「流体云」通知频道（不能复用现有三个：频道重要性一旦创建不可改，
   而现有 `SERVICE` 是 `IMPORTANCE_MIN`，**MIN 渠道不能提升**，这是硬失败点）。
3. 一个 `CapsulePublisher`（或扩展 `NotificationCenter`）：
   - 用固定的、单一的 notification id（实测「ColorOS 始终只认一个胶囊 ID」）
   - 构造 `ProgressStyle` + `requestPromotedOngoing` extras
   - 每次状态变化原地 `notify()` 同 id
4. 一个能力探测 + 引导：
   - `nm.canPostPromotedNotifications()` 判断
   - 不行时在设置页/首页显示提示行 + 深链按钮
5. 状态机 → 胶囊文案的映射（把 `CarrierState` / 工具执行进度翻译成 `shortCriticalText` + `contentText` + 进度）。

### 4.3 与现有 `ForegroundLinkService` 的关系

**两条通知，职责不同，都要有**：

| | `ServiceNotice`（已有） | 新流体云 |
|---|---|---|
| id | `151_074` | 新建，固定单一 |
| 频道 | `SERVICE`（`IMPORTANCE_MIN`） | 新建 `IMPORTANCE_HIGH` 或 `DEFAULT` |
| 作用 | 满足前台服务「必须有通知」的硬要求 | 用户可见的实时状态 |
| 提升 | **不提升**（MIN 渠道不行） | 提升为胶囊 |

⚠️ **不能合并成一条**：合并会导致前台服务通知被提升成胶囊 → 用户切到别的 App 时
状态栏永远挂着一个胶囊，而 ColorOS 的胶囊是「进行中任务」的语义，长期占用会被用户
反感并直接关掉（一关就永久失效）。**状态归状态，任务进度归任务进度。**

### 4.4 合规张力（必须正视）

Google 官方 Live Updates 文档明确列出**不适用**场景，其中包含：

> 聊天消息（chat messages）、提醒（reminders）、即将发生的日历活动、快速访问应用功能

我方用途是「显示 AI 对话/工具执行状态」，**接近但不等同于聊天消息**：
- ✅ 可以做：工具正在执行、进度 X/Y、等待用户批准（这是一个**进行中的进程**，正是 Live Updates 的设计意图）
- ⚠️ 要避免：单纯把「收到一条新消息」提升成胶囊（这正是文档禁止的「聊天消息」）
- 官方文档同时说明「OEM 可以针对实时动态资格强制执行其他条件」，ColorOS 有自己的过滤

**这不是 Play 上架阻塞项**（本 App 是自用/侧载），但影响「会不会被系统稳定渲染」。

## 5. 推荐方案

### 方案 A（推荐）：官方 API + 能力探测 + 优雅降级

1. **新增 `core/capsule/` 包**，含 `CapsulePublisher`、`CapsuleState`、`CapsuleText`。
2. `CapsulePublisher` 只在 `canPostPromotedNotifications() == true` 时走提升路径，
   否则**回落到现有通知**（用户仍能收到普通通知，功能不丢）。
3. 单一固定 id，所有更新原地覆盖（实测平滑）。
4. 审批态用 `addAction` 挂「批准」「拒绝」——实测有效，且**最多只能 3 个**，
   所以多选题超过 3 项的，胶囊只放「批准 / 拒绝 / 打开 App」，详细选项引导到 App 内。
5. `deleteIntent` 感知用户划掉，状态回到 `Idle`。
6. 设置页加一行「流体云」状态：`已开启 / 未开启（点击去设置）/ 本机不支持`。

**风险**：
- 用户不开开关就永远看不到（实测默认 `ignore`）→ 用 4 的引导行缓解
- ColorOS 固件更新可能改变渲染行为（FluidCapsule 项目 README 原话：
  "最终实时通知由操作系统渲染，系统固件更新可能改变其行为"）
- 只能在 ColorOS 16+/Android 16+ 生效；旧系统必须走回落

### 方案 B（不推荐）：通知监听 + 二次发布（FluidCapsule 的做法）

用 `NotificationListenerService` 收别的 App 的通知，再提升成自己的胶囊。
**对我方无意义**：我们是自己产生状态，不需要监听别人的通知。这条路径只适合做「通知聚合器」。

### 方案 C（明确排除）：Xposed / LSPosed 私有钩子

`mouzuan/FluidCloudExtension`、`Mubai-meng/FKColorOS` 走的是这条路。
**排除理由**：需要 root + LSPosed，用户设备上不可能要求；且 ColorOS 17 已把
`POST_PROMOTED_NOTIFICATIONS` 开放给普通 App，没有理由再用私有手段。

## 6. 复现方法（供后续阶段验证）

原型工程在 `F:\bot\_fcprobe`（**不在本仓库内，是调研用临时工程**）。

```powershell
cd F:\bot\_fcprobe
$env:JAVA_HOME='E:\JDK 21'; $env:ANDROID_HOME='F:\Android\Sdk'
$env:ANDROID_SDK_ROOT='F:\Android\Sdk'; $env:GRADLE_USER_HOME='F:\gradle-home'
.\gradlew.bat :app:assembleDebug --offline
$ADB='F:\Android\Sdk\platform-tools\adb.exe'
& $ADB -s 3B658N00HXC00000 install -r app\build\outputs\apk\debug\app-debug.apk
& $ADB -s 3B658N00HXC00000 shell am start -n probe.fc/.MainActivity
# 用户手动开：设置 → 通知与状态栏 → 流体云 → 应用提醒 → FCProbe → 流体云显示实时活动
# 验证：
& $ADB -s 3B658N00HXC00000 shell cmd appops get probe.fc POST_PROMOTED_NOTIFICATIONS
& $ADB -s 3B658N00HXC00000 shell input keyevent KEYCODE_HOME
# 截图看状态栏胶囊，点击 (534, 66) 展开
```

**关键坑（实测踩过）**：
- 截图是 540 宽而设备是 1080 宽，**点击坐标要 ×2**。第一次点胶囊点到了时钟区。
- `pm grant` / `cmd appops set` 在零售机上被拒：
  `SecurityException: uid 2000 does not have MANAGE_APP_OPS_MODES`。
  **只能靠用户在系统设置里手动开**，这也是为什么必须做引导行。
- `uiautomator dump` 拉文件要用 `adb pull` 且中文会因编码变乱码，
  用 `adb exec-out cat` 也拿不到干净 UTF-8；解析时按 `errors='replace'` 处理即可，
  **位置信息（bounds）是 ASCII，不受影响**。

## 7. 风险清单

| 风险 | 等级 | 缓解 |
|---|---|---|
| 用户不开开关 → 功能静默失效 | **高** | `canPostPromotedNotifications()` 探测 + 设置页引导行 + 深链 |
| 固件更新改变渲染 | 中 | 回落路径始终可用；`canPost` 每次动态检测 |
| 卡片最多 3 个 action | 中 | 超出部分引导回 App |
| 合规（聊天消息不适用） | 中 | 只用于「进行中的工具执行」，不用于「新消息提醒」 |
| 旧系统（< Android 16）无此能力 | 低 | 按版本回落，无副作用 |
| ColorOS 胶囊长期占用被用户反感 | 中 | 任务结束立即 `cancel`；不把前台服务通知提升 |
