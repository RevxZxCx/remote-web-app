## T004 · M1 真机链路验证（协议层 + 配对 + 凭证）

**时间**：2026-10-13 12:40–13:20
**目的**：M1 的验收标准是「真机配对成功 + 调通 `workspace/follow`」。本轮**没有真机**（`adb devices` 为空，也没有 emulator 镜像），所以改为用**真实的 Kotlin 客户端代码**打**真实运行中的 DSH 实例**（`127.0.0.1:19387`）——验证的是同一份 `PairingApi` / `TypertClient` / `RemoteStreamMux` 本体，只少了 Android UI 那一层。

### 环境
- 桌面端 DSH 在跑：`GET http://127.0.0.1:19387/api/pair/status` → 200。
- `adb devices` 输出为空；`F:\Android\Sdk\emulator\emulator.exe` 不存在（未装 emulator 包，也没有 AVD）。
- 无真机 → 用 JVM 单测跑真实协议栈，见 `app/src/test/java/.../core/integration/LiveHarnessTest.kt`。

### 方法
1. 先写一次性 Node 探针（`F:\bot\_m1_probe.mjs`、`_m1_wires.mjs`）摸清真实契约：用**故意传错参数**的办法从服务端 `gateway/arguments-invalid` 的报错里读出每个端点的**权威 wire 名**，并用真实实例确认时间字段是 ISO 字符串。
2. 把探针结论落到 `DshEndpoints.kt` / `DshTime.kt` / `WorkspaceFrameParser.kt`。
3. 再写 `LiveHarnessTest` 用**产品代码**复跑同一条链路，作为回归测试长期保留。

### 结果：✅ 通过（2 项全绿）

```
.\gradlew.bat :app:testDebugUnitTest --tests '*LiveHarnessTest*'
BUILD SUCCESSFUL
LiveHarnessTest  tests=2 failures=0 errors=0 skipped=0
```

两条用例：
- **`配对 + unary + mux 全链路对真实实例可用`**：`issue`（loopback）→ `PairingApi.accept` 拿到 `deviceId` → `TypertClient.callRaw("session/list")` 返回带 `items` 的对象 → **反证**：把 wire 名换成 `request` 必须失败（证明 `_request` 这个结论是被真实验证过的，不是碰巧）→ `RemoteStreamMux.open("workspace/follow")` 首帧解析为 `WorkspaceFrame.Baseline`，且 `items` 非空、`createdAt > 0`（证明 ISO 字符串→毫秒的解析是对的）→ `revoke` 清掉自己创建的设备。
- **`伪造设备 id 会被 remote 通道拒绝`**：用 32 个 `0` 当 deviceId 调 `/remote`，必须失败且原因是 `unpaired` / `forbidden` / 403。这是安全模型（D16/D17）的核心断言。

**副作用控制**：测试自己 issue token、自己 revoke 设备，不动用户已有的配对设备。

### 失败项与修复

#### 失败项 1：`issue` 传 `address` 被判 `unknown-address`
```
java.lang.AssertionError: issue 失败：HTTP 400 {"ok":false,"code":"unknown-address"}
```
**原因**：`handleIssue`（`src/routes.ts:686-731`）的 `address` 必须是桌面端**已知的 LAN 地址**，我随手传了 `"127.0.0.1"`，不在 `service.lanAddresses` 里。
**修复**：`issueToken()` 改成传**空对象**，让服务端自己挑 `publicBaseUrl ?? lanBaseUrl`。
**教训**：`issue` 的 `address` 不是「想监听哪个地址」，而是「从已知地址里选一个」。App 不调这个接口（loopback-only），只有测试代劳时才需要小心。

#### 失败项 2：JUnit4 断言参数顺序写反（3 处编译错误）
```
Argument type mismatch: actual type is 'Boolean', but 'String!' was expected.
```
**原因**：我按 `kotlin.test.assertTrue(condition, message)` 的习惯写，但项目用的是 **JUnit4**，签名是 `assertTrue(String message, boolean condition)`——**message 在前**。
**修复**：全部改成 `assertTrue("说明", 条件)` / `assertEquals("说明", 期望, 实际)`。
**教训**：同一个项目里断言库要统一。本项目 `app/build.gradle.kts` 只依赖 `junit:junit:4.13.2`，所以一律按 JUnit4 的顺序写。

### 本轮的契约发现（重要，已落进代码）
1. **wire 名不是统一规则**：多数方法是 `request`，但 `session/list` 是 **`_request`**（源码签名 `async list(_request, signal)`）。传错就是 `missing "_request"; unexpected "request"`。
2. **时间字段线上是 ISO-8601 字符串**（如 `"2026-10-12T21:25:11.055Z"`），而类型声明里写的是 `number`。`DshTime.epochMillis` 两种都吃。
3. **`workspaceFiles/*` 的第一个参数是 Typert lookup**，wire 名 `workspaceFileScopeId`，传的是 **sessionId**（服务端据此推导 workspace 根）。
4. **`workspace/follow` 首帧就是 `baseline`**，`items` 里带全部工作区。

**教训**：`wire` 名与「类型声明里的字段名」**可以不同**，永远不要从 `.d.ts` 猜 wire 名——要用真实实例读出来（本轮的探针手法见上「方法」第 1 步）。

## T008 · 隧道路径（公网）可用性排查

**时间**：2026-10-13 14:48–15:05
**目的**：T007 遗留项 ① 要求补测隧道路径。用户拔掉 USB 后，`https://5b4551427f0ab7aa.dsh-market.com` 是**唯一**远程入口（LAN 不可用，见下），所以这条路径不通等于 App 在户外完全不可用。

### 结果：❌ 隧道路径当前不可用，**原因在桌面端环境，不在 App**

**证据链**：

1. **LAN 结构性不可用**（不是配置问题）：
   ```
   GET /api/pair/lan-bind → { bindHost: "127.0.0.1", lanUrls: [], setting: null }
   Get-NetTCPConnection -LocalPort 19387 → LocalAddress 127.0.0.1
   ```
   服务只绑回环，`lanUrls` 为空，因此 `lanAvailable: false`、`lanAddresses: []`。
   桌面端本机有 `192.168.0.106`（以太网），但服务没绑到它。

2. **公网入口返回的是 relay 层的 405，不是插件的响应**：
   ```
   手机 curl https://5b4551427f0ab7aa.dsh-market.com/api/pair/status
   → 405 {"success":false,"result":null,"errors":[{"code":10005,"message":"Method Not Allowed"}]}
   ```
   注意这个 JSON 形状（`success`/`errors`/`code:10005`）**不是**插件的响应格式（插件是 `{ok:...}`），说明请求还没到本地插件就被中继层拒了。

3. **`tunnel` 进程在崩溃-重启循环**：
   ```
   14:59:53 tunnel=starting
   15:00:03 tunnel=failed  "the tunnel process exited unexpectedly"
   15:00:08 tunnel=starting
   ...
   distinct states over 40s: starting ×6, failed ×2
   ```

4. **根因（手动复现）**：用同样参数直接跑 `cloudflared`：
   ```
   INF Requesting new quick Tunnel on trycloudflare.com...
   failed to request quick Tunnel: Post "https://api.trycloudflare.com/tunnel":
     context deadline exceeded (Client.Timeout exceeded while awaiting headers)
   ```
   即 **`cloudflared` 拿不到 quick tunnel**。验证是网络问题而非 cloudflared 故障：
   ```
   POST https://api.trycloudflare.com/tunnel  direct → 超时
   POST https://api.trycloudflare.com/tunnel  via proxy 127.0.0.1:7897 → 200
   ```
   本机直连 `api.trycloudflare.com` 超时，走 Clash 代理（`127.0.0.1:7897`）则 200。

5. **为什么 `relay.state` 仍是 `running`**：`relay` 用的是**已注册的固定身份** `5b4551427f0ab7aa`（`C:\Users\26903\.dsh\remote-web-ui-registry\desktop.json`），它不需要每次新建 quick tunnel，所以中继自身显示正常；但把流量转回本机的那条 `cloudflared` 隧道（`tunnel.state`）建不起来，于是公网请求到不了插件。

### 结论与处置

- **不是 App 缺陷**：App 侧的隧道路径代码（`https://` → `wss://`、`HostPolicy` 放行 https、`/remote` 前缀、`?device=` 查询参数）与 USB 路径共用同一套已通过 T007 验证的代码，只差一个可达的地址。本轮**无法**在真机上验证隧道，因为隧道本身没建立。
- **修复不在本仓库**：需要桌面端让 `cloudflared` 能出网。两个方向（都需要用户决定，本轮不动）：
  1. 给 cloudflared 配代理（cloudflared 的 `--proxy-*` 只作用于 origin 侧，不作用于 `api.trycloudflare.com` 的控制面调用；需要用 Clash 的 TUN 模式或系统级代理让它透明出网）；
  2. 或改用**具名隧道**（`cloudflared tunnel run <name>` + 预创建凭证），不依赖 `api.trycloudflare.com` 的 quick tunnel 申请。
- **对 App 的影响**：M2 之后若要支持「户外使用」，必须先解决隧道；在那之前 App 只在 USB / 局域网可用。这属于**部署环境**问题，已记入 `环境与构建.md` 的遗留。

## T014 · 公网隧道路径打通 + churn 根治（T008 的关闭项）

- 时间：2026-10-13 19:09 – 19:20（根因定位与修复跨越 15:00–19:20）

### 结果：✅ 通过 —— 公网入口连续 3 分钟 100% 可用，隧道零 churn

### 一、两个互相独立的故障（T008 只看到了其中一个）

**故障 A：控制面（`api.trycloudflare.com`）不可用。**
本机 DNS 给出的 anycast IP 对 `POST /tunnel` 稳定返回 **429**（`error code: 1015`、`Retry-After ≈ 2500s`），且限流会随时间轮换到不同 IP：

```
104.18.0.1 / 104.18.1.1 / 104.16.0.1 / 104.18.2.1 ... → 429 retry-after≈985~1000
104.17.24.185 / 104.17.25.185                        → 200 {"success":true,...}
104.19.0.1 / 104.16.230.132 / 104.16.231.132         → DIAL timeout
```

**`cloudflared` 不认 `HTTPS_PROXY`/`HTTP_PROXY`/`ALL_PROXY`**：导出三个变量后重跑，日志停在 `Requesting new quick Tunnel on trycloudflare.com...` 再无下文。`--proxy-*` 全部注明 *only takes effect if you define your origin with `--url`*（只管回源侧）。→ **代理路线整体不可行**。

**故障 B：数据面（edge `TCP/7844`）被按 SNI 阻断。**
这是本轮最关键的发现，也是 cloudflared 官方文档不涉及的一层：

```
同一 edge IP 198.41.200.63:7844，同一条代理出口，只换 ClientHello 里的 SNI：
  region1.v2.argotunnel.com   → OK    TLSv1.3
  region2.v2.argotunnel.com   → OK    TLSv1.3
  h2.cftunnel.com             → ECONNRESET ~0.6s
  probe.cftunnel.com          → ECONNRESET ~0.6s
  quic.cftunnel.com           → ECONNRESET ~0.6s
  H2.cftunnel.com / h2.CFTUNNEL.com → ECONNRESET（大小写都拒 → 是后缀匹配）
  h2.cftunnel.com.            → ERR_SSL_TLSV1_ALERT_DECODE_ERROR
  argotunnel.com（裸域）       → 失败（→ 只放行这两个精确名字，不是 DomainSuffix）
  example.com / www.cloudflare.com → 12s 超时（不是快速断开，形态不同）
```

而 **cloudflared 二进制里写死的 edge SNI 恰好全是 `*.cftunnel.com`**（`h2.cftunnel.com` @16228048、`quic.cftunnel.com` @16243501、`registerConnectionprobe.cftunnel.com` @16252796）——正是被拒的那个后缀。讽刺之处：**edge 出示的证书 SAN 本身就是 `DNS:*.cftunnel.com, DNS:cftunnel.com`**，即 edge 服务的正是这个名字，但链路上它被拒。

- 端口无关：`7844` 是唯一能完成握手的端口；`443/7843/8443/2053` 上 `region1` 分别是 `HANDSHAKE_FAILURE`/超时，`*.cftunnel.com` 一律 `ECONNRESET`。
- **不是 Clash 的域名分流**：mihomo `/connections` 记录显示该连接 `host=`（空）、`rule=Match()` → 没把 SNI 用于选路，阻断发生在代理隧道**下游**。
- **不是 DNS 污染**：system / `8.8.8.8` / `1.1.1.1` / `223.5.5.5` / `119.29.29.29` 五个解析器答案一致。
- **直连路线判死**：直连 12 个 edge IP，3 个 TCP 可通，但 TCP 通了以后 **TLS 100% 不成功**（`_direct_tls.mjs`：`198.41.200.63 → tcpFail=5 tlsOk=0 tlsTimeout=7`；`198.41.192.67 → tcpFail=10 tlsOk=0 tlsTimeout=2`）。
- **SNI 改写路线判死**：写 `tools\..\_relay_debug.mjs` 做字节级 SNI 改写，修好一个 off-by-two（`extTotalOff` 必须指向 extensions 块首字节，取值后 `p += 2`），改写本身成功（`reparse=region1.v2.argotunnel.com`），edge 也真的回了 ServerHello，但本机报 **`error:0A000119 tls_get_more_records:decryption failed or bad record mac`**。→ **TLS 1.3 把整个 ClientHello（含 SNI 字节）纳入密钥派生，中继改 SNI 必然导致 Finished / record MAC 校验失败，此路不可能通。**

### 三、churn 根因（T008 完全没看到的一层）

隧道虽然建得起来，但**每约 2 分钟换一次 URL**，每次重启窗口内 `https://5b4551427f0ab7aa.dsh-market.com` 返回 **530**（origin 消失）——手机拿不到任何东西，是真实的可用性缺陷，不是外观问题。

```
18:35:13 tunnel=starting relayHTTP=530
18:35:20 tunnel=running  relayHTTP=200  bloggers-persons-mass-province...
18:35:59 tunnel=running  relayHTTP=000
18:37:37 tunnel=failed   relayHTTP=530
18:37:43 tunnel=starting relayHTTP=530
```

**根因**：插件 `TunnelManager` 每 60s 用 `probeTunnelUrl()`（`src\tunnel.ts:132`）探测**它自己刚铸造的 quick tunnel URL**，判定标准是 `response.status < 500`；连续 2 次失败（`DEFAULT_HEALTH_CHECK_FAILURES = 2`，`src\tunnel.ts:255`）就 `this.fail('the tunnel stopped answering on its public URL')` 并重启。探测失败的原因是 OS 解析器把 `*.trycloudflare.com` 解析到 **`104.16.230.132` / `104.16.231.132`**，而这两个 IP 在链路上**完全不可达**（`curl` 15s 超时、Node `fetch` 10s AbortError）→ 健康隧道被判死。

- 复现：`node -e "fetch(url,{redirect:'manual',cache:'no-store',signal})"` → `FAILED AbortError ms 10006`（正好是插件的 10s 超时）。
- 对照：同一 hostname `--resolve <host>:443:104.18.0.1` → **401 / 1.1s**（插件要求活着的响应）→ 只要解析到健康 IP 就算活。
- **插件没有可调旋钮**：`healthCheckIntervalMs` / `healthCheckFailures` / `probeTimeoutMs` 只是 `TunnelManager` 的构造器 seam，配置 schema 里不暴露，且 `new TunnelManager()` 是无参构造（`lib\index.js` @167814）→ **不能靠改配置关掉看门狗**。

**修法**：`tools\tunnel-health-pin.mjs` 每 5s 查插件 `/api/pair/status`，把**当前** live hostname pin 到可达 anycast IP（`104.18.24.129`），并淘汰过期的 pinned 行。这样插件的探测与 App 的访问都命中健康 IP。

### 教训

1. **「A 方案能跑通」必须先确认探针与真实客户端走的是同一条路。** 早期结论「走 Clash 代理 100% 可用」是**假阳性**——那个探针的 SNI 默认写的是 `region2.v2.argotunnel.com`（`_edge_relay.mjs:7`、`:38`），而 cloudflared 真实用的是 `h2.cftunnel.com`；换成真实 SNI 就复现不了。**探针的 SNI 必须从被代理程序的二进制里取，不能自己挑一个「看起来对」的。**
2. **TLS 1.3 下不要在中间人位置改 ClientHello。** 改 SNI 会破坏 transcript → record MAC 失败。要中继就做纯字节透传（本方案的 relay 就是这么做的）。
3. **「控制面通了」不等于「隧道通了」。** T008 只看到控制面，修好它之后才暴露出数据面 SNI 阻断，修好数据面之后才暴露出 churn。三层故障必须逐层验证到端到端可用为止。
4. **T008 的处置建议（给 cloudflared 配代理 / 改用具名隧道）两条都错。** cloudflared 根本不走代理变量；而具名隧道同样要用被拒的 `*.cftunnel.com` SNI，换隧道类型解决不了 SNI 阻断。真正起作用的是**换一个接受该 SNI 的代理节点**。
5. **churn 的修法只能落在 DNS 层**，因为插件的健康探测参数不暴露。这属于「被测服务的部署环境缺陷」，本仓库只能以 `tools\` 助手的形式绕过；若插件后续版本暴露 `healthCheckFailures`，应优先改用配置。
6. `hosts` 写入的唯一可靠姿势是这个仓库里反复用到的写法（PowerShell 管道写会破坏 UTF-8，且文件被占用时会先截断后失败）：
   ```powershell
   [IO.File]::WriteAllText($h, $final, (New-Object Text.UTF8Encoding($false)))
   ```
   备份在 `C:\Users\26903\.dsh\hosts.bak-20261013` 与 `hosts.bak-t009-2`。
7. `tools\tunnel-services.ps1` **必须保持纯 ASCII**：Windows PowerShell 5.1 会把 BOM-less 的 `.ps1` 当 ANSI 读，一个 em dash 就会变成乱码并破坏脚本。

### 四、复验期新暴露的缺陷 1：`.scan` 种子空快照谎报「已连接」

**现象**：冷启动后约 1.9s 就显示「已连接 / 这个桌面端还没有工作区。」，而真实工作区要 2.9s 后才到。5 次冷启动实验中 **2/5** 停在这个假空态，且 banner 全部谎报「已连接」。

**根因**（`core/workspace/WorkspaceRepository.kt`）：流水线用 `.scan(WorkspaceSnapshot())` 折叠，`scan` **在订阅时立即发射初始值**。该文件 KDoc 明确写着「故意不放 `onStart { emit(WorkspaceSnapshot()) }`，因为重试会重新订阅，首帧空快照会让每次断线重连都先清空列表」——**意图被 `scan` 的初始发射抵消**。

**修复**：`.scan(null as WorkspaceSnapshot?) { acc, frame -> WorkspaceReducer.reduce(acc ?: WorkspaceSnapshot(), frame) }.filterNotNull()`，让「还没有任何快照」与「快照是空的」在类型上可区分。另加 `.filterNotNull()` 处理 `parser.parse()` 的可空返回。

**编译坑**：`scan` 有两个类型参数 `<T, R>`，写 `.scan<WorkspaceSnapshot?>(null)` 只给了 R → `Cannot infer type for type parameter R`。必须写 `null as WorkspaceSnapshot?` 显式给出 R。（`runningFold` 同样会发射初始值，不可用。）

**给这条根因补的回归测试** `WorkspaceRepositoryTest`（4 项，mockwebserver3 + 真实时间 `runBlocking`）：
1. `emitsNothingUntilFirstServerFrame` —— **核心守护**：订阅后等满 2 秒必须一帧都没发射（旧实现会命中 1 个空快照）
2. `baselineAfterUpsertReplacesWholeSnapshot` —— upsert 后收到 baseline 必须整表替换而非合并
3. `unknownFrameTypeIsIgnored` —— 未知帧类型被忽略且不影响后续帧
4. `subscribesWithExactEndpointAndNoArguments` —— 握手路径 `remote.mux?device=`、open 帧 `endpoint=workspace/follow`、`payload.args` 为空对象

**写这个测试时踩的坑（首跑 3/4 失败）**：测试把工作区帧**裸着**推给客户端，但 mux 线格式要求服务端把负载包在 `{"type":"item","streamId":"<open 帧里的 id>","value":<负载>}` 里；裸帧被 `RemoteStreamMux.validate` 判为非法，按规矩以 **close code 4002**（reason `invalid Remote stream frame`）关掉整条连接 → 订阅者永远收不到帧。**这反而证明 4002 逻辑是对的。** 修法：解析客户端发出的第一条 open 帧取出 `streamId` 再包帧。

### 五、复验期新暴露的缺陷 2：WS 握手无超时（`连接中…` 永久停留）

**现象**：6 次冷启动实验中 **3/6** 在 12s 时还停在「连接中…」；实测有 **>40s** 才连上的样本。

**定位过程（主机侧对照，排除服务端）**：

| 对照项 | 结果 |
| --- | --- |
| 主机侧 loopback `session/list`（unary） | 8/8 成功，**89–152ms** |
| 主机侧经公网隧道 `session/list`（unary） | 8/8 成功，**1.0–1.9s** |
| 主机侧 mux 握手（loopback） | 升级 3–6ms / 首帧 3–8ms |
| 主机侧 mux 握手（公网隧道） | 平均 **1.79s** |
| 手机侧同一 mux 握手 | **15s 超时**（修复前**无任何回调**） |

**根因**：`core/net/HttpClients.kt` 的 `stream()` 用 `readTimeout(0)`（流式连接不能有读超时，这是对的），但 OkHttp 把**握手等待**也算在这次 read 里 → 握手挂死时既没有回调也没有超时，`RemoteStreamMux` 的 `waitForSocket()` 永久等待 → 界面永久「连接中…」，退避重连逻辑根本没机会跑。

**修复**：`RemoteStreamMux` 新增 `HANDSHAKE_TIMEOUT_MS = 15_000`，在 `waitForSocket()` 的 `deferred.await()` 外层加 `withTimeoutOrNull`，超时后按传输错误抛出，交给上层的 `retryWhen` 退避重试。

**修复后证据**：logcat 出现 `Canceled`（15s 超时）→ 退避重试 → **成功建连**，工作区列表出现。即「永久卡死」变成「最多等 15s 后可恢复」。

**诚实记录：剩余问题不在 App**。修复后仍有约 3/6 冷启动在 12s 内没连上（>40s 的极端样本也有），但主机侧经同一隧道只要 1–2s，且手机侧失败形状是**读超时**（而非协议错误）→ 归因于**手机 → Cloudflare 这条链路的网络质量**，不是 App 代码缺陷。已把该结论写进 `开发进度.md` 的遗留项。

### 六、复验期新暴露的缺陷 3：抽屉里失败与「没有会话」不可区分

`sessionsError` 的黄条只在主区渲染，抽屉里看不到 → `session/list` 超时（手机侧读超时是常态）与「这个账号真的没有会话」在抽屉里长得一模一样。

### 七、附带修正：`session/page` 的 `throughSeq = -1` 语义（KDoc 原来是错的）

`ChatArgs.page` 的 KDoc 原文写「`-1` 表示到日志头」。**实测证伪**：服务端 `paginate` 里 `end = Math.min(throughSeq + 1, beforeSeq ?? throughSeq + 1)`，`throughSeq = -1` 算出 `end = 0` → `slice(cut, 0)` 恒为空页。`validatePageRequest` 允许 `>= -1` 只是不报错，**不代表语义是「到日志头」**。已改正 KDoc：必须传真实游标（快照的 `cursor`）。

### 八、工具层面的教训（本阶段新增）

1. **屏幕休眠时 `uiautomator dump` 抓到的是锁屏**（`package="com.android.systemui"`），会得出假阴性。dump 前必须 `input keyevent KEYCODE_WAKEUP` + `wm dismiss-keyguard`，并在 dump 后校验 XML 的 package 含本 App，否则丢弃该次采样。
2. **PS 5.1 的 `Invoke-WebRequest` 对公网隧道报「未能创建 SSL/TLS 安全通道」是 PS 自己的 TLS 问题**，不是隧道故障。判定网络可用性优先用 node `fetch`。
3. **不能把 node 脚本内联进 PowerShell 命令**（`"`/`[`/`||`/`)` 会被 PS 解析器破坏并报 `MissingTypename`），必须写成 `.js`/`.mjs` 文件再 `node file.js`。
4. `.mjs` 里不能用 `require()`（`ReferenceError: require is not defined in ES module scope`），要用 `import { execFileSync } from 'node:child_process'`。
5. **`adb shell input text` 会被中文输入法联想成汉字**（实测 `M3-device-test-reply-OK-only` → `hell哦from安当然哦ID马3`）。必须临时 `ime disable` 搜狗与百度输入法，**收尾务必 `ime enable` + `ime set` 恢复**。
6. 点「发送」前要先 `input keyevent 4` 收软键盘，否则 tap 落在 IME 面板上。
7. `adb pull` 把「1 file pulled」写到 stderr → PowerShell 报 `NativeCommandError` 且 exit 1，但**文件其实已拉到**；判定要用文件是否存在/内容，不要用 exit code。
8. node v24 内置 `WebSocket` 与全局 `fetch`，写协议探针**不需要任何依赖**。

## T016 · M3.5 契约探针实测（文件读取 / 二进制 / 改动摘要三组线上形状）

配对流程：`POST /api/pair/issue {}` → `POST /api/pair/accept {token}` 取 `deviceId`，
之后所有 `/remote/api/*` 调用带 `x-dsh-remote-device` 头；收尾 `POST /api/pair/revoke {deviceId}`。

### 一、`workspaceFiles/*` 的真实形状

| 方法 | 必需参数 | 返回 |
| --- | --- | --- |
| `read` | `workspaceFileScopeId`、`path`、**`range`（必需）** | `{absolutePath,version,bytes,offset,text,lines,eof}` |
| `stat` | `workspaceFileScopeId`、`path` | `{absolutePath,version,bytes}` |
| `list` | `workspaceFileScopeId`、`path` | `{path,entries:[{name,type,size?}],truncated}` |
| `readBytes` | `workspaceFileScopeId`、`path`、**`options`（必需）** | **`multipart/form-data`（不是 JSON 信封）** |

**决定性发现**：

1. **`range` 和 `options` 是必需参数**，漏传报 `gateway/arguments-invalid: missing "range"`；传 `{}` 等于默认值。
2. **`range.offset` 是 1-based 行号**：`{limit:5}` → `offset=1 lines=5 eof=false`；再传 `{offset:6,limit:5}` 正好接上。
   推进公式 = **下次 offset = 本次 offset + 本次 lines**。
3. **服务端硬拒越界值**：`offset:0` → `gateway/bad-request` + `offset must be a safe integer of at least 1`；
   `limit:99999` → `limit must be at most 5000`。→ **客户端必须自己 coerce**（offset≥1、limit≤5000），
   否则一次误传就是整个文件查看页不可用。
4. **`version` 是不透明复合字符串**，形如 `2296164758:1688849860631842:539:1791865110422149900:1791865110430414700`，
   **不是数字**（早期按数字解析会静默得到 0）。App 侧类型为 `String`，从不解析。
5. **`workspaceFileScopeId` 传的是 `sessionId`**（服务端拿该会话的 `cwd` 推导工作区根）。
   实测：会话 cwd=`F:\bot` 时传 `app/build.gradle.kts` 报 `workspace-file/not-found`，
   传 `remote-web-app/settings.gradle.kts` 成功 → **相对路径相对会话 cwd，不是仓库根**。
6. **四种路径写法全部可用**：`remote-web-app/settings.gradle.kts`、反斜杠、`F:\bot\...`、`F:/bot/...`
   都解析到同一个 `absolutePath`。`dsh-resource://file/session/<id>/...` 服务端**不认**
   （`workspace-file/not-found`）→ App 不需要处理该地址形态。

### 二、`readBytes` 的 multipart 形状（二进制/图片/PDF）

成功时返回 **`Content-Type: multipart/form-data; boundary=----formdata-undici-...`**，单 part：

```
------formdata-undici-001661913666
Content-Disposition: form-data; name="bytes-0"; filename="blob"
Content-Type: application/octet-stream

<原始字节>
```

- PNG 实测：`bytes=311139`，**PNG 魔数位于偏移 143**（即上述头部长度）。
- **尾部还有一段 JSON 元数据**（`[{"...","codec":"bytes","part":"bytes-0"}]`），
  其后才是结束边界 → **part 内容必须按 boundary 切分，不能假设「到结尾」**
  （否则尾部 metadata 会被当成文件内容的一部分）。
- 失败时**仍是普通 JSON 错误信封**（不是 multipart）→ 客户端必须看 `Content-Type` 分流，
  否则会把错误 JSON 当二进制图片显示。
- 文本、PNG、Markdown **走同一通道，服务端无类型分支**。

### 三、改动摘要三路由（普通鉴权 HTTP，不是 Typert RPC）

| 路由 | 返回 |
| --- | --- |
| `GET /remote/api/changes.summary?sessionId=&seq=` | `{turn,files,total,added,deleted}` |
| `GET /remote/api/changes.diff?sessionId=&seq=&index=` | `{kind,path,display,before,after,hunks,coarse}` |
| `POST /remote/api/changes.open?...` | 204（无 body） |

**决定性发现**：

1. **`changes.diff` 的键名是 `before`/`after`（布尔，表示改动前/后文件是否存在）**，
   **不是 `beforeExists`/`afterExists`**。新增文件样本 `{"kind":"text","before":false,"after":true}`，
   修改文件两者皆 `true`。→ 解析器若读错键名，「新增」与「修改」在 UI 上无法区分
   （探针首跑时 `beforeExists` 读出 `undefined`，正是这个坑）。
2. **`changes.summary` 的 `total` 是截断前的完整文件数**，`files` 才是数组（可小于 `total`）。
   实测 seq=6237 → `turn=6,total=19`；seq=7865 → `turn=7,total=30`。
3. **失败回 `text/plain` 的 `404 Change summary unavailable.`**（不是 JSON 信封）。
   语义是「摘要已随 Host 进程消失」，与「这轮真的没改文件」（`total == 0`）**必须区分**。
4. **缺 device header 回 403 + `unpaired` 信封**。
5. **`workspace/changes` 事件的 `data` 里只有 `{turn}`**，文件清单不在事件里——
   必须拿该事件的 **`seq`** 去查 `changes.summary`。摘要只存在 Host 内存中，**Host 重启后旧轮次 404**。

### 四、工具调用里的文件路径参数名（决定工具卡片的文件行）

全量统计 51 个会话的所有 `tool/call`：

```
139 pwsh |  81 read | 75 write | 50 edit | 21 grep
 10 compress | 2 job_kill | 2 search_context | 1 todo_write | 1 decompress | 1 glob
```

- **带文件路径的只有 `read`/`write`/`edit`，且参数名统一是 `file_path`**
  （`write` → `{"file_path":...,"content":...}`，`edit` → `{"file_path":...,"old_string":...,"new_string":...}`）。
- **`str_replace_editor` 一次都没出现**（虽然桌面端插件会为它做整文件捕获）→ 保留兼容但不依赖。
- **键序不固定**：两个 `write` 样本，一个 `file_path` 在前、一个 `content` 在前 →
  **必须 JSON 解析，绝不能正则捞 `"file_path"` 后面的内容**。
- 其余工具（`pwsh`/`grep`/`compress`/`glob`/`todo_write`）不带路径，不该出现在文件行里。

### 结论

三组契约全部实测确认；其中 **`range`/`options` 必需、offset 1-based 与 limit≤5000、
`before`/`after` 键名、multipart 尾部 JSON、404 与 total==0 的语义差** 五条若不落实，
对应 UI 功能会直接不可用或给出错误结论。均已落进实现与 KDoc。

## T034 · 排队回声（用户 m20380 反馈「请用」消息不可见）

**背景**：用户发现一条早前打进 App 的测试文本「请用」在会话正在生成时没有任何回显，
直到当前轮结束才被服务端取出执行。用户原话：「是你之前自己的测试消息发出了，但是因为在对话，
所以没有发送到大模型端，对话完成后消息自动发送了」。

### 一、契约核实（全部逐字读过 SDK 源码）

走 wire 的远程客户端**拿不到服务端排队信息**，这是本功能必须做本地回声的根本原因：

| 事实 | 出处 |
| --- | --- |
| `session/prompt` 结果**只有 `{accepted: true}`**，不带 itemId | `typert.host.js:803-805` |
| `session/follow` 快照 result schema 逐行读完，**没有任何 queue 投影** | `typert.remote-client.js:222-341` |
| SDK 的 `pendingSubmissions` 是**进程内客户端**的本地回声，wire 客户端拿不到 | `client.js:1684-1707` `beginSubmission` |
| `session/updateQueue` 参数 `{sessionId, itemId, action}`，**必须要 itemId** | `typert.host.js:843-862` |

`updateQueue` 的 action 三选一：`{kind:'edit',content:[{type:'text',text}]}`（**只接受 text 块**，
服务端 `index.js:939` 非 text 抛 `session/attachment-invalid` + reason `QUEUE_EDIT_NON_TEXT`，
`:940` 空白抛 `gateway/bad-request`）/ `{kind:'remove'}` / `{kind:'steer}`；
错误码 `session/queue-item-not-found`（`index.js:947`/`:964`）。
**因为拿不到 itemId，`updateQueue` 对纯远程客户端实际上不可用** → 不做「撤回」按钮。

### 二、定案：回声一直在，是列表没滚到底

临时埋点（`android.util.Log.d("DSH-QUEUE", ...)`，三处：`ChatViewModel.send()` 的 echo 追加/成功/失败，
`ChatScreen` 的 `LaunchedEffect(state.queued.size)`）打出的现场：

```
12:58:53.250  echo added id=3 gen=true
12:58:53.282  queued size=1 ids=[3] items=164 live=false atBottom=false canForward=true lastIndex=164
12:58:53.288  prompt ok id=3
13:06:17.576  queued size=0 ids=[] items=166 live=true atBottom=false canForward=true lastIndex=166
```

**回声确实在 `state.queued` 里（size=1, id=3），RPC 也成功**；但 `atBottom=false canForward=true`
—— 列表停在半路，回声躺在视口下方。`uiautomator dump` **只报可见节点**，所以每次采样都看不到它，
我据此误判成「回声消失了」。

（13:06 那条 `size=0` 是 `user/message` 正常摘除：`items` 从 164 涨到 166。）

### 三、真正的缺陷：滚动跟随被 latch

```kotlin
var atBottom by rememberSaveable { mutableStateOf(true) }
LaunchedEffect(listState) {
    snapshotFlow { listState.canScrollForward }.collect { atBottom = !it }
}
LaunchedEffect(listState, lastIndex) {
    snapshotFlow { state.live?.text?.length ?: 0 }
        .collect { if (atBottom) listState.scrollToBottom(lastIndex) }
}
```

打开一个长会话时列表从索引 0 开始 → `canScrollForward` 恒真 → 上面的观察**立刻**把 `atBottom`
置 false；而本 effect 的 `snapshotFlow` 在 `live == null` 时**只发射一次 0**，于是
`if (atBottom)` 永不成立 → **列表永远停在顶部、`atBottom` 永远 false、之后再也不跟随**。

这同时是用户 **T7** 反馈「生成时文本到底部不自动滚到最新行」的**残余根因**：T7 当时修的是
`scrollToItem` → `scrollToBottom` 的对齐问题（那一半确实修好了），但跟随的闸门还 latch 着。
为什么之前几次设备验收没看到：会话刚打开时 `items` 往往是空的（无缓存）→ 列表不溢出 →
`canScrollForward=false` → `atBottom=true`，等内容到达时闸门还开着；**有热缓存（`warmStart`）
或会话已打开一会儿时才复现**。

### 四、修复

- 新建 `ui/chat/ChatScrollFollow.kt`：把「贴底跟随」整段逻辑抽成独立 `@Composable`

  渲染测试直接驱动**（这段逻辑的缺陷只在真实布局后现形）。
- 首帧内容到位时**无条件跳到底一次**（`jumpedToNewest` 是普通 `remember` 而不是
  `rememberSaveable`：`listState` 旋转后换新实例，标记必须跟着重置）。
- `liveLength` 必须是 lambda：`snapshotFlow` 只观察 Compose 快照系统里的对象，

### 三、顺带发现并加固：`scrollToBottom` 的补滚循环有屏数上界

`ChatScreen.kt` 原实现是 `while (canScrollForward && guard++ < 4) { scrollBy(viewportHeight) }`，
最多补滚 4 个视口高（≈4176px）。2844px 的行还在范围内，但**更长的消息会滚不到底**。

**定稿修法**：改成按溢出量一次到位，无 guard 上界：

```kotlin
scrollToItem(index)
scroll(MutatePriority.Default) {
    val last = layoutInfo.visibleItemsInfo.lastOrNull() ?: return@scroll
    val overflow = (last.offset + last.size) - layoutInfo.viewportEndOffset
    if (overflow > 0) scrollBy(overflow.toFloat())
}
```

收敛条件是 overflow 本身而不是「还能不能向前滚」——后者需要循环若干屏才收敛，而末行可能高过多屏。

**回归用例**：`ChatScrollFollowTest` 新增 `最后一行高过四屏时也能一次滚到底`
（视口 200dp、末行 1200dp = 6 屏；旧 `guard++ < 4` 只能滚 4 屏必然失粘）。

#### 🔴 设备验收抓到的两个真实缺陷（均已修复 + 变异验证）

**缺陷 A：点输入框永远展不开（④，P1 级）**

- 现象：收起态正确，但展开态**一连四次点击 + `input text` 都没反应**——权限 chip / 模型胶囊始终不出现，打进去的字也不进 draft。
- 根因：输入区写成 `if (!expanded) { Row{ AttachButton, ComposerField, ComposerSendButton } } else { ComposerField }`，
  `ComposerField` 出现在**两个不同的调用点**，Compose 视作不同节点。点一下 → 聚焦 → `expanded` 变真 → 走到另一分支
  **重建**出没有焦点的新节点 → `collectIsFocusedAsState` 立刻变假 → `expanded` 变假 → 回到原分支，如此往复。
- **为什么 18 条既有渲染测试没抓住**：它们都用 `draft`/`pending` 把界面直接摆到展开态，**没有一条走交互路径**。
- 修法：`Row` 无条件存在、`ComposerField` 永远在同一调用点，只把 `AttachButton` / `ComposerSendButton` 两根**兄弟**放进 `if (!expanded)`。
- 变异验证：给 `ComposerField` 套一层 `androidx.compose.runtime.key(expanded) { … }`（等价于两个调用点）→
  单跑 `ComposerLayoutRenderTest` → **`33 tests completed, 1 failed`，失败的正是新增的 `点输入框会展开并且不会自己缩回去`**。已还原并 grep 确认无残留。

**缺陷 B：模型胶囊被过度截断（④，P2 级）**

- 现象：`buddy/deepseek-v4.1-flash` 被截成「buddy/de…」。
- 根因：底排写成 `Box(Modifier.weight(1f, fill = false)) { modelChip() }` + `Spacer(Modifier.weight(1f))` ——
  **两个 `1f` 兄弟把剩余宽度对半分，而 spacer 一个像素都用不掉**。
- 修法：改成唯一弹性槽 `Box(modifier = Modifier.weight(1f)) { modelChip() }`（等价效果图 `.chip{flex:0 1 auto}` + `.spacer{flex:1 1 auto}`）
  → 修后显示 `buddy/deepseek-v4.1-fl…`，宽度从 195px 涨到 498px。
