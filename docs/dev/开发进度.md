**本阶段**确定的接口契约（见 `测试记录.md` T016）：

| 端点 | 关键点 |
| --- | --- |
| `workspaceFiles/read` | `{workspaceFileScopeId, path, range}`，**`range` 必需**；`range.offset` **1-based**；`limit ≤ 5000`（服务端硬拒，客户端必须 coerce） |
| `workspaceFiles/readBytes` | **`options` 必需**；成功回 **multipart/form-data**（不是 JSON 信封），失败才回 JSON |
| `changes.summary` | `GET /remote/api/changes.summary?sessionId=&seq=` → `{turn,files,total,added,deleted}`；**`total` 是截断前完整数** |
| `changes.diff` | `GET ...?sessionId=&seq=&index=` → `{kind,path,display,before,after,hunks,coarse}`，**键名是 `before`/`after`** |
| — | 摘要**只存在 Host 内存**：Host 重启后旧轮次回 `text/plain` 的 404；`workspace/changes` 事件体**只有 `{turn}`**，须拿该事件 `seq` 去查 |

**关键实现点**：
1. `workspaceFileScopeId` 传的是 **sessionId**（服务端拿会话 `cwd` 推导根）；相对路径是相对**会话 cwd**，不是仓库根。
2. `workspaceFiles/read` 的 `version` 是**不透明字符串**（`2296164758:1688849842:539:...`），别解析成数字。
3. multipart 的 body **尾部还有一段 JSON 元数据**，part 内容必须按 boundary 切分，不能假设「到结尾」；**必须按字节切**（先转 String 会破坏 PNG/PDF）。
4. 桌面端 `MarkdownText` 的策略是「冻结除最后两块外的全部块、只重解析尾部」——`MdStream` 照抄，并把「`update(text)` 恒等于 `MdParser.parse(text)`」写成**单测断言的不变量**。
5. 高亮库的 `CodeHighlight` 区间**可能互相交叉**，直接逐个 `withStyle` 叠加会「后加的被先加的盖住」→ 必须先压成逐字符表再合并。
6. `MdFileRef.looksLikePath` **故意保守**（误判代价 > 漏判）：相对裸文件名不算，带目录的相对路径算。**R005 发现盘符分支曾是死代码**（冒号在否决字符集里且先于盘符判断），已修为「先剥盘符再校验剩余部分无冒号」。
7. 三条限制**必须写进 UI 文案**：Host 重启后旧轮次无改动卡片与 diff；非 git 仓库里纯 shell 命令改的文件看不到；单文件 > 2 MiB 不做 diff。降级路径 = 「从工具调用推断的文件行 + 当前全文」。

**本阶段**确定的接口契约（源码核实，见 `需求文档.md` §3.5）：

| 端点 | 模式 | args wire 名 | 形状 |
| --- | --- | --- | --- |
| `session/follow` | ⚡流 | `request` | `{address:{kind:'session',sessionId}, assistantStream?:true, maxMessages?, turnWindow?}` |
| `session/page` | unary | `request` | `{address, throughSeq, beforeSeq?, maxMessages?, turnWindow?}` → `{records:[{type:'event',event}], hasMore}` |
| `session/prompt` | unary | `request` | `{requestId, sessionId, mode:'queue'\|'steer', content, clientTimeZone?}` → `{accepted:true}` |
| `session/cancel` | unary | `request` | `{sessionId}` → `{accepted:true}` |

**`session/follow` 帧**（`typert.remote-client.js:221-424`）：
- `{type:'snapshot', header, cursor, records:[{type:'event',event}], hasMore, projections, assistantStream?}`
- `{type:'event', event}`
- `{type:'assistant-stream', frame}` —— `frame` = `{type:'start',attemptId,revision,startedAfterSeq,turn,step}` / `{type:'chunk',attemptId,revision,index,time,chunk}` / `{type:'end',attemptId,revision,index,outcome:{kind:'committed',eventType,seq}\|{kind:'abandoned'}}`

**事件信封**（`lib/types/client/session-wire-event.js:10-42`）：`{type, seq, time, data, ignorable?, surfaceOp?, sourceEventSeqs?}`——**键是封闭集合**，多一个键服务端就会抛。

**关键实现点**：
1. `AssistantStreamRecord` 是**压缩**表示（`text-chunks` 带 `time0`+`dt[]`+`texts[]`），不是逐条 delta。`expandAssistantStream` 才是展开逻辑（`client.js:1251-1291`）：`time = time0`，之后 `time += dt[index-1]`，逐条产出 `{type:'text-delta'|'reasoning-delta'|'tool-call-delta', index, ...}`。
2. `assistant-stream` 帧的 `chunk.chunk` 是 `StreamChunk` 联合（`{type:'text-delta',index,text}` / `{type:'reasoning-delta',index,text}` / `{type:'tool-call-delta',index,id,name?,argumentsDelta}` / `{type:'block-start'|'block-end'|'usage'|'finish'}`）。
3. 流式与持久化**会重复**：`assistant/message` 事件是权威结果，`assistant-stream` 是瞬时预览。桌面端 `ClientAssistantStream`（`lib/types/client/sessions/assistant-stream.js`）用 `pending` + `publishedSeqs` 去重，在 `end` 帧的 `outcome.kind==='committed'` 时发布对应 seq 的持久化条目。**M3 简化为**：流式增量只写进「当前活跃气泡」，一旦收到 `assistant/message` 事件就用持久化内容替换该气泡——不实现 revision/rebaseline 那套重连对齐（留 M4）。
4. `tool/call.arguments` 是 **JSON 字符串**，要自己 parse。
5. `address` 用 `{kind:'session', sessionId}`；子代理会话必须用 `{kind:'subagent', parentSessionId, childSessionId, mode}`，用错报 `session/agent-busy` 或 `subagent/unauthorized`。

### M3.5 Markdown 渲染 + 工具卡片 + 改动文件卡片 + 文件查看页（2026-10-13 夜间）

- **探针先行的三组契约实测（T016）**：`range`/`options` 是**必需**参数、`offset` 是 **1-based** 且服务端硬拒 `offset:0`/`limit>5000` 并报 `gateway/bad-request`；`readBytes` 成功回 **multipart**（不是 JSON 信封）且**尾部还有 JSON 元数据**；`changes.diff` 的键名是 **`before`/`after`**（不是 `beforeExists`）；changes 失败回 `text/plain` 的 404，语义是「摘要随 Host 进程消失」而非「没改文件」。**这五条任何一条搞错，对应功能都不可用或给出错误结论。**
- **工具调用里怎么看改了哪个文件**：51 个会话全量统计 → 带路径的只有 `read`/`write`/`edit`，参数名统一 `file_path`，**且键序不固定**（两个 `write` 样本一个 `file_path` 在前、一个 `content` 在前）→ 必须 JSON 解析，正则捞会把内容里的同名字符串也算进去。

## 已核实的接口契约（速查，详见需求文档 §3）

**传输**：Typert RPC，不是 REST。
- unary：`POST /remote/api/<namespace>/<method>`，头 `x-dsh-remote-device: <deviceId>`，体 `{type:"client-request", rpcId, method, payload}`，`payload = {args: {...}}`
- 流式：**一条** WebSocket `wss://<host>/remote/api/remote.mux?device=<deviceId>` 多路复用所有流
- 服务端信封：`{type:"server-response", rpcId, result:{ok:true, value}}` 或 `{ok:false, error:{code,message,details}}`

**配对**：
- `POST /api/pair/accept` `{token}` → `{ok:true, deviceId}`（走公网隧道也可，因为 public host 在 trusted 列表里）
- 二维码/链接只能在**桌面端**生成（`/api/pair/issue` 是 loopback-only）
- `GET /api/pair/status` → `{ok, paired, requirePairingForLan, publicUrl, lanAddresses, tunnel}`（免鉴权）

**参数 wire 名（真机确认，不是猜的）**：
- 多数方法：`{args: {request: {...}}}`
- **`session/list`：`{args: {_request: {...}}}`** ← 唯一带下划线前缀的
- `workspaceFiles/*`：`{args: {workspaceFileScopeId: <sessionId>, path, range|options}}`（第一个是 Typert lookup，传 sessionId）
- 流式端点无参数：`{args: {}}`
- 名字不对 → `gateway/arguments-invalid: args fields do not match the descriptor: missing "x"; unexpected "y"`

**时间字段**：线上是 ISO-8601 字符串（`"2026-10-12T21:25:11.055Z"`），类型声明写的是 `number`。两种都要能解析。

**App 实际会用到的 namespace**：`workspace`、`session`、`workspaceFiles`、`directoryPicker`、`skills`、`fileReferences`

**改动文件卡片**（非 Typert，是普通 HTTP 路由）：
- `GET /remote/api/changes.summary?sessionId=&seq=`
- `GET /remote/api/changes.diff?sessionId=&seq=&index=`

### R024 · 提问通道即时化（user-questions waterfall）

**来源**：R024 审查指出「提问只靠 2.5s 轮询投影」会让模型刚发问时卡片慢几秒；
用户 m29539 同时要求「支持连续回答问题」。本轮把 `$events` 转发流里的
`user-questions/request` waterfall 帧从「只发信号」升级为「真正接住请求」。

#### ① 数据层

**`core/events/RemoteEvents.kt`**（新增提问模型，放在本文件而非 `core/session`——
waterfall 帧的解析只属于这条通道）：

- `data class QuestionRequest(eventId, agentId, questions: List<AskQuestion>, state)`
  + `belongsTo(sessionId)` / `isOpen` / `firstUnanswered()` / `parse(element)`；
- `enum class QuestionOutcome` 两值：`ANSWERED("answer")` / `SKIPPED("skip")`；
- `RemoteEventsStats` 新增 `questionsSeen` 与 `answeredQuestions`，
  `approvalsSeen` / `answeredApprovals` 语义不变（KDoc 说明「提问的回答不走 `$events`，
  这两个计数只是诊断页的展示口径」）。

**`core/session/SessionQuestions.kt`**：`AskQuestion` 增加 `parse(element)`，
内部转 `SessionProjectionParser.questionPublic`——waterfall 帧里的 `questions`
与投影里的 `active[].questions` 是同一套 wire 形状，**解析规则只能有一份**。

#### ② RemoteEventsClient

- `handle()` 的 waterfall 分支：`event == "user-questions/request"` 时
  `QuestionRequest.parse` → 成功则 `submit(QuestionOutcome.ANSWERED)`、
  失败则 `submit(QuestionOutcome.SKIPPED)`；`eventId` 为空或解析不出 `agentId`
  一律 SKIPPED。**type 是 `Waterfall` 但 outcome 不是 `ApprovalOutcome`**——
  二者不可混用，混用会让 `$events/result` 回 `gateway/bad-request`。
- `submit(outcome)`：`@Synchronized`，`when` 两个分支把 `eventId` 分别记进
  `handledApprovals` / `answeredQuestions`，再统一走 `answer(eventId, outcome)`。
  先记账后发送——崩溃窗口从「已答未记」缩小成「记了没答」，而后者只是卡片不消失，
  用户可以自己点，不会点出第二次回答。
- 新增 `answeredQuestions`（`ArrayDeque` + `HashSet` 双索引 + 环形上限 64），
  `close()` 与 `ready`（新 clientId）时清空。**必须与审批共用同一个 ring 大小**，
  否则两条路径的清理时机不一致。
- `questionOutcomes` Map（`eventId → QuestionOutcome`）只作「同一条 waterfall
  重复投递时把 SKIPPED 改成 ANSWERED」的兜底，`submit` 已成功就直接返回、不进这里。

#### ③ ChatViewModel

- `questionsOf(request)`：**先转成草稿形式立即弹窗**（用户零延迟看到卡片），
  再去投影快照里按 `callId` 找 `QuestionSet`；找不到就返回 null——宁可没有，
  也不要拿半截信息做一张看起来完整、实际字段是猜的卡片。
- 投影里已有同一 `callId` 的活动提问时**不重复添加**（按 `token` 去重）。

#### ④ 诊断页计数器拆分

原实现审批与提问共用 `submit()` 里的 `answers` 计数器 → 答过一次提问会被显示成
「已回答 1 条审批」，误导排查。定稿：`answeredApprovals` 与 `answeredQuestions`
分开计数，诊断页两行各自显示「见过 / 收到」与「已回答」。

设备实测（提问两次、审批零次）：
```
审批请求  见过 0 条 · 已回答 0 条
提问请求  收到 2 次 · 已回答 2 次

### R026 · 提问交互三个 P1 修复 + 单选语义修正

R025 两份独立审查（协议层 `b7bd8d58` / UI 层 `772eb9ea`）报出的 P1 全部修复，
另外自己抓到一个**由我自己的测试方法造成的真缺陷**。

#### ① 修复 A：合成键匹配不到（点提交什么都没发生）

`core/events/RemoteEventsClient.kt` 的 `answerQuestions(callId, answers)` 原来只做
`it.callId == callId || it.eventId == callId`。waterfall 帧拿不到 callId 时
`ChatViewModel` 用 `waterfall:<eventId>` 当卡片身份，带前缀的键两者都不等 →
`?: return` 空返 → `answerQuestionGroup` 走成功分支：无 outcome 送出、无错误提示、

修法：匹配前剥 `waterfall:` 前缀；无命中时**报错**（写 `_questionError`）而不是静默走成功分支。

#### ② 修复 B：多题组只显示最后一道题

`ChatReducer.applyQuestions` 对组内每道题都 `enterQuestion` 铺 `defaultOf`（第一个选项预选）

`indexOfFirst { drafts[it.id]?.isAnswered != true }` 全部命中 → 回落到 `lastIndex`

「第一道还没草稿的题」为止，全部有草稿时停在最后一道。

#### ③ 修复 C：未答题被静默补空答案

`submitQuestionGroup` 首行加 `unansweredCount` 守卫，缺几题就报「还有 N 题没有回答」。

#### ④ 修复 D（自己抓到）：单选点已选项把预选清空

`ChatReducer.toggleOption` 的单选分支原来是 `if (label in current.selected) emptySet() else setOf(label)`。

「卡片提交了，selected 数组是空的——既没有 继续 也没有 停止 落进去。」

改成单选语义：点已选项幂等。想表达「都不对」有专门的自定义答案框。
配套改写 `用户主动清空的题不会被重铺默认值`：清空路径从「点已选项取消」
改为「自定义答案打进去又删掉」。

## R027 · 真机崩溃「点开对话自动退出」的定位与修复（用户 m39951）

**用户报告**：User said (m39951):「我在真机上进行测试的时候出现了问题，点开一个对话之后软件会自动退出，
这个问题很严重。请你立即排查并修复。真机已连接adb，并且进行了配对了」。

**崩溃栈**（`adb -s 3B658N00HXC00000 logcat -d`）：`FATAL EXCEPTION: main` /
`Process: com.revxzxcx.remotewebapp` / `java.io.EOFException` /
`at okio.RealBufferedSource.require(RealBufferedSource.kt:225)` /
`at okhttp3.internal.ws.WebSocketReader.readHeader(WebSocketReader.kt:128)` /
`at okhttp3.internal.ws.RealWebSocket.loopReader(RealWebSocket.kt:317)` /
`Suppressed: kotlinx.coroutines.internal.DiagnosticCoroutineContextException: [StandaloneCoroutine{Cancelling}@6da7675, Dispatchers.Main.immediate]`。
**时间线：点开会话后 25 秒**。

### 根因

审计 14 个 `viewModelScope.launch` 后定案：`ChatViewModel` 的 `controlJob`
（`watchQuestions()` 里 `projections.control().collect{…}`）是**唯一没有 `.catch` 的 mux 流收集点**。

路径：桌面端进程退出 → TCP 断且**没有关闭帧** → OkHttp 读循环抛 `java.io.EOFException` →
`loopReader` 自己 catch 后走 `failWebSocket` → `MuxListener.onFailure` →
`RemoteStreamMux.failCarrier` 用**同一个 cause** 关掉所有流的 Channel
（`channels.forEach { it.close(cause) }`）→ `callbackFlow` 把它当**流的终止原因**抛给收集方 →
`viewModelScope` 是 `Dispatchers.Main.immediate` → 异常逃出协程 → `FATAL EXCEPTION: main`，
与栈里的 `Suppressed` 逐字吻合。

**真正杀死进程的是**：`failCarrier` → `live.deferred.completeExceptionally(EOFException)` →
`waitForSocket()` 抛出 → `callbackFlow` 终止 → 收集方在 Main 上重抛。
**不是**异常从 OkHttp 回调线程逃逸——`loopReader` 自己接住了它。

其余 13 处审计安全：`sendJob`/`queueJob`/`answerJob`/`attachJob`/`cancel`/`catalogJob`/
`modelJob`/`pageJob`/`changesJob` 都带 try/catch；`questionSignal`/`generating` 只收集本地 StateFlow；
`streamJob` 的 `follow()` 链上有 `.catch` + `.retryWhen`。

### 修复

| 文件 | 改动 |
|---|---|
| `ui/chat/ChatViewModel.kt` | `controlJob` 补 `.retryWhen { … }` **再** `.catch { if (cause is CancellationException) throw cause }`。**顺序必须在 retryWhen 之后**——反序会让 catch 先吞异常、retryWhen 永看不到失败。unpaired 时 `retryWhen` 返回 false（终态，交给 `Unpaired` 载体状态条 + 「重新配对」入口），其余按 `backoffMillis(attempt)` 退避并 `noteRetry`。**control 流原来没有任何自愈路径**——`watchQuestions()` 只在 `init` 调一次，`start()` 重连的是 `session/follow` 自己那条流 |
| `core/protocol/RemoteStreamMux.kt` | ① `open()` 与 `MuxListener` 的 KDoc 写清「**调用方必须给收集链加 `.catch`，这是硬性契约**」；② `MuxListener` 五个回调包 `runCatching { … }.onFailure { noteCallbackCrash(it) }`（**纵深防御，不是本次崩溃的修复点**）；③ 非法帧路径**先 `close(4002)` 再 `failCarrier(cancelSocket = false)`**；④ `onOpen` 的 `runCatching` 异常时补 `completeExceptionally`；⑤ 新增 `noteCallbackCrash` 塞故障环；⑥ stale generation 守卫（`webSocket.close(1000, "stale generation")`） |
| `core/protocol/RemoteStreamMuxTest.kt` | 新增裸 `ServerSocket` 复现用例（手工 WS 握手 → 读一帧 → `client.close()` 不发关闭帧）+ 断言收紧 |
| `ui/chat/ChatViewModelStreamFailureTest.kt`（新） | 两条用例钉住「异常不逃出 ChatViewModel 的收集协程」，`runBlocking` + 真实时间 + 线程 `UncaughtExceptionHandler` |

**`failCarrier` 的 `cancelSocket` 形参由来（自伤记录）**：无条件加 `live.socket?.cancel()` 后
2 条既有测试失败。根因是 `WebSocket.close(4002, …)` 是**优雅关闭**（排入关闭帧、等对端回），
紧接着 `cancel()` 会立刻拆掉 TCP，**4002 帧根本发不出去**。

### 🔴 本轮最重要的教训：判据用了错的输入

第 ② 条首版实现写的是：

```kotlin
val reasoningOnly = item.blocks.isNotEmpty() &&
    item.blocks.all { it is ContentBlock.Reasoning } &&
    !item.interrupted
```

这条判据**看起来**完全正确——「只含思考的助手消息走行式」。单元测试也全绿：
测试里构造的 `ChatItem.Assistant` 就是 `blocks = listOf(Reasoning(...))`。

**但真机上一张卡都没变。** 拿真实会话日志统计块形状才看清：

| `assistant/message` 的 blocks 形状 | 条数（`f3c843ab`，共 12221） |
|---|---|
| `[reasoning, tool-call]` | **5738** |
| `[tool-call]` | 5130 |
| `[reasoning, text, tool-call]` | 809 |
| `[text, tool-call]` | 374 |
| `[reasoning, tool-call, tool-call]` | 66 |
| `[reasoning, text]` | 31 |
| `[reasoning]` | **5** |

「只想不做」的 5 条，占比 0.04%。模型的常态是「先想、再调工具」，这类消息带了
`tool-call` 块，`all { it is Reasoning }` 恒假 → 永远走卡片分支。

正确的判据必须与**折叠判据同源**：`hasReply()` 用的是
`visibleAssistantBlocks(blocks, interrupted)`（该函数会滤掉 `tool-call`），所以在
「消息是否进分组」和「进组后怎么画」两处必须用同一个过滤后的列表，否则两个判据会分叉。

**测试为什么没抓到**：测试数据按「我以为的数据形状」构造，而不是按真实日志的形状。
→ 已定 D81：**折叠相关的渲染测试，样本形状必须取自真实会话日志的统计**。

**变异验证**：把判据改回 `item.blocks` → `先思考再调工具的成员里思考也是行式` 立刻变红；
还原 → 绿。证明这条测试确实钉住了根因，不是空转。
