## B001 · 设备栏展开卡片是直角，与全局圆角风格割裂

**登记时间**：2026-10-29 22:32
**状态**：待修
**发现环境**：手机 PKG110 / Android 16 (sdk 36) / App 0.2.0 (versionCode 2) / `6641e83`
**严重度**：轻微（纯外观，不影响功能）

### 用户原话

> 切换远程的展开卡片不是圆角的，这一点和实际的设计风格有割裂感，属于外观缺陷

### 现状代码

`app/src/main/java/com/revxzxcx/remotewebapp/ui/home/HomeDeviceBar.kt:116-122`

```kotlin
Surface(
    modifier = Modifier.fillMaxWidth(),
    shape = RoundedCornerShape(0.dp),   // ← 就是这里
    color = MaterialTheme.colorScheme.surface,
    border = BorderStroke(1.dp, MaterialTheme.colorScheme.outlineVariant),
    shadowElevation = 0.dp,
)
```

### 对比证据

全 App 其它容器都不是直角：

| 位置 | 圆角 |
| --- | --- |
| `ui/home/HomeScreen.kt:930` 会话行 `rowShape` | `RoundedCornerShape(16.dp)` |
| `ui/home/HomeScreen.kt:1316` 抽屉面板 `DrawerPanelShape` | `topEnd=20.dp, bottomEnd=20.dp` |
| `ui/home/HomeScreen.kt:1319` 抽屉行 `DrawerRowShape` | `RoundedCornerShape(10.dp)` |
| `ui/home/SessionActionsMenu.kt:50` `MenuShape` | `RoundedCornerShape(14.dp)` |
| 原型 `docs/R054-多主机效果图.html:14` | `--r-xs:6px --r-sm:10px --r-md:14px --r-lg:20px --r-xl:28px` |

设备栏内部元素其实都是圆角的：`.dev{border-radius:var(--r-md)}`（行）、`.db-add{border-radius:var(--r-md)}`（添加按钮）、`.db-head .c{border-radius:var(--r-pill)}`（计数胶囊）。只有最外层容器是直角。

### 需要裁决的点（修复前必须先问用户）

原型 `docs/R054-多主机效果图.html:86-88` 里 `.devbar` 本身就是**整宽通条、无圆角**的顶栏下拉：

```css
.devbar{background:var(--surface);border-bottom:1px solid var(--outline);
  box-shadow:0 14px 34px rgba(0,0,0,.5);position:relative;z-index:3}
```

也就是说当前实现是**照原型做的**，但用户看到实机后认为割裂。所以这不是「实现偏离原型」，而是「原型本身要改」。修复前需要用户确认走哪条：

| 方案 | 做法 | 代价 |
| --- | --- | --- |
| A · 浮动圆角卡片 | 卡片脱离顶栏，左右各留 8-10dp 边距，`RoundedCornerShape(14.dp 或 16.dp)`，四角全圆 | 视觉上更像「飘出来的面板」，但会失去「顶栏下拉到底」的连体感；展开动画要从顶栏宽度过渡，否则会跳一下 |
| B · 只圆下方两角 | `RoundedCornerShape(bottomStart=16.dp, bottomEnd=16.dp)`，上方两角仍贴着顶栏 | 保留连体感，改动最小，与「下拉」语义一致 |
| C · 保持通条，只加内层留白 | 不改 shape，改内部 padding/描边 | 大概率仍被判「割裂」，不推荐 |

**建议 B**：它同时满足「和全局圆角风格一致」与「它确实是顶栏的下拉延伸」两个约束，而且不需要重做展开动画。

## B002 · 扫码配对失败一次后扫码框不再识别二维码

**登记时间**：2026-10-29 22:32
**状态**：**待修（验收不通过）** —— 2026-10-30 用户实测「B002 修复没有完成，验收不通过」。
代码已按六轮审查收敛并合入（`723d9ab`），但真机流程未被用户确认有效，
需要用户配合做「扫码 → 配对失败 → 再扫一次」的实操才能定论。
**发现环境**：手机 PKG110 / Android 16 (sdk 36) / App 0.2.0 (versionCode 2) / `6641e83`
**严重度**：严重（功能不可用，且用户不知道要退出重进）

### 用户原话

> 当使用扫码配对功能时，扫码配对失败后（显示红色提醒报错）扫码功能将不再可用，也就是扫码框将不识别二维码，这种情况只有退出界面重进才能解决。

### 相关代码

全部在 `app/src/main/java/com/revxzxcx/remotewebapp/ui/pair/PairScreen.kt`。

**消费闩（关键）**：

```kotlin
var consumed by remember { mutableStateOf(false) }              // :567
LaunchedEffect(scanEpoch) { consumed = false }                  // :569
val callback = remember {                                       // :570
    object : BarcodeCallback {
        override fun barcodeResult(result: BarcodeResult?) {
            val text = result?.text
            if (consumed || !latestEnabled || text.isNullOrBlank()) return
            consumed = true                                      // :575
            latestOnScanned(text)
        }
    }
}
```

**控件重建**：`key(scanEpoch) { AndroidView(...) }`（:666-681），`factory` 里 `BarcodeView(ctx).also { it.decodeSingle(callback); scanner = it }`。

**唯一的复位入口**（:705-711）：

```kotlin
if (consumed && enabled) {
    TextButton(onClick = onRescan) { Text("重新扫描") }
}
```

**调用点**（:281-286）：

```kotlin
PairEntry.Scan -> ScanCard(
    enabled = !state.busy,
    scanEpoch = scanEpoch,
    onRescan = { scanEpoch++ },
    onScanned = viewModel::pairWithText,
)
```

`scanEpoch` 声明在 `:153`：`var scanEpoch by rememberSaveable { mutableIntStateOf(0) }`。

**失败路径**（`ui/pair/PairViewModel.kt:112-134`）：

```kotlin
fun pairWithText(rawText: String) {
    if (_state.value.busy) return
    ...
    _state.value = _state.value.copy(busy = true, error = null, probe = null)
    viewModelScope.launch {
        try { ... onSuccess(credential) }
        catch (e: PairingException) {
            _state.value = _state.value.copy(busy = false, error = e.message ?: "配对失败")
        }
        ...
    }
}
```

### 推测的根因方向（待修复时用 logcat 证实）

1. `BarcodeView.decodeSingle()` 是**一次性**的：底层解码线程回调一次后就不再回调。`consumed = true` 之后，即使底层还能解到码，`barcodeResult` 也会在 `:574` 直接 return。
2. 复位只有两条路：`scanEpoch` 递增（只能靠点「重新扫描」按钮），或整个组合重建（退出重进）。
3. 失败后 `busy` 回到 `false` → `enabled = true`，且 `consumed = true`，所以「重新扫描」按钮**理应**出现（:708）。但用户说「扫码框将不识别二维码」，说明用户**没看到**或**没意识到**要点它 —— 这本身就是设计缺陷：一个必须手动点的复位按钮，藏在取景框下方，用户不知道扫码已经死了。
4. 另一种可能：`key(scanEpoch)` 只重建 `AndroidView`，但 `scanner` 这个 `remember` 的引用在旧视图 `onRelease` 时被置 null 的时序，可能与新视图 `factory` 的执行顺序冲突（`onRelease` 晚于新 `factory` 就会把新 scanner 置 null）。**若是这个原因，点「重新扫描」也没用**，与用户「只有退出界面重进才能解决」的描述更吻合。这条优先级更高，需先验证。

### 预期

扫码失败后，扫码框应当自动恢复识别能力（自动重建控件、自动复位闩），用户不需要手动点任何东西就能重扫。

### 实际

失败一次后扫码框不再识别二维码，必须退出配对页重进。

### 备注

- 这条是**功能缺陷 + 交互缺陷**双重问题：即使「重新扫描」按钮存在，让用户手动复活扫码也不合理。
- 修复时要一并补测试：失败 → 自动复位 → 能再扫第二次。

### 修复记录（2026-11-03）

**根因**：zxing-android-embedded 4.3.0 的字节码证明——`decodeSingle()` 送达一次结果后
`handleMessage` 会顺手 `stopDecoding()`，把 `callback` 置空、`decodeMode` 归 `NONE`。
旧实现靠 `key(scanEpoch)` **重建控件**来复位，而 `startDecoderThread()` 在
`!isPreviewActive()` 时直接 return 且无人重试；重建时新旧控件抢同一个摄像头，
新控件大概率打空——于是扫码框永久失效。

**修法**：不拆控件，只重新武装。新增 `ui/pair/ScanChannel.kt` 状态机，
`ScanRearmer.rearmScan()` 对**同一个** `BarcodeView` 再调 `decodeSingle(callback)`；
删掉 `key(scanEpoch)` 包裹。

**六轮审查各揪出一个真缺陷**（详见 `代码审查记录.md`）：切标签吞码 / 欠账被吞 /
空结果静默死 / 分支顺序抢线程 / 欠账不销 / 权限重建闸门 / 后台开相机。

**验证**：全量 `classes=124 tests=1699 failures=0 errors=0 skipped=0`；lint 0 error；
变异验证 M1–M15 **全部 killed**；新增 3 个测试文件共 26 项。

**未做**：模拟器无摄像头画面源（MuMu 12 无 cam 注入键），改用 Robolectric 驱动真实
`BarcodeView` 走它自己的 `resultHandler`；手机端未装新包复验。

## B004 · 切换设备后首页工作区不刷新

**登记时间**：2026-10-30
**状态**：待修
**发现环境**：手机 PKG110 / Android 16 (sdk 36) / App 0.2.0 (versionCode 2) / `9301caf`
**严重度**：最严重（多主机功能形同虚设，用户必须杀进程重启）

### 用户原话

> 当用户配对多设备的时候，进行设备的切换，首页展示的工作区并不会及时更换，而是显示为之前的设备的工作区。只有退出应用重新进入才会刷新出切换后的工作区，这一点可能是因为当时开发的时候没有做实际多设备的测试而漏掉的。mumu模拟器中我配置了新的设备，你如果需要复现可以使用mumu模拟器进行。

### 根因（竞态：簿先发布，连接后安装）

三处代码共同造成：

1. `app/src/main/java/com/revxzxcx/remotewebapp/ui/AppRoot.kt:315-323` 用
   `key = "home-${activeHost.deviceId}"` 创建 `HomeViewModel`，
   而 `factory` 里的 `connection = connection` 取的是**当时的** `container.connection`。
2. `app/src/main/java/com/revxzxcx/remotewebapp/core/AppContainer.kt:229-239`
   `switchHost()` 先 `_book.value = next`（发布新簿），**之后**才 `installConnection(target)`。
3. `installConnection()` 内部第一步是 `withContext(Dispatchers.IO) { cacheLazy }`，
   这是个真正的挂起点。

于是时序变成：

```
_book.value = next             →  主线程下一帧重组，activeHost 已是新主机
installConnection():            →  VM key 变了，重建 HomeViewModel
    withContext(IO) {...}          ← 它捕获的 container.connection 还是旧的
    connection = DshConnection(新)  →  新连接装上，但 key 已经算完了
    _state.value = Paired          →  StateFlow 去重，`Paired` 是同一个值，不发射
```

`_state.value = Paired` 不会触发重组（`Paired` 没有载荷，StateFlow 对相等值不发射），
所以**没有任何后续事件再去重建那个 VM**。新 VM 攥着旧连接，旧连接的流在
`RemoteStreamMux.close()` 后以「正常完成」结束（不带 cause、不触发 `retryWhen`），
页面就停在旧主机的工作区列表上。重启应用时 `bootstrap()` 走完整流程，才拿到正确数据。

代码里其实已经警告过这个坑，见 `AppContainer.kt:340-343` 的 KDoc：
「`HomeViewModel` 在 Activity 的 ViewModelStore 里仍持有旧连接，旧流以「正常完成」结束、
不报错也不重试，页面就停在旧列表上。」

### 为什么单主机时代没暴露

单主机时 `installConnection` 只在配对完成那一刻跑一次，那时 `AppState` 从 `Unpaired`
变 `Paired`，突变本身就是一次重组信号；而 `switchHost` 路径下 `Paired → Paired` 是静默的。

## B005 · 重复添加同一台设备没有校验和提示

**登记时间**：2026-10-30
**状态**：待修
**发现环境**：手机 PKG110 / Android 16 (sdk 36) / App 0.2.0 (versionCode 2) / `9301caf`
**严重度**：严重（用户看到多行一模一样的主机，不知道哪一行是有效的）

### 用户原话

> 虽然说目前支持多设备配对，但是当用户重复添加一个设备的时候，没有做校验和提示，这是不合理的，重复配对应该被拒绝并提醒。

### 根因（去重按 deviceId，而每次配对都会换 deviceId）

`app/src/main/java/com/revxzxcx/remotewebapp/core/credentials/CredentialBook.kt:57-84`
`withUpsert()` 的判定是：

```kotlin
val sameEndpoint = hosts.firstOrNull {
    it.baseUrl == credential.baseUrl && it.deviceId == credential.deviceId
}
```

而桌面端 `POST /api/pair/issue` 每次签发的 token，`accept` 之后都会给一个**新的 deviceId**
（同一台桌面端可以同时登记多台设备，`/api/pair/status` 的 `deviceCount` 会累加）。
所以「同一台桌面端、同一个地址」的第二次配对，`baseUrl` 相同但 `deviceId` 不同，
`sameEndpoint` 命中不了 → 走 `else -> credential.copy(hostId = newHostId())` 新增一行。

用户视角里「一台设备」是按**地址**认的，代码里是按「地址 + deviceId」认的，两套口径不一致。

### 证据

- R054 真机验收时实测攒出 **11 行** `PGBM10 / 127.0.0.1:19387`（见 `开发进度.md` R054 节）。
- `AppContainer.addHost()`（`AppContainer.kt:213-218`）的 KDoc 也写着「若是同一台
  （baseUrl + deviceId 相同），会就地更新而不是新增一行」——它只覆盖了「同一个 deviceId 重复登记」。

## B006 · 设备行操作菜单弹在卡片底部而不是按钮下方

**登记时间**：2026-10-30
**状态**：待修
**发现环境**：手机 PKG110 / Android 16 (sdk 36) / App 0.2.0 (versionCode 2) / `9301caf`
**严重度**：一般（能用，但点哪一行都弹在同一个位置）

### 用户原话

> 多设备的下拉折叠卡片中，每一个设备的操作菜单按钮点击后显示的菜单位置不对，应该是在菜单按钮的下方显示，而不是每一个设备的菜单都显示在卡片下方（如图）。

### 根因（菜单没有锚在按钮上）

`app/src/main/java/com/revxzxcx/remotewebapp/ui/home/HomeDeviceBar.kt:164-221`

`DeviceRow(...)` 与紧随其后的 `DropdownMenu(...)` 是 `Column` 里的**两个兄弟节点**。
`DropdownMenu` 用的是 `Popup`，位置由它自己的父布局节点决定；作为 `Column` 的直接子节点，
它的父节点锚点落在整栏的布局流里，而不是那一行、更不是那个 `⋯` 按钮上。
`⋯` 按钮本身在 `DeviceRow` 内部（`:392-394` 的 `AppIconButtonSmall`），
`DropdownMenu` 根本看不到它，所以只能按 Column 的位置摆——表现为「都弹在卡片底部」。

对比：项目里 `AppButtons.kt` 的 `OverflowMenuAnchor` 是正确写法，
它把锚点与 `AppOverflowMenu` 放进同一个 `Box` 里，菜单因此贴着锚点。

### 根因（BorderStroke 是四面）

`app/src/main/java/com/revxzxcx/remotewebapp/ui/home/HomeDeviceBar.kt:131`

border = BorderStroke(1.dp, MaterialTheme.colorScheme.outlineVariant),

`AppContainer` 只发 `val link: StateFlow<ActiveLink>`，`AppRoot` 四处 VM key 改 `link.scopeToken`。

P2 先关旧连接再发布 → 改成先发布。变异 11/11 KILLED。

**验证**：classes=133 / tests=1783 全绿；lint 0 error / 15 warning；
模拟器双击双向切换即时生效。

**未做**：手机未复验。

### 修复记录（B005，2026-10-30）

②`PairingCoordinator` 末尾 `store.save()` 抢激活；③重复添加静默成功无提示。

### 修复记录（B006，2026-10-30）

**根因**：`DeviceRow(...)` 与 `DropdownMenu(...)` 是 `Column` 里的兄弟节点；`DropdownMenu` 用
`Popup`，锚点由自身父布局决定 → 落在整栏布局流上，点任何一行的 ⋯ 都从卡片底部弹出。

**验证**：模拟器点第一行 ⋯，菜单落在该行按钮正下方 ✅。变异 2/2 KILLED。

### 修复记录（B007，2026-10-30）

**根因**：`Surface(border = BorderStroke(1.dp, outlineVariant))` 画的是**整圈四边**；B001 只改了
`shape`（只圆下两角），上沿紧贴 `TopAppBar` 处仍留 1dp 亮线。

**三版迭代**：
1. `drawBehind` 自绘 → 被 `Surface` 自己的背景整片盖掉（modifier 在节点链最前端）；
2. `drawWithContent` + `Path` 纯函数 → **不可测**：`android.graphics.Path` 在纯 JVM 报

   `buildPath()` 只遍历命令。**教训：不要在 JVM/Robolectric 里断 `Path` 几何。**

**验证**：模拟器上顶栏与设备栏之间无分割线，同一块背景连续 ✅。13 项几何测试 + 7 变异 KILLED。
