## B001 · 设备栏展开卡片是直角，与全局圆角风格割裂

**登记时间**：2026-10-29 22:32
**状态**：待修
**发现环境**：手机 PKG110 / Android 16 (sdk 36) / App 0.2.0 (versionCode 2) / `6641e83`
**严重度**：轻微（纯外观，不影响功能）

### 用户原话

> 切换远程的展开卡片不是圆角的，这一点和实际的设计风格有割裂感，属于外观缺陷

### 现状代码

`app/src/main/java/com/revxzxcx/remotewebapp/ui/home/HomeDeviceBar.kt:116-122`

```kotlin
Surface(
    modifier = Modifier.fillMaxWidth(),
    shape = RoundedCornerShape(0.dp),   // ← 就是这里
    color = MaterialTheme.colorScheme.surface,
    border = BorderStroke(1.dp, MaterialTheme.colorScheme.outlineVariant),
    shadowElevation = 0.dp,
)
```

### 对比证据

全 App 其它容器都不是直角：

| 位置 | 圆角 |
| --- | --- |
| `ui/home/HomeScreen.kt:930` 会话行 `rowShape` | `RoundedCornerShape(16.dp)` |
| `ui/home/HomeScreen.kt:1316` 抽屉面板 `DrawerPanelShape` | `topEnd=20.dp, bottomEnd=20.dp` |
| `ui/home/HomeScreen.kt:1319` 抽屉行 `DrawerRowShape` | `RoundedCornerShape(10.dp)` |
| `ui/home/SessionActionsMenu.kt:50` `MenuShape` | `RoundedCornerShape(14.dp)` |
| 原型 `docs/R054-多主机效果图.html:14` | `--r-xs:6px --r-sm:10px --r-md:14px --r-lg:20px --r-xl:28px` |

设备栏内部元素其实都是圆角的：`.dev{border-radius:var(--r-md)}`（行）、`.db-add{border-radius:var(--r-md)}`（添加按钮）、`.db-head .c{border-radius:var(--r-pill)}`（计数胶囊）。只有最外层容器是直角。

### 需要裁决的点（修复前必须先问用户）

原型 `docs/R054-多主机效果图.html:86-88` 里 `.devbar` 本身就是**整宽通条、无圆角**的顶栏下拉：

```css
.devbar{background:var(--surface);border-bottom:1px solid var(--outline);
  box-shadow:0 14px 34px rgba(0,0,0,.5);position:relative;z-index:3}
```

也就是说当前实现是**照原型做的**，但用户看到实机后认为割裂。所以这不是「实现偏离原型」，而是「原型本身要改」。修复前需要用户确认走哪条：

| 方案 | 做法 | 代价 |
| --- | --- | --- |
| A · 浮动圆角卡片 | 卡片脱离顶栏，左右各留 8-10dp 边距，`RoundedCornerShape(14.dp 或 16.dp)`，四角全圆 | 视觉上更像「飘出来的面板」，但会失去「顶栏下拉到底」的连体感；展开动画要从顶栏宽度过渡，否则会跳一下 |
| B · 只圆下方两角 | `RoundedCornerShape(bottomStart=16.dp, bottomEnd=16.dp)`，上方两角仍贴着顶栏 | 保留连体感，改动最小，与「下拉」语义一致 |
| C · 保持通条，只加内层留白 | 不改 shape，改内部 padding/描边 | 大概率仍被判「割裂」，不推荐 |

**建议 B**：它同时满足「和全局圆角风格一致」与「它确实是顶栏的下拉延伸」两个约束，而且不需要重做展开动画。

## B002 · 扫码配对失败一次后扫码框不再识别二维码

**登记时间**：2026-10-29 22:32
**状态**：**待修（验收不通过）** —— 2026-10-30 用户实测「B002 修复没有完成，验收不通过」。
代码已按六轮审查收敛并合入（`723d9ab`），但真机流程未被用户确认有效，
需要用户配合做「扫码 → 配对失败 → 再扫一次」的实操才能定论。
**发现环境**：手机 PKG110 / Android 16 (sdk 36) / App 0.2.0 (versionCode 2) / `6641e83`
**严重度**：严重（功能不可用，且用户不知道要退出重进）

### 用户原话

> 当使用扫码配对功能时，扫码配对失败后（显示红色提醒报错）扫码功能将不再可用，也就是扫码框将不识别二维码，这种情况只有退出界面重进才能解决。

### 相关代码

全部在 `app/src/main/java/com/revxzxcx/remotewebapp/ui/pair/PairScreen.kt`。

**消费闩（关键）**：

```kotlin
var consumed by remember { mutableStateOf(false) }              // :567
LaunchedEffect(scanEpoch) { consumed = false }                  // :569
val callback = remember {                                       // :570
    object : BarcodeCallback {
        override fun barcodeResult(result: BarcodeResult?) {
            val text = result?.text
            if (consumed || !latestEnabled || text.isNullOrBlank()) return
            consumed = true                                      // :575
            latestOnScanned(text)
        }
    }
}
```

**控件重建**：`key(scanEpoch) { AndroidView(...) }`（:666-681），`factory` 里 `BarcodeView(ctx).also { it.decodeSingle(callback); scanner = it }`。

**唯一的复位入口**（:705-711）：

```kotlin
if (consumed && enabled) {
    TextButton(onClick = onRescan) { Text("重新扫描") }
}
```

**调用点**（:281-286）：

```kotlin
PairEntry.Scan -> ScanCard(
    enabled = !state.busy,
    scanEpoch = scanEpoch,
    onRescan = { scanEpoch++ },
    onScanned = viewModel::pairWithText,
)
```

`scanEpoch` 声明在 `:153`：`var scanEpoch by rememberSaveable { mutableIntStateOf(0) }`。

**失败路径**（`ui/pair/PairViewModel.kt:112-134`）：

```kotlin
fun pairWithText(rawText: String) {
    if (_state.value.busy) return
    ...
    _state.value = _state.value.copy(busy = true, error = null, probe = null)
    viewModelScope.launch {
        try { ... onSuccess(credential) }
        catch (e: PairingException) {
            _state.value = _state.value.copy(busy = false, error = e.message ?: "配对失败")
        }
        ...
    }
}
```

### 推测的根因方向（待修复时用 logcat 证实）

1. `BarcodeView.decodeSingle()` 是**一次性**的：底层解码线程回调一次后就不再回调。`consumed = true` 之后，即使底层还能解到码，`barcodeResult` 也会在 `:574` 直接 return。
2. 复位只有两条路：`scanEpoch` 递增（只能靠点「重新扫描」按钮），或整个组合重建（退出重进）。
3. 失败后 `busy` 回到 `false` → `enabled = true`，且 `consumed = true`，所以「重新扫描」按钮**理应**出现（:708）。但用户说「扫码框将不识别二维码」，说明用户**没看到**或**没意识到**要点它 —— 这本身就是设计缺陷：一个必须手动点的复位按钮，藏在取景框下方，用户不知道扫码已经死了。
4. 另一种可能：`key(scanEpoch)` 只重建 `AndroidView`，但 `scanner` 这个 `remember` 的引用在旧视图 `onRelease` 时被置 null 的时序，可能与新视图 `factory` 的执行顺序冲突（`onRelease` 晚于新 `factory` 就会把新 scanner 置 null）。**若是这个原因，点「重新扫描」也没用**，与用户「只有退出界面重进才能解决」的描述更吻合。这条优先级更高，需先验证。

### 预期

扫码失败后，扫码框应当自动恢复识别能力（自动重建控件、自动复位闩），用户不需要手动点任何东西就能重扫。

### 实际

失败一次后扫码框不再识别二维码，必须退出配对页重进。

### 备注

- 这条是**功能缺陷 + 交互缺陷**双重问题：即使「重新扫描」按钮存在，让用户手动复活扫码也不合理。
- 修复时要一并补测试：失败 → 自动复位 → 能再扫第二次。

### 修复记录（2026-11-03）

**根因**：zxing-android-embedded 4.3.0 的字节码证明——`decodeSingle()` 送达一次结果后
`handleMessage` 会顺手 `stopDecoding()`，把 `callback` 置空、`decodeMode` 归 `NONE`。
旧实现靠 `key(scanEpoch)` **重建控件**来复位，而 `startDecoderThread()` 在
`!isPreviewActive()` 时直接 return 且无人重试；重建时新旧控件抢同一个摄像头，
新控件大概率打空——于是扫码框永久失效。

**修法**：不拆控件，只重新武装。新增 `ui/pair/ScanChannel.kt` 状态机，
`ScanRearmer.rearmScan()` 对**同一个** `BarcodeView` 再调 `decodeSingle(callback)`；
删掉 `key(scanEpoch)` 包裹。

**六轮审查各揪出一个真缺陷**（详见 `代码审查记录.md`）：切标签吞码 / 欠账被吞 /
空结果静默死 / 分支顺序抢线程 / 欠账不销 / 权限重建闸门 / 后台开相机。

**验证**：全量 `classes=124 tests=1699 failures=0 errors=0 skipped=0`；lint 0 error；
变异验证 M1–M15 **全部 killed**；新增 3 个测试文件共 26 项。

**未做**：模拟器无摄像头画面源（MuMu 12 无 cam 注入键），改用 Robolectric 驱动真实
`BarcodeView` 走它自己的 `resultHandler`；手机端未装新包复验。

## B004 · 切换设备后首页工作区不刷新

**登记时间**：2026-10-30
**状态**：待修
**发现环境**：手机 PKG110 / Android 16 (sdk 36) / App 0.2.0 (versionCode 2) / `9301caf`
**严重度**：最严重（多主机功能形同虚设，用户必须杀进程重启）

### 用户原话

> 当用户配对多设备的时候，进行设备的切换，首页展示的工作区并不会及时更换，而是显示为之前的设备的工作区。只有退出应用重新进入才会刷新出切换后的工作区，这一点可能是因为当时开发的时候没有做实际多设备的测试而漏掉的。mumu模拟器中我配置了新的设备，你如果需要复现可以使用mumu模拟器进行。

### 根因（竞态：簿先发布，连接后安装）

三处代码共同造成：

1. `app/src/main/java/com/revxzxcx/remotewebapp/ui/AppRoot.kt:315-323` 用
   `key = "home-${activeHost.deviceId}"` 创建 `HomeViewModel`，
   而 `factory` 里的 `connection = connection` 取的是**当时的** `container.connection`。
2. `app/src/main/java/com/revxzxcx/remotewebapp/core/AppContainer.kt:229-239`
   `switchHost()` 先 `_book.value = next`（发布新簿），**之后**才 `installConnection(target)`。
3. `installConnection()` 内部第一步是 `withContext(Dispatchers.IO) { cacheLazy }`，
   这是个真正的挂起点。

于是时序变成：

```
_book.value = next             →  主线程下一帧重组，activeHost 已是新主机
installConnection():            →  VM key 变了，重建 HomeViewModel
    withContext(IO) {...}          ← 它捕获的 container.connection 还是旧的
    connection = DshConnection(新)  →  新连接装上，但 key 已经算完了
    _state.value = Paired          →  StateFlow 去重，`Paired` 是同一个值，不发射
```

`_state.value = Paired` 不会触发重组（`Paired` 没有载荷，StateFlow 对相等值不发射），
所以**没有任何后续事件再去重建那个 VM**。新 VM 攥着旧连接，旧连接的流在
`RemoteStreamMux.close()` 后以「正常完成」结束（不带 cause、不触发 `retryWhen`），
页面就停在旧主机的工作区列表上。重启应用时 `bootstrap()` 走完整流程，才拿到正确数据。

代码里其实已经警告过这个坑，见 `AppContainer.kt:340-343` 的 KDoc：
「`HomeViewModel` 在 Activity 的 ViewModelStore 里仍持有旧连接，旧流以「正常完成」结束、
不报错也不重试，页面就停在旧列表上。」

### 为什么单主机时代没暴露

单主机时 `installConnection` 只在配对完成那一刻跑一次，那时 `AppState` 从 `Unpaired`
变 `Paired`，突变本身就是一次重组信号；而 `switchHost` 路径下 `Paired → Paired` 是静默的。

## B008 · 切换主机时崩溃（NoSuchElementException）

**登记时间**：2026-11-02 22:20
**状态**：已修（2026-11-02）
**发现环境**：手机 PKG110 / Android 16 (sdk 36) / App 0.2.0 (versionCode 2) / `591b822`
**严重度**：严重（进程崩溃，发生在切主机这条常用路径上）
**发现方式**：给手机装最新包时顺手读 `adb logcat -b crash`，发现 21:28 那次崩溃
（旧包，但代码路径未变，新包同样会复现）

### 崩溃栈原文

```
FATAL EXCEPTION: DefaultDispatcher-worker-6
Process: com.revxzxcx.remotewebapp, PID: 22592
java.util.NoSuchElementException
	at java.util.concurrent.ConcurrentHashMap$ValueIterator.next(ConcurrentHashMap.java:3486)
	at kotlin.collections.CollectionsKt___CollectionsKt.toList(_Collections.kt:1329)
	at com.revxzxcx.remotewebapp.core.protocol.RemoteStreamMux.close(RemoteStreamMux.kt:217)
	at com.revxzxcx.remotewebapp.core.connection.DshConnection.close(DshConnection.kt:103)
	at com.revxzxcx.remotewebapp.core.AppContainer.installConnection(AppContainer.kt:360)
	at com.revxzxcx.remotewebapp.core.AppContainer.switchHost(AppContainer.kt:237)
	at com.revxzxcx.remotewebapp.ui.AppRootKt$AppRoot$2$12$5$1$1.invokeSuspend(AppRoot.kt:439)
```

### 根因

`RemoteStreamMux.kt:217`（`close()`）与 `:693`（`failCarrier()`）都是同一段：

```kotlin
val channels = streams.values.toList()
streams.clear()
```

`streams` 是 `ConcurrentHashMap<String, Channel<MuxEvent>>`（`:88`）。Kotlin 的
`Iterable.toList()` 在接收者是 `Collection` 时按 `size` 走**快路径**：
`0 -> emptyList()`、`1 -> iterator().next()`、其余 `toMutableList()`。
`ConcurrentHashMap.values` 正是这种弱一致的 `Collection` 视图，于是：

1. 线程 A 读 `size == 1`，决定走 `iterator().next()`；
2. 线程 B（`failCarrier` 里同一段代码，断线时会并发进来）执行了 `streams.clear()`；
3. 线程 A 的迭代器已经空了 → `next()` 抛 `NoSuchElementException`。

**只在流数量恰好为 1 且发生并发清理时命中**，所以线上是偶发；一旦命中就是进程级崩溃，
且因为它在 `installConnection` 里，恰好落在「切主机」这条最常用的路径上。

### 修法

新增 `app/src/main/java/com/revxzxcx/remotewebapp/core/protocol/StreamRegistry.kt`：

```kotlin
internal fun <V> drainConcurrent(map: ConcurrentHashMap<String, V>): List<V> {
    val drained = ArrayList<V>(map.size)
    map.forEach { key, value ->
        if (map.remove(key) === value) drained += value
    }
    return drained
}
```

`RemoteStreamMux` 里两处调用点都改成 `drainStreams().forEach { ... }`
（`private fun drainStreams() = drainConcurrent(streams)`，`:221`）。

为什么不是简单地换成 `ConcurrentHashMap.forEach` 快照 + `clear()`：那样虽然不抛了，但
「快照完」到「`clear()`」之间新注册的流会被清掉却没被关闭，变成一个永远没人关闭、
收集方永远挂着的空 Channel。逐条 `remove` 保证：

- 只有 `remove(key)` 真的返回了同一个值才计入 → 同一条不会被摘两次、不会重复关闭；
- 两个线程同时摘同一批是安全的（各自只能摘到自己成功 `remove` 掉的那些）；
- 遍历期间新注册的条目留在表里等下一次摘取，不会出现「被清掉却没被关闭」的空洞。

### 验证

- 新增 `app/src/test/java/com/revxzxcx/remotewebapp/core/protocol/StreamRegistryTest.kt`
  5 项，用**真实并发**（`Thread` + `CountDownLatch`）压「表里只有 1 条、两个线程同时摘」
  3000 轮。
- 变异 3/3 KILLED，其中 M1 把实现退回 `values.toList() + clear()` → 精确红在
  `并发摘取同一条不会抛异常也不会重复摘到`，**复现了线上那条崩溃**。
- 全量 `classes=134 tests=1787 failures=0 errors=0 skipped=0`；lint 0 error / 15 warning；
  APK 16,420,167 B。

### 未做的验证

真机上没有再跑一轮「反复切主机」的压测（该崩溃本来就是偶发，几百次里才撞一次，
靠真机复现不可靠）；改由并发单测钉住。

**登记时间**：2026-11-07 23:40
**状态**：待修
**发现方式**：用户实测（本轮口头反馈，先记录，后续修复）
**严重度**：中（功能没坏，但把「点了没反应」变成了「弹一条英文错误」，体验倒退）

### 用户原话

> 现在我发现了一个bug，排队消息在发出的时候没有做锁，发送排队消息后，重复点击插队会报错，
> 虽然说有报错，但是用户交互逻辑并不好，应该改为提醒而不是报错。这一点你先记录到待办，
> 后续再进行修复

### 复现路径（待用户确认细节时补充）

1. 会话正在生成（`generating == true`），发一条消息 → 它进排队区；
2. 点这条排队消息上的「插队」图标；
3. **再点一次**（或在第一次还在飞的时候连点）→ 出现一条错误横幅。

### 已定位的代码现状

**UI 层**（`ui/chat/ChatScreen.kt:3522`）：插队按钮的 `enabled = generating`，只看
「是否正在生成」，**不看这一条是否已经有插队在飞**。所以第一次点击之后按钮仍然可点。

**执行体**（`ui/chat/ChatViewModel.kt:1088` `queueAction`）：

```kotlin
private fun queueAction(message: QueuedMessage, action: ChatArgs.QueueAction, pending: String?) {
    if (!message.confirmed) return
    queueJob?.cancel()                    // ← 取消在飞的那一个，而不是忽略新点击
    queueJob = viewModelScope.launch {
        _state.value = _state.value.copy(sending = true)
        try {
            repository.updateQueue(sessionId, message.id, action)
            _state.value = _state.value.copy(sendError = null)
        } catch (cause: Exception) {
            _state.value = _state.value.copy(sendError = describe(cause))
        } finally {
            _state.value = _state.value.copy(sending = false)
        }
    }
}
```

两个问题叠在一起：

1. **`queueJob?.cancel()` 取消的是「正在飞的请求」，不是「这次点击」**。
   第一次插队的 RPC 可能已经到达服务端（服务端把条目置为 `next-step`），
   但协程被取消后不会上报结果，界面也没有任何反馈。
2. **第二次请求撞上服务端状态机**。服务端要求条目仍在 `next-turn` 且会话正在运行，
   否则抛 `session/steer-unavailable`（`core/session/ChatArgs.kt:183` 记着
   `index.js:966`）。第一次已经把条目推进到 `next-step`，第二次必然被拒。

**错误呈现**（`ui/chat/ChatViewModel.kt:2293` `describe` + `ChatScreen.kt:615`）：

```kotlin
private fun describe(cause: Throwable): String {
    val typert = cause as? TypertException
    return typert?.let { "${it.code}：${it.message}" }
        ?: (cause.message ?: cause.javaClass.simpleName)
}
```

`sendError` 被渲染成带「重试」按钮的 `ChatErrorBanner`。于是用户看到的是一条
**`session/steer-unavailable：...` 的英文错误码 + 重试按钮**，而那个「重试」绑的是
`retrySend()`（重发草稿），与插队毫无关系。

### 应该怎么改（方向，修复时再定稿）

1. **加锁，而不是 cancel**：`steerQueued` 走与 `goalMutex` 相同的串行闸
   （`ChatViewModel.kt:1136` 已有先例与一段 KDoc 说明为什么不能「cancel 再赋新值」），
   或者给每条消息记一个「插队请求在飞」的标记，在飞期间按钮置灰。
2. **拒绝时给提醒，不给报错**：`session/steer-unavailable` 不该走 `sendError`
   （那是「发送失败」的位置，配的是重发草稿的重试按钮）。应改成一次性的轻提示
   （snackbar / `attachNotice` 那种「一句话，自己消失」的通道），文案说人话，例如
   「这条已经插过队了」/「当前轮已经不接受插队」。
3. **落到列表状态而不只是横幅**：插队成功后条目本来就该从「等当前轮结束后发出」变成
   「已插队 · 在当前轮执行」——那段文案 `ChatScreen.kt:3512` 已经写好了，
   关键是要保证第一次点完之后界面真的切过去，用户就不会想再点第二次。

### 待补充

- 用户实际看到的错误原文（是 `session/steer-unavailable` 还是别的码）——修复前先确认，
  避免按推测改错分支。
- 重复点击是「连点两下」还是「隔几秒再点」：前者是没做防抖，后者是状态没同步，
  两种情况都要处理，但优先级不同。


## R056-B1 · 后台跑完任务收不到通知（「正看着」判定压掉了主场景）

### 现象

在会话里输入内容点发送，立刻按 Home 切到后台，`dumpsys notification --noredact` 轮询 60～72 秒
恒 **0 条**。频道正常（`ask` importance=4 / `done` importance=3），权限已授权，进程还活着。

### 根因

`core/notify/NoticeGate.kt` 原来的 `shouldPost`：
`if (visibility.foreground) return false` 与
`if (viewingSessionId == completedSessionId) return false` 是**两个各自独立**的阻断条件。
真实路径：会话 X 点发送 → 进聊天页（`viewingSessionId = X`）→ 按 Home（`foreground = false`，
但**按 Home 不会清 `viewingSessionId`**）→ 跑完 → 两个 id 相等 → 通知被压掉。

而「发完任务就切出去等结果」正是这个功能存在的**全部理由**。等于白做。

### 修法

改成三态 `NoticeDelivery { Skip, Silent, Alert }` 的 `decide()`：
权限/频道任一关 → `Skip`；审批 → `Alert`；前台 + 正看着 → `Skip`；前台 + 看别处 → `Silent`；
**后台 → `Alert`（不管视角）**。布尔版 `shouldPost` 已删（没有 Silent 档，误用即静默丢通知）。
原有两条把错误语义钉住的用例（`foreground = false` + 相同 id 断言「不发」）一并改正。

### 验收

修复前同场景恒 0 条，修复后 **t=5s 出现**：
`channel=done importance=3`、`android.title=任务结束 · hi`、`flags=ONLY_ALERT_ONCE|AUTO_CANCEL`。
点通知跳进对应会话，通知自动撤销。

## R056-B2 · 通知里的「批准」点了没反应

### 现象

审批通知弹出，两个按钮都在。点「批准」后**通知条消失，但 App 里审批卡还在**（「需要授权 / ops_bash /
允许一次 / 拒绝」），任务停在那里不动。

### 根因

`core/notify/NoticeActionReceiver.kt`：
`val app = context.applicationContext as? NoticeActionHost ?: run { ...cancel...; return }`
而 `DshApplication` 原文是 `class DshApplication : Application() {` —— **没 implements `NoticeActionHost`**。
`as?` 拿 null → 走兜底分支只 `cancel(noticeId)` 然后 return，
`answerFromNotification` 从头到尾没被调用。

`AppContainer.answerFromNotification` 的实现在 `core/AppContainer.kt:180` 是完好的，接口也定义好了，
**纯接线遗漏**。用户看到「通知消失了，但什么都没发生」——**比按钮不存在更糟**，因为任务其实还在等授权。

### 修法

`DshApplication` 加 `, NoticeActionHost` 与
`override fun answerFromNotification(eventId: String, allow: Boolean) { container.answerFromNotification(eventId, allow) }`，
KDoc 写明「这个 implements 不是可选的」。

### 为什么 1960 条单测全绿也拦不住

单测只测 `AppContainer.answerFromNotification`，**从不经过 `Application` 这一跳**。
新增 `core/notify/NoticeActionWiringTest`（5 项）专门测「装配对不对」而非「接收器逻辑对不对」，
第一条就是 `assertTrue(app is NoticeActionHost)`。变异验证：同时删掉却 `, NoticeActionHost`
与整个 `override` → KILLED。

### 验收

点「批准」后 `~/.gitconfig` 出现测试探针 `[r056] probe = 1`，
**文件 mtime = `2026-11-08 01:51:33`**，正是点击那一刻。App 拉到前台看到 Agent 已继续执行。
探针已清理，`grep -c r056` = 0。

## R056-B3 · 设置页摘要永远显示最乐观的那句

### 现象

`POST_NOTIFICATIONS` 实际是 `granted=false`（`dumpsys package` 确认），但设置页「通知与后台保活」
的摘要显示「任务跑完、需要你确认时提醒」（全通文案），而不是「还没授权，点这里开启」。

### 根因

`ui/AppRoot.kt` 的 `var noticeStatus by remember { mutableStateOf(NoticeStatus()) }` 默认全是 `true`
（为了避免首帧闪一下「通知不会响」），而刷新它的地方只有通知**二级页**的
`LaunchedEffect(openNoticeSettings)`。设置**主页**直接读初值 → 摘要永远「一切正常」。

**这恰恰是四层诊断最不该犯的错：用户看到「正常」就不会点进去，而诊断的全部意义就是让他点进去。**

### 修法

`openSettings -> {` 分支里加 `LaunchedEffect(openSettings) { if (openSettings) noticeStatus = container.noticeStatus() }`，
摘要处注释改为「⚠️ 必须读上面刷新过的值。它初值是「全通」，直接读初值会把未授权显示成一切正常。」

### 验收

重装 → 杀进程重启 → 进设置页，摘要变成「**还没授权，点这里开启**」。

### R056-B5 被杀提示冤枉用户「自己划掉的」（真机发现）

- **发现时间**：2026-11-08（真机验收 B4 修复时）
- **严重程度**：中（说错话，会摧毁用户对提示的信任）
- **现象**：第一版把 `REASON_USER_REQUESTED`（10）判成「用户从最近任务划掉的」，卡片写「上次是从最近任务里划掉的」。但真机上 **`adb shell am kill` 也会落在这条**，实际 subreason 是 24 (KILL BACKGROUND)。
- **实测数据**：

```
am kill      -> reason=10 (USER REQUESTED) subreason=24 (KILL BACKGROUND)
am force-stop -> reason=10 (USER REQUESTED) subreason=21 (FORCE STOP)
OEM 电池杀   -> reason=10 (USER REQUESTED) subreason=24 (KILL BACKGROUND)（与 am kill 相同）
```

- **根因**：`javap android.app.ApplicationExitInfo`（android-36）确认**公开 API 没有 `getSubReason()`**，只有 `getReason/getTimestamp/getDescription` 等。`REASON_USER_REQUESTED` 是「用户划掉 / 系统 killBackground / force stop」的混合体，**没有可靠手段分辨**。
- **修法**：`DeathCause.UserSwiped` → `DeathCause.Stopped`。标题「上次 App 是被停掉的」，正文把两种可能都摆出来，按钮「去开保活」。顺带把 `REASON_USER_STOPPED`（11）也归到同一族。
- **为什么不猜**：`getDescription()` 里有 `kill background` / `FORCE STOP` 字样，可做启发式，但那是非契约的、随 OEM 与版本变化、且可为 null。选择「承认分不出来」。
- **状态**：已修
