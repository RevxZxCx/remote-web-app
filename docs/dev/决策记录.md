## D11 · 改动文件卡片：推断 + 权威摘要，两条路都做（Q10）

**日期**：2026-10-13 · **状态**：已接受（用户 m00811「接受建议」）

**决策**：
- **路 A（实时推断）**：解析 `tool/call` 的 `name ∈ {write, edit, str_replace_editor}` 与 `arguments`（**是 JSON 字符串**）取出 `file_path`，渲染可点文件行。
- **路 B（权威摘要）**：出现 `workspace/changes` 事件时，用其 `seq` 调 `GET /remote/api/changes.summary?sessionId=&seq=` 拿 `+added/-deleted` 权威统计。

**理由**：摘要只活在**同一 Host 进程内的会话**生命周期里，Host 重启后旧轮次返回 404；只做路 B 会空白。反之只做路 A 会丢行数统计。

**限制（必须写进 UI 文案）**：
1. Host 重启后旧轮次没有卡片与 diff（404）→ 降级为路 A。
2. 非 git 仓库里，纯 shell 命令改的文件不会出现在卡片里（只统计文件工具改动）。

## D17 · 传输层不依赖 `/remote` 之外的前缀

**日期**：2026-10-13 · **状态**：已接受（自主决策）

**决策**：所有业务请求统一走 `/remote/api/<namespace>/<method>`，WebSocket 走 `/remote/api/remote.mux?device=<id>`。

**理由**：插件 `/remote` 通道是唯一的**无 cookie** 入口，且它把请求以进程自身凭证重新签发到 `127.0.0.1`。直接打 `/api` 会被 harness 的 Host 围栏 + 浏览器 cookie 拦成 401（已实测：`POST /api/session.list` → `401 unauthorized`）。

## D18 · 依赖版本按 AAR 的 `minCompileSdk` 实测选定，不取 latest

**日期**：2026-10-13 · **状态**：已接受（自主决策）

**决策**：`gradle/libs.versions.toml` 里的版本以**实测的兼容矩阵**为准，锁定在 compileSdk 36 / AGP 8.13.2 可用的上限，而不是 maven 上的 latest。

**采用值**：AGP 8.13.2 / Gradle 8.13 / Kotlin 2.2.21 / core-ktx 1.18.0 / lifecycle 2.10.0 / activity-compose 1.13.0 / compose-bom 2026.06.01（ui 1.11.4、material3 1.4.0）/ okhttp 5.4.0 / kotlinx-serialization-json 1.9.0 / coroutines 1.10.2。

## D21 · 不引入 Robolectric，Room 用假 DAO 做 JVM 单测

**日期**：2026-10-14 · **状态**：已接受（自主决策）

**决策**：M4 引入 Room 后，**不引入 Robolectric**，也不为单元测试开 `unitTests.isIncludeAndroidResources`。
Room 的测试策略改为：`CacheMappers` 是纯函数（直接测）；`DshCache` 的 DAO 依赖用**手写假 DAO**（一个实现 `CacheDao` 接口的普通 Kotlin 类，把行存在内存 `MutableList` 里）注入；真实的 SQLite 建库、DDL、事务、WAL 行为**靠模拟器手工验收**。

**理由**：
1. Robolectric 会在测试期拉 `android-all` 系列 jar，本工程的构建约定是 `--offline`（D19 把缓存放 F 盘，离线是常态）——一个测试依赖需要联网下载会破坏这条约定。
2. 需要 `unitTests.isIncludeAndroidResources = true` 与额外的 `testOptions`，会拖慢所有单测。
3. 真正需要验证的**业务语义**（整体替换而非累积、ownerId 隔离、`trimMessages` 裁剪、磁盘故障退化成 null、`CancellationException` 原样上抛）**全部落在 `DshCache` 这层编排逻辑上**，与 SQLite 本身无关；而 SQLite 的 DDL/事务正确性由 Room 编译器与模拟器验收覆盖。

**代价**：单测**不覆盖**真实 SQL 语句、外键与事务边界；`CacheDao` 的注解若有误，编译期能发现（KSP 会报错），但运行期的约束冲突只能在模拟器上暴露。
已用 `dsh-cache.db` + `-wal` 的实际落盘与诊断页读数（T021）作为代偿证据。

**记录**：`测试记录.md` T021；本决策与 D04（离线缓存：做）配套。

## D22 · 缓存库不落 deviceId 原文，用指纹作分区键

**日期**：2026-10-14 · **状态**：已接受（自主决策）

**决策**：本地缓存库（`dsh-cache.db`）的所有表主键都包含 `ownerId`，而 `ownerId = SHA-256(baseUrl + '\u0000' + deviceId)` 的前 8 字节十六进制。**不**把 `deviceId` 明文写进 SQLite。

**理由**：「已配对设备 = FULL-CONTROL 凭证」（`remote-api.ts:1-27` 的机制：插件用进程自身的浏览器鉴权 cookie 代发请求）。而 `dsh-cache.db` 是**明文 SQLite**，落在 App 私有目录但可被 root / 备份 / `run-as` 读出。凭证本身已经由 Keystore AES-GCM 加密保管（D16），缓存库不该成为第二个更容易读的泄露点。

**代价**：诊断页里 `ownerId` 显示为一串 16 位十六进制（`ea79c5642ad8aa2f`），排查问题时无法直接对上桌面的设备列表——**这是有意的**，需要对照时用「设备 id 打码」（`204a48…7ea2`）即可。重新配对会产生新的 `ownerId`，旧缓存行自然不匹配（换设备语义），另由 `pruneOtherOwners` 清理。

**记录**：`core/cache/CacheMappers.kt` 的 `ownerIdOf`；`测试记录.md` T021。

## D23 · 缓存只缓存「已确认」的事件，不缓存 assistant-stream 帧

**日期**：2026-10-14 · **状态**：已接受（自主决策）

**决策**：`ChatViewModel.persist(envelopes)` 只落库**事件信封**（`session/follow` 的 `event` 帧 / 快照里的 `records`），**瞬时 `assistant-stream` 帧不缓存**。

**理由**：`assistant-stream` 的 `chunk` 是**未提交**的增量猜测——官方的权威性只在 `end` 帧的 `outcome.kind == 'committed'` 时才成立（未提交即 `abandoned`）。若把半成品落库，下次冷启动会把一段从未被服务端确认过的文本当成历史渲染出来，而重连后权威快照一到达又把它抹掉，用户会看到「消息闪一下又变了」。
冷启动时若已有事件落库，`ChatReducer` 会按同样的规则从事件重建，流式部分自然从「没有 live 帧」的干净状态开始。

**代价**：断线瞬间正在流式输出的最后半句话**不会**出现在离线缓存里（这是正确的——它本来就不确定会不会被提交）。

**记录**：`ChatViewModel.kt` 的 `persist`；`测试记录.md` T021。

## D24 · 展示路径与查询路径分成两个字段，且 KDoc 必须写明「不得用于查询」

**日期**：2026-10-14 · **状态**：已接受（自主决策，源自 R006 P1-5 与 R005 P1-A 的同一根因复发）

**决策**：凡是「给用户看」的路径字符串与「拿去查」的路径字符串，**必须是两个不同名字的字段**，且展示字段的 KDoc 必须显式写「仅用于显示，不得用于查询或作为 key」。

**理由**：这个坑在本工程**连续两次**出现，换了调用点、换了层：

- R005 P1-A（M3.5）：改动文件卡片把 `display`（桌面端裁短的展示路径）当 `path` 传给 `FileTarget` → `indexOfFirst { it.path == path }` 恒为 -1 → `hasDiff = false`，本轮 diff 与「在电脑上打开」入口一起丢失。
- R006 P1-5（M4）：同一个 `display` / `path` 混淆在**另一个**调用点重演。

两次都不是「写错一行」，而是**两个字段长得很像、语义不同，而类型系统完全无法区分**（都是 `String`）。只靠「下次小心」没用——事实已经证明它会在新代码里再犯。

**代价**：字段数略增；每次新增路径字段都要多想一步「这个字段会被拿去查吗」。

**记录**：`代码审查记录.md` R005 P1-A / R006 P1-5；`core/changes/ChangesModel.kt` 与 `ui/chat/ChatCards.kt`。

## D25 · 状态一律由 reducer 单一真相源推导，禁止私有台账

**日期**：2026-10-14 · **状态**：已接受（自主决策，源自 R006 P1-4 与 M3 冷启动的同一根因）

**决策**：`ChatUiState` / `HomeUiState` 里任何「待办/已请求」集合，**只允许从 `StateFlow` 的当前值推导**，不得在 ViewModel 里另存一份私有 Set/Map 台账。

**理由**：同一个根因在本工程出现第三次：

- M3 冷启动空列表：`WorkspaceRepository` 的 `.scan(WorkspaceSnapshot())` 种子在 reducer 之外产生了第二份状态。
- R005 P1-B：`requestedChanges` 私有 Set 与快照裁剪不同步 → 重连后卡片永久空白。
- R006 P1-4：同一处台账在 M4 的接线里再次漂移。

三次的共同形状：**状态有两个表示方式，它们必然漂移，而漂移方向总是「旧的覆盖新的」**（`distinctBy` 保首、`.copy` 覆盖、裁剪只裁一边）。

**代价**：推导式代码比直接查台账略绕；有时需要把「谁在加载中」这种信息显式搬进 state（R006 正是这么修 `changesLoading` 的）。

## D36 · 服务端不回执的状态，客户端必须做本地回声；回声只能挂在独立的、无 seq 的槽位

**日期**：2026-10-14 · **状态**：已接受（源自用户 m20380 反馈）

**决策**：当一次用户操作在服务端**没有可查询的回执**时，客户端必须自己做本地回声（optimistic echo），
且回声只能放进**独立的、没有 `seq` 的槽位**，绝不与权威列表混存。

**理由**：用户发现一条早前打进 App 的消息在会话生成时「没有任何反应」，直到当前轮结束才被执行。
根因是 `session/prompt` 的结果**只有 `{accepted: true}`**（`typert.host.js:803-805`），
`session/follow` 快照投影里**没有任何 queue 投影**（`typert.remote-client.js:222-341` 逐行读完），
SDK 的 `pendingSubmissions` 只是进程内客户端的本地回声（`client.js:1684-1707`）。
**走 wire 的远程客户端对「我的消息排到第几、能不能撤」一无所知。**

两条子决策：

1. **不做「撤回」按钮**。`session/updateQueue` 必须要 `itemId`（`typert.host.js:843-862`），
   而 itemId 在 prompt 返回值、快照投影、事件里**都拿不到** → 对纯远程客户端实际不可用。
   一个撤不掉的撤回按钮比不做更糟。
2. **回声绝不进 `state.items`、绝不进 Room**。它没有 `seq`，而 `ChatScreen` 用
   `key = { it.seq }` 渲染 `LazyColumn`，假 seq 会抛 `Key was already used`；
   同时会污染 `session/page` 的游标语义与 `distinctBy{seq}` 合并且逻辑。进 Room 则会让它
   在冷启动后复活——而服务端队列与本地状态无关，那时它本该消失。

**回声的生命周期由两个事件驱动**：`turn/start` 清空全部（服务端开始出队 = 队列已腾空），
`user/message` 摘掉最老一条（FIFO 对上）。**`when` 分支里 `turn/start` 必须排在 `item == null` 之前**——
轮次事件不占行、`item` 恒为 null，顺序写反这条分支永远走不到（首跑测试即此错）。

**代价**：多一个 `ChatUiState.queued` 字段与两条 reducer 分支；RPC 失败时要显式摘掉回声
（否则是一条永不被换掉的幽灵气泡），而 `CancellationException` 分支不能摘（服务端可能已收下）。

**记录**：`core/session/ChatModel.kt`（`QueuedMessage`）、`core/session/ChatReducer.kt`、
`ui/chat/ChatViewModel.kt`（`queuedEchoSeq`）、`ui/chat/ChatScreen.kt`（`QueuedRow`）；

## D36：`user/message` 的渲染判据是 `data.source.kind === 'user'`，不是事件类型

**背景**：用户 m22856 反馈「对话气泡中显示不是我发送的提示词（看起来是插件构建的 prompt）」。
探针全量统计 227 条 `user/message`，只有 40 条 kind 是 `user`，

**理由**：

## D39：缓存过滤的判据必须是「要不要写」，不是「要不要渲染」

**背景**：R012 为「注入的 `user/message` 不占缓存预算」把
`ChatFrameParser.recordEnvelopes` 的判据写成 `toChatItem(parsed) != null`（可渲染才写缓存）。
独立复审（子 Agent `5ae695e2`）指出这是回退：`windowMinSeq` 退化成「首个可渲染事件的 seq」，
而 `ChatReducer.onSnapshot` 的 `older = items.filter { it.seq < snapshotMinSeq }` 正是靠这个
下界把旧条目转成 `prepended` 而不重复渲染（R006 P3-1 定下的设计）。

**决策**：新增 `SessionEventParser.isCacheable(event)`，判据收窄为
`event.type != "user/message" || userItem(event) != null`。只挡注入的 `user/message`，
turn 系列照旧进 envelopes，`windowMinSeq` 恢复。

**理由**：
1. **「读回来会不会变成 null」不是判断标准**。`turn/start` 读回来确实是 null（没有卡片），
   但它有别的用途：缓存的意义不只是「重放消息」，还包括让重连后的生成状态、窗口下界成立。
   为 A 目标优化而破坏 B 目标，是本轮踩的坑。
2. **同一目标的两处实现必须共用同一个谓词**。本轮的真实目标是「注入的 user/message 别占预算」，
   而快照路径与实时路径各写了一遍过滤（P2-B 发现实时路径根本没写）。抽成
   `recordEnvelopes` / `cacheable` 两个入口共用 `isCacheable`，第三个入口才不会再漏。
3. **升级路径要考虑旧数据**。同版本内 P2-A 不可达（解析规则未变），但用户从旧包升级时
   旧缓存里的注入气泡会被 prepend 回列表。修复不依赖版本号，靠判据本身正确。

**代价**：turn/step 事件仍会进 envelopes（约占缓存行数的一部分），注入过滤只砍掉
`user/message` 这一族。实测某会话 31361 条事件里 `user/message` 227 条（其中 187 条注入），
turn/step 系 12159 条——但缓存上限是 600 条且按 append trim，砍掉 187 条注入已经把
真实对话的占用降回原来的四分之一左右，目标达成。

**记录**：`core/session/SessionEventParser.kt`（`isCacheable` + KDoc 完整论证）、

## D40：滚动条的高度模型必须乘「会话长度系数」，不能只用已加载窗口

**背景**：用户 m24431 真机反馈「滑块不会根据会话长度变化，大小不变」。

**理由**：`session/follow` 首屏只给约 50 行，而真实会话可能有几万条事件。滚动条若只用
已加载窗口的行高，`viewport / total` 在所有会话里恒为同一个数——滑块大小与会话长度完全无关，
滚动条退化成「一个装饰」。反过来，把未加载头部按 `已加载总高 × (scale - 1)` 估算后，
「我发送的消息」标记也自动落到轨道末段，与真实分布一致。

**系数**：`sessionScale = (cursor + 1) / (cursor - 已加载首行 seq + 1)`，
即「整个会话事件数 / 已加载窗口事件数」。`hasMore == false` 或 `items` 为空时取 1
（没有可放大的头部）；系数 `coerceIn(1f, 64f)`。**是估算不是精确值**：行高方差大，
但累积后方差被平均掉，标记位置足够接近；点标记即使偏一行也只是跳到相邻消息。
**宁可近似也要有正确的量级感**。

**代价**：`cursor + 1` 假设 seq 从 0 连续递增；实际首个可渲染项的 seq 之前还有噪声事件，
所以 span 略偏大、系数略偏小（滑块略大）——保守方向，可接受。

**实现约束**：系数在**组合期读一次、再把值当 `remember` 的键**，不要塞进 `derivedStateOf`。
derivedStateOf 的计算可能在 pointerInput / SideEffect 这些非观察作用域里被调用，
那种调用不登记依赖，系数变了模型不重算（本轮实测踩过）。

**记录**：`ui/chat/ChatScreen.kt` 的 `sessionLengthScale` lambda 与 KDoc、
`ui/chat/ChatScrollbar.kt` 的 `Geometry` 与 `MAX_SESSION_SCALE`。
## D40：滚动条的「会话长度」只能由系数补偿，且下限必须留

`session/follow` 首屏只给约 50 行，滚动条的行高模型量到的永远只是**已加载窗口**。
要让滑块大小反映真实会话长度，只能乘一个系数
`sessionScale = (cursor + 1) / (cursor - 已加载首行 seq + 1)`，未加载头部按
`已加载总高 × (scale - 1)` 估算。三点约束：

1. **系数在组合期读一次、把值当 `remember` 的键**，不塞进 `derivedStateOf`——
   derivedStateOf 的计算可能在 pointerInput / SideEffect 这类非观察作用域里被调用，
   那种调用不登记依赖，系数变了模型不重算（实测踩过）。
2. **必须留下限**（`MIN_THUMB_FRACTION = 0.06` ≈ 48dp）。长会话的真实比例可能只有 0.3%，
   没有下限滑块细到点不着；钳了高度还要反过来钳位置，否则贴底时底边画到轨道外面。
3. **系数同时决定标记位置**：已加载窗口是会话较新的尾部，标记必须整体后移，
   否则老会话把所有标记挤在轨道最下面一小段。实测四个会话标记落在 0.918–0.978。

判断「补偿是否正确」的判据不是滑块好不好看，而是**标记 fraction 是否明显大于 0**：
不乘系数时标记必然摊在 0..1，乘了才聚集在末段。

## D41｜永不重启的 effect 持有的 lambda 必须读委托，不能按值捕获普通 val

**规则**：`LaunchedEffect` 的 key 在整个会话里不变时（本工程四处：`ChatScrollFollow`、
`ChatHistoryFollow`、`ChatScrollbar` 的两个协程），effect 里所有「当前值」都必须通过
**读活状态**拿到——要么 `by derivedStateOf` / `by collectAsState` 的委托，
要么 lambda 里直接读 `state.x`。写成 `val x = 算一下()` 再 `{ x }` 就是缺陷。

**理由**：这类缺陷有三个特征让它反复逃脱——① 开会话时 `items` 通常为空，冻住的值是
「空的」，看起来跟「还没到」一模一样；② 只在**真实渲染**时现形，纯逻辑单测一条也抓不到
（本工程第九次为此付代价）；③ 症状（不滚动 / 标记消失 / 点击跳底部）分散在三处，
每处单看都像别的问题。

**代价与边界**：`derivedStateOf` 只在依赖变化时重算，读它要付出一次依赖登记；
对于 `foldChatItems` 这种 O(n) 纯函数，每个 token 重算一次是可接受的
（折叠后行数远小于事件数）。


## D42｜「生成中没法翻历史」是自动跟随的正确行为，不是缺陷

流式生成时 `ChatScrollFollow` 每个 token 都按当前 `lastIndex` 拉回底部，用户上翻的手势会被立即撤回去。
这与桌面端一致（生成中默认跟随最新）。**设备验证时若会话正在生成，要么等轮次结束、要么换一个空闲会话**，
否则会把「跟随生效」误测成「列表滚不动」。

反过来，这也是一条现成的判据：**对生成中的列表连发多个方向不同的 swipe，屏幕纹丝不动
= 跟随逻辑活着**。本次用它证明了 R015 P1-1 的 `lastIndex` 不再被冻住。

## D44 · 「消息内容」与「待发送区」的视觉语言必须不同

助手气泡去掉底色（用户明确要求），但折叠分组卡片、工具卡片、排队条条带保留 `surfaceVariant`。
判据不是「好看」而是**「这是不是对话内容」**：对话内容铺在列表背景上（与桌面端一致），
非对话内容（折叠的过程摘要、待发送队列、错误横幅）必须有可见边界。
排队条尤其不能去底——它在 composer 上方，去底后会与消息列表的最后一条糊成一片。
同理：`GroupRow` / `ToolCall` / `ToolResult` 三个仍是卡片，用户反馈的「气泡」只指助手正文。

### D46 · 「正在运行」全 App 只由一个组件表达，且必须有「动画关闭」退化路径

R017 之前，App 里有 **5 处**各自表达「正在运行」：`SessionRowItem` 的 6dp 静态绿点、
`GroupRow` 的呼吸点 + 「进行中」文字、`LiveRow` 的呼吸点、`ModelBar` 无、
`ConnectionBanner` 的重连态呼吸圆点。五处形态、大小、节奏全不一样。

定稿：**只由 `ui/common/GeneratingGlyph.kt` 的 `GeneratingGlyph` 表达**，三档尺寸
（SM 16dp 三柱均衡器 600ms 错峰 / MD 20dp 弧线扫旋 900ms / LG 28dp 终端光标 530ms）。
判据不是「统一好看」，而是**用户只应学会一个符号**：看到三柱 = 有会话在跑，看到光标 =
正在往这条气泡里吐字。混用会让用户把「重连中」和「生成中」读成同一件事。

配套铁律（写进组件 KDoc，也是审查判据）：
- 每屏可见无限动画 **≤2** 个；
- 动画量走 Canvas/`graphicsLayer` 内部重绘，**不触发重新测量**；
- 循环周期 **≥530ms**（低于这个值在 60Hz 屏上就是纯频闪，无障碍风险）；
- `rememberAnimationsEnabled()` 读 `Settings.Global.ANIMATOR_DURATION_SCALE != 0f`，
  关闭时退化静态三柱，**但状态不能消失**（不能变成空白）；
- 每个 Glyph 带 `contentDescription`；
- 不引 Lottie（一个 Canvas + 三个 animateFloat 的事，不值得 300KB 依赖与 JSON 解析）。

### D47 · 卡片一律「实底 + 1dp 描边」，会话行一律「无底 + 2dp 导轨」

R017 之前 `WorkspaceRow` 用 `surfaceVariant@0.35`、`SessionRowItem`/`GroupRow` 用
`@0.45`——**两套主题各自糊成不同灰**，而且 alpha 叠加在 `LazyColumn` 的滚动背景上会
出现「卡片边缘比中间亮」的脏边。

定稿：
- 工作区卡 = `surface` 实底 + 1dp `outlineVariant` 描边 + `groupShape` 14dp；
- 会话行 = **无底无卡** + 左侧 2dp 圆角导轨（`primary@35%`，归档降 `outline` 色）；
- 聊天折叠卡/工具卡/思考块 = `surfaceVariant` 实底 + 1dp 描边。

判据：**「这是不是一个容器」**。会话行是列表的一行（不是卡片），所以只用一条 2dp 导轨
标记它的边界与状态；工作区是容纳会话的容器，所以要闭合描边。
副作用收益：去掉 alpha 叠加后深浅两套主题的颜色可以精确预测，不再需要逐个屏幕调透明度。

同时**删掉卡片之间的 `HorizontalDivider`**——卡片自带描边后再加分隔线是双描。
`WorkspaceRow` 左侧标识从 `CircleShape` 改 36dp 圆角方块：圆读作头像、方读作容器。

### D48 · 语义色必须显式定义；tertiary 一直没设是既有缺陷

`ui/theme/Theme.kt` 两套 palette **都没设 tertiary**，落 Material 默认紫

定稿：
- `tertiary` 四件套 × 两套：dark `#F2C14E`（琥珀，`onTertiary=#3A2A00`，
  `tertiaryContainer=#4A3A12`，`onTertiaryContainer=#FFE7B0`）；
  light `#8A5A00`（配套反色）。
- 新增语义 token `LocalStatusRunning`：dark `#4ADE80` / light `#15803D`，

### D49 · 顶栏 actions 只准一个图标按钮，其余动作进溢出菜单；诊断给两个入口

## D50 · 按压反馈的 interactionSource 必须由调用方创建并外传

按压态 hook（`rememberPressScale` / `rememberPressTint`）内部**不能**自建
`MutableInteractionSource`。`.clickable(onClick = …)` 会自建自己的 source，两个 source
互不相通 → scale 恒 1f、tint 恒 Transparent，反馈"看起来接上了"实际完全没生效（R018 P2-2）。
修法：hook 收 `interactionSource` 参数，调用方 `val interaction = remember { MutableInteractionSource() }`
创建后同时传给 `.clickable(interactionSource = interaction)` 与 hook。

配套：`pressed = interaction is PressInteraction.Press`（**不是 `Press || Release`**）。
Release 表示手指抬起，不是"该复位"——常规点按不产生 Cancel，写成 `Press || Release`
会让按压态永久停在 true（R018 P1-2）。

## D53 · 审批策略手机端只读，但审批请求必须能答

用户 m28009 要求实现「会话审批权限」。侦察结论分两半，必须分开对待：

- **策略本身手机端只读**：`session` 命名空间 17 个方法里没有任何 setApprovalPolicy；

**`SessionPermission` 是三个独立字段（`sandboxMode` / `approvalPolicy` / `preset`）+ asOfSeq，

合成档位必然与桌面端不一致，而这里错一次用户就完全失去对权限状态的判断。

## D54 · 乐观移除一律按「流代次」守卫，失败回填要看流有没有重建过

`answerApproval` 点了就该立刻消失（否则网络往返那几百毫秒里用户会再点一次），但失败时
要不要放回来，取决于**流在这几百毫秒里重建过没有**：重建过（重连 / 新 ready）时旧 eventId
在新流里本来就不存在，放回来只会多一张永远点不动的卡片。
修法是记 `startedEpoch = epoch`，catch 里 `if (startedEpoch == epoch)` 才回填。

这是本工程第 N 次「乐观更新需要守卫」：M2 的 `sessionsLoading`、R005 的 `requestedChanges`、
R006 的 `committedSeq` 都是同一形状。**规则固化：任何乐观更新的回滚条件都不能只看
「操作失败了」，还要看「世界还是不是原来那个世界」。**

## D56 · 审批与提问必须占住输入框，而不是在消息区插横幅

## D57 · `interactive` 的优先级固定为 审批 > 提问

`interactive = approval ?: question`。理由：审批请求带 `callId` 与「允许后这一步会立刻执行」，

## D58 · 提问刷新走四条路，`questionSignal` 只是其中一条

① `session/projections` unary 首读（进会话立即拉一次）；② `session/control` 流（投影变更推送）；
③ `$events` 的 `user-questions/request` waterfall → `questionSignal`；④ `generating` 时 2.5s 周期重读。
理由：control 流的 baseline 只含 Host 当前选中的那 1 个会话（实测），单靠它不够；

所以 waterfall 只能当「该去重读了」的信号，真正的问题清单永远来自投影。

## D59 · `permission` 投影优先于事件折叠，但两者都保留

`session/list` / `session/projections` / `session/follow` 快照都带 `permissions` 投影
（`{"currentValue": …}`），比从 `approval/policy` + `sandbox/mode` + `permission/preset`

## D61 · 「已回答」必须独立于「当前在列表里」记账

**日期**：2026-10-15　**状态**：已接受（R024 审查 P1-1）

审批卡片的去重不能只看 `_approvals.value`：`answer()` 会立刻把卡片摘走，
此时服务端补发同一条 waterfall 就会被当成新请求插回来，而服务端早已视为已回答——
用户拿到一张点一次错一次的卡片。

定稿：`RemoteEventsClient` 维护 `handledApprovals`（`ArrayDeque` + `HashSet` 双索引），

两条边界：
1. **环形上限 `HANDLED_RING = 64`**——只需覆盖「服务端补发」的秒级窗口，
   全留就是与历史审批次数成正比的无界增长。
2. **新流清账**——`ready` 帧带来新 `clientId` 时（以及 `unpaired`）必须清空记账，
   否则新流里同一个 eventId 会被误判为已处理而静默丢弃。

只写 `current.none { … }` 是这条缺陷的根因，代码评审时值得单独看一眼。

## D62 · 读-改-写一律整块加锁，`update{}` 不嵌套

**日期**：2026-10-15　**状态**：已接受（R020 已立，R024 P2-1 重申）

`RemoteEventsClient.handle()` 跑在 IO 调度器，`answer()` / `dismiss()` 跑在主线程。
任何「先读 `_approvals.value` 再写回」的复合操作都必须 `synchronized(lock)` 整块包住，
否则一次并发删除会被随后的写回盖掉。

**不用 `MutableStateFlow.update{}` 嵌套**：外层 CAS 重试会让内层 `update` 也重跑，统计双算。
本轮 `dismiss()` 与 `cancel` 分支就是漏加锁的两处，已补。


## D63 · 提问走 waterfall 即时通道，2.5s 轮询降为兜底

**日期**：2026-10-15　**状态**：已接受（R024）

`$events` 转发流的 `user-questions/request` 是 `mode:'waterfall'`，
与 `approval/request` 同一套机制。R024 之前它只被当作「去刷一次投影」的信号，
卡片最坏要等一个轮询周期（2.5s）才出现。

定稿：**waterfall 帧的 `request` 直接转成交互卡片**，
`ChatViewModel.questionsOf` 先弹窗、再去投影里按 `callId` 补全；
投影里已有同一 `callId` 的活动提问时不重复添加。

三条边界：

1. **投影快照里找不到对应 `QuestionSet` 就放弃这张卡片**。
   宁可没有，也不要拿半截信息做一张看起来完整、实际字段是猜的卡片。
2. **type 是 `Waterfall` 但 outcome 不是 `ApprovalOutcome`**。
   `ApprovalOutcome` 只有 `allowed-once` / `rejected` 两值，硬套会让
   `$events/result` 回 `gateway/bad-request`。必须新开 `QuestionOutcome`
   （`answer` / `skip`）。
3. **「已回答」记账必须先记账后发送**。
   崩溃窗口从「已答未记」缩小成「记了没答」，而后者只是卡片不消失，用户能自己点，
   不会点出第二次回答。

配套纪律：**审批与提问的记账必须共用同一个环形上限**（都是 64），
否则两条路径的清理时机不一致，排查时会对不上。

### D65 · 单选的「点已选项」是幂等，不是取消

**问题**：`ChatReducer.toggleOption` 的单选分支把「点已选中的选项」解释成取消。
而第一个选项是被 `defaultOf` 预选的，用户认同它时会顺手点一下确认 →
提交出去的是 `{selected: []}`，桌面端拿到空答案，什么决定都没收到。
真机上桌面端 agent 的原话：「卡片提交了，selected 数组是空的——
既没有 继续 也没有 停止 落进去。所以我这边没有拿到任何决定，不会替你猜一个往下走。」

**定稿**：单选下点已选项幂等（重新选中同一项、清掉自定义文本）。
多选保持开关语义（点已选项 = 取消），因为多选本来就是 checkbox。
「都不对」的出口是自定义答案框，不是取消预选。

**理由**：
1. 桌面端规格只说「点击单选选项会立即前进」，没说可以取消；
   原生 radio 语义也不允许点已选项取消。
2. 预选项是「未提交草稿」，用户点它 = 确认，不是撤回。
3. 空 `selected` 在 wire 上等于「跳过」，把确认动作变成跳过是静默的数据损坏。

**代价**：用户无法用点击表达「我要清空这道题」。实际路径是自定义答案框打进去再删掉
（`setCustomAnswer("")`），草稿键仍在、`isAnswered` 为 false，
`seedQuestionDefaults` 的 `containsKey` 截断照样认得它被碰过。

**测试教训**：`用户主动清空的题不会被重铺默认值` 原本用「点已选项取消」制造清空，
修复后这条用例的**前提**没了——**当一个缺陷修复让某条测试的造数据手段失效时，
要换手段而不是删测试**，否则被守护的行为（「碰过但故意清空」不被重铺）就裸奔了。

## D66 · 提问守卫必须数「答案」而不是「草稿键」

## D67 · mux 流的「收集方必须自带 catch」是硬性契约，不是可选防御

**背景**：真机崩溃（用户 m39951）的根因是 `ChatViewModel` 的 `controlJob` 是唯一没有
`.catch` 的 mux 流收集点。`RemoteStreamMux` 在连接失败时会用**同一个 cause** 关闭所有流的
Channel（`channels.forEach { it.close(cause) }`），`callbackFlow` 于是把它当作**流的终止原因**
抛给收集方；收集方跑在 `Dispatchers.Main.immediate` 上，异常逃出协程即
`FATAL EXCEPTION: main`（进程被杀）。

**决策**：把「**调用方必须给收集链加 `.catch`（并原样重抛 `CancellationException`）**」
写进 `RemoteStreamMux.open()` 与 `MuxListener` 的 KDoc，作为本类与调用方之间的**硬性契约**；
`MuxListener` 五个回调的 `runCatching` 保留，但标注为**纵深防御**而非修复点。

**理由**：崩溃的异常**不从 OkHttp 回调线程逃逸**——`RealWebSocket.loopReader` 自己 `catch`
后走 `failWebSocket` → `onFailure`；真正抛出的是
`failCarrier` → `live.deferred.completeExceptionally(cause)` → `waitForSocket()`。
原注释声称「两层都要有，缺任一层进程都会死」，与实现不符，危害是**下一位维护者会以为
mux 已保护所有收集方**——R027 审查 D3 就是据此提出的。把契约写清比加一层挡不住的防御更有价值。

**推论**：这类「防御加在了不经过的路径上」与本工程已出现三次的「用一个邻近量代替真正要
守护的量」（D66）同源——都是**对机制的想象代替了对机制的验证**。写防护前先确认异常
**实际从哪条路走**。

## D68 · 优雅关闭与强制拆连必须分开控制（`cancelSocket`）

**背景**：R027 修非法帧路径时给 `failCarrier` 无条件加了 `live.socket?.cancel()`，
2 条既有测试立刻失败（`malformedServerFrameClosesClientWith4002`）。

**决策**：`failCarrier(live, cause, cancelSocket: Boolean = true)`；非法帧路径**先**
`webSocket.close(MuxFrame.CLOSE_INVALID_FRAME, INVALID_FRAME_REASON)` **再** `failCarrier(…, cancelSocket = false)`。
默认 `true` 让既有调用点行为不变。

**理由**：`WebSocket.close(4002, …)` 是**优雅关闭**——它把关闭帧排入发送队列并等对端回应；
紧接着 `cancel()` 会立刻拆掉 TCP，**4002 帧根本发不出去**，服务端看不到关闭原因。
「告诉对端我为什么关」与「立刻释放本地资源」是两个不同意图，不能用一个无条件动作表达。

## D73 · 组件必须只有一个调用点，否则点一下就会丢焦点

**背景**：R028 ④ 真机抓到「点输入框毫无反应、永远展不开」。根因是输入区写成

改条件式，`expanded` 参数也从写死改成传值）。
另：**`Modifier.weight(1f)` 不要成对给「会吃掉宽度」的兄弟**——底排曾写成
`Box(weight(1f, fill = false)){模型胶囊}` + `Spacer(weight(1f))`，两个 1f 对半分，
而 spacer 一个像素都不用，模型名被截成「buddy/de…」。改成唯一弹性槽后宽度从 195px 涨到 498px。

**理由**：这是本工程第三次由「交互路径没有测试覆盖」付出代价（R003 `LazyColumn` key、
R027 收集方 `.catch`、R028 焦点）。**渲染测试必须至少有一条走点击/输入，不能全靠传参把界面摆到目标态**——
18 条既有 Composer 渲染测试全绿，却一条都没走交互路径。

## D75 · 握手期 RST 的失败要带「换入口」引导，而不是裸 Connection reset

**背景**：T052 定案 zcsb.ltd:38443 链路按 ClientHello 指纹（长度/后量子组）丢弃握手包，
Android Conscrypt 的 ~250B hello 必被 RST；浏览器（后量子、1.5KB+）能过。App 无法伪装指纹
（Conscrypt 不暴露追加扩展/padding 的接口），该入口对 App 永久不可用。

**决策**：新增 `core/net/TlsFingerprintHint.kt`（纯 JVM、可单测）：
- `isHandshakeReset(cause)`：沿 cause 链认 `SSLException` 家族或消息含
  `Connection reset` / `Read error` / `connection aborted`（Conscrypt 部分版本把握手 RST
  包成裸 SocketException）；
- `hintFor(baseUrl, cause)`：仅对 `https://` 生成引导文案（明文 http 的 RST 与指纹无关，不套这套说辞）；
- `augment(...)`：拼进原消息，供 `PairingApi` 两处 CODE_NETWORK 出口共用。

**理由**：这是启发式**文案增强**，不参与任何安全/准入决策（准入仍只有 HostPolicy 一道闸）。
失败本身不可恢复（重试无意义），唯一出路是换入口，所以文案必须给出可执行的下一步
（换 *.ts.net 二维码 / 桌面端调隧道），而不是让用户对着一句 reset 发呆。

## D76 · 公网入口用「裸 IP + Let's Encrypt IP 证书」，不改 App 信任链

**背景**：T052 定案 zcsb.ltd 被链路 DPI 按「目的地 IP × SNI 观察名单 × 非浏览器指纹」拦截，
服务器侧配置无法解除；等 ICP 备案周期不可控。用户明确「先不修改 app」。

**决策**：入口改为 `https://47.114.41.61`（裸 IP，443 与 8888 双端口），证书用 Let's Encrypt
`shortlived` profile 的 IP 证书（RFC 8738），App 侧零改动。

**理由**：
1. **DPI 规则三键之一是 SNI**：裸 IP 直连的 ClientHello **不带 SNI**，规则不触发——客户端指纹
   再小也能过（实测同一台机器：直连 IP 握手成功，带 `SNI=zcsb.ltd` 一律 RST）；
2. **不动 App 是硬约束**：App 用系统 Conscrypt，无法追加扩展/padding；要让 App 连上，只能是
   「系统已信任的 CA 签发、SAN 含该 IP」的证书，LE IP 证书正好满足（Android 默认信 ISRG Root X1）；
3. **不内置自签 CA**：用户否决把证书信任写进 App——开源分发会让别人的 App 只信我们的根，且要改
   代码、加信任 UI；
4. **比 Funnel 更稳**：Funnel 依赖第三方命名与带宽；裸 IP 走境内节点，延迟低、无第三方依赖。

**代价与补偿**：
- IP 证书只有 **6 天**有效期（shortlived profile 强制）→ 每日 cron + 剩余 3 天续期脚本覆盖，
  实测 8.7s 完成且不停站；
- IP 写死在配对链接里，换服务器要重新配对（App 的「地址」本就可改）；
- 服务器 IP 暴露在配对链接中（它本来就是公网地址，可接受）。

**边界**：不改 App 的任何信任/准入逻辑（HostPolicy 仍在配对前跑）；这是**部署形态决策**，
不是安全策略变更。zcsb.ltd:8888 保留为备用入口。

## D77 · 隧道传输用 QUIC + 用户级 watchdog 自愈，UDP 不通时自动回退 TCP

**决定**：frpc 连接 frps 用 QUIC（`transport.protocol = "quic"`；frps 根级 `quicBindPort = 7000`），
并给 frpc 配「开机自启 + 30s 守护 + 失败重启 + QUIC→TCP 回退」。

**为什么换 QUIC**：并发 3×60 实测，TCP 最坏 **3.408s**（三条流同时卡死 3.34–3.41s），QUIC 最坏
**0.774s**；串行样本两者无差异。根因是单条 TCP 上 yamux 多路复用的**队头阻塞**：一条流丢包/延迟，
其后的帧全部排队。QUIC 的流级独立重传天然规避这一点，且对移动网络抖动更友好。

**为什么用 Run 键而不是计划任务**：当前会话非管理员，`Register-ScheduledTask` 返回
`0x80070005`；`HKCU\...\CurrentVersion\Run` + 隐藏 `wscript` 启动同效且不需提权。守护用 pid 文件
保证单实例（曾因手动启动与守护并发出现两个 frpc 抢 `dsh-web`，表现为 502）。

**为什么保留 TCP 回退**：QUIC 依赖 UDP 7000 全程可达；若客户端所在网络封 UDP，frpc 永远登录不上，
守护会无限重启且入口静默死亡。故 watchdog 在 QUIC 下连续 2 个「重启后仍不健康」周期时，自动用
`frpc.toml.tcp` 覆盖并重启——宁可多一次重启噪声，也不接受入口永久失效。

**代价**：切换传输瞬间有 33–40 秒的旧 proxy 过期窗口（`proxy already exists` → 502）；两份模板
（`frpc.toml.quic`、`frpc.toml.tcp`）需与 `frpc.toml` 保持同步；QUIC 走 UDP，个别企业网/运营商可能
限速或阻断，回退逻辑是兜底而非等价方案。

## D78 · 折叠分组内的工具条目用「行式」，分组外才用「卡片」

**背景**：用户 m44550 第二条反馈——「实际表现与原型图中的美化不符，操作和工具调用的样式还是
和之前一样」。R028 当时只改了**卡片本身**的底色与描边（`surface` + 1dp `outlineVariant`），
没改**形态**：分组内每条工具调用仍是一张独立卡片，展开一个 `×52` 的分组就是 52 张带描边的卡。

**决策**：同一个工具事件在两种语境下用两种形态，**不合并成一个带布尔开关的组件**。

| 语境 | 形态 | 组件 |
|---|---|---|
| 折叠分组内（`GroupRow` 的成员） | 一行：`[工具名 chip] [参数摘要] …… [状态 tag]`，行间靠 1dp 上分隔线连接 | `ToolCallRow` / `ToolResultRow` |
| 分组外（零散的工具事件） | 独立卡片：实底 + 1dp 描边 + chevron + 展开 | `ToolCallCard` / `ToolResultCard` |

**为什么不加 `inGroup: Boolean`**：两者的**点击语义不同**——卡片点标题展开参数，行式点整行
进文件查看页（有路径时）。用布尔开关会把两套语义塞进一个函数，调用方永远要读实现才知道
点了会发生什么。`ChatScreen.kt` 里因此分成 `GroupMemberRow`（分组内分发）与 `ChatItemRow`
（独立条目），而不是给后者加参数。

**连带改动**：分组内层 `LazyColumn` 的 `verticalArrangement` 从 `spacedBy(8.dp)` 改成
`spacedBy(0.dp)`——行与行之间由各自的上分隔线连接，若还留 8dp 空隙，分隔线会浮在两段空白
中间，看起来像断开的短横线。

**代价**：`ToolCallCard` 与 `ToolCallRow` 的展开态各有一份 `rememberSaveable(item.seq)`，
同一个事件在两种语境下的展开状态**互不相通**。接受：一个事件只会出现在其中一种语境里
（`foldChatItems` 决定），不存在同一事件两种形态同时可见的情况。

## D80 · 渲染测试的容器必须与真机一致，否则变异验证也会假阴性

**背景**：R028b 修「助手消息导轨没铺满」时，第一版 `BubbleRailRenderTest` 把 `Bubble` 直接
摆在 `setContent` 的根上——那里高度**有界**，`fillMaxHeight()` 正常工作，测试全绿；**真机上
导轨却完全消失**。

根因：真实的聊天列表是 `LazyColumn` 的 item，高度约束是 `Constraints.Infinity`，而
`fillMaxHeight()` 在无界高度下的语义是「取 maxHeight，否则取 minHeight」= **0**。

**决策**：凡是断言「某个 `fillMaxHeight` / `fillMaxWidth` / 权重分配生效」的渲染测试，
**容器必须复现真机的约束环境**：

- 测聊天消息的布局 → 必须摆在 `LazyColumn` 里；
- 测输入框（`Scaffold` 的 `bottomBar`）→ 必须摆在 `Scaffold` 里，不能裸放；
- 测「点得到按钮」→ 必须考虑 Robolectric 窗口只有 320×386px（D73 的静默失败）。

**这一条与 D46（测试全绿 ≠ 无缺陷）是同一族问题的两个面**：
- D46 说「有测试也可能漏掉缺陷」；
- D80 说「**变异验证通过**也可能守错了布局」——变异验证只证明「删掉修复测试会红」，
  不证明「测试的场景与真机一致」。

**操作要求**：写下任何「几何 / 填充 / 权重」类断言时，先在真机（或至少模拟器）上确认该
断言的场景能复现用户看到的现象；反过来，如果真机现象与测试结论矛盾，**优先怀疑测试的
容器而不是产品代码**。R028b 里我一度按「测试绿 = 修复对」把 `IntrinsicSize.Min` 删掉了，
幸好随后在设备上做了像素扫描才发现导轨根本没画出来。

## D81 · 「铺满父容器」的竖线一律用 `drawBehind`，不用 `fillMaxHeight` + `IntrinsicSize`

**背景**：R028b 修「助手消息导轨没铺满」时踩了两次坑，两次都表现为「导轨在测试里正常、
在真机上看不见或崩溃」。

**坑一（不可见）**：`Row { Box(Modifier.width(1.dp).fillMaxHeight()) }` 住在聊天 `LazyColumn` 的
item 里，高度约束是 `Constraints.Infinity`，而 `fillMaxHeight()` 的实现是
「有上界取 maxHeight，否则取 minHeight」——无界时就是 **0**。导轨一个像素都画不出来。
**渲染测试测不出来**，因为它把组件摆在 `setContent` 根上（高度有界）。

**坑二（崩溃）**：改用 `height(IntrinsicSize.Min)` 让它变成有界值。这对纯内容子项有效，
但一旦子项里有 `LazyColumn` / `LazyRow` / `BoxWithConstraints`（`SubcomposeLayout` 家族），
就抛：

```
IllegalStateException: Asking for intrinsic measurements of SubcomposeLayout layouts is
not supported. This includes components that are built on top of SubcomposeLayout, such
as lazy lists, BoxWithConstraints, TabRow, etc.
```

**决策**：凡是要画一条「与父容器等高」的线/背景，用 `Modifier.drawBehind { drawRect(...) }`。

- 它在**布局完成之后**执行，此时 `size.height` 已经是实测值；
- 不请求固有测量，不受无界高度影响，零额外布局开销；
- 颜色要在**组合作用域**里先取出（`DrawScope` 不是 `@Composable`，拿不到 `MaterialTheme`）。

**适用判断**：只在「线/底纹这类纯装饰」上用 `drawBehind`。如果那条竖线**需要参与布局**
（例如占位、挡住点击、随滚动平移），才考虑 `IntrinsicSize`，并且必须确认子树里没有
`SubcomposeLayout`。

**配套要求（D80）**：这类几何断言必须把组件摆在**真机的容器**里（聊天消息 → `LazyColumn`），
否则测试会绿而真机是空的。

## D82 · 折叠分组内的 tag 只写状态，不写操作

**背景**：用户 m44550 第 2 条「操作和工具调用的样式还是和之前一样」。R028 只改了卡片的
底色与描边，没改**形态**；补行式条目时又把 tag 写成「详情 / 收起」，并涂成绿色
（`ToolTagStyle.OK`）。

**问题**：「详情 / 收起」是**操作提示**，而绿色在整套配色里是「成功」。两者拼在一起
（绿底 + 「详情」）语义彻底错位；原型 `docs/R028-效果图.html` 的 `.grow` 里三条 tag 是
「已编辑 / 完成 / 已读取」——**全是状态**。

**决策**：分组内工具行的 tag 只表达**结果状态**，不表达「能不能展开」。

| 情形 | tag | 配色 |
|---|---|---|
| 工具调用，有文件路径且是写操作 | `已编辑` | `EDIT`（secondaryContainer） |
| 工具调用，有文件路径且是读操作 | `已读取` | `EDIT` |
| 工具调用，无路径 | `已调用` | `NEUTRAL` |
| 工具结果，成功 | `完成` | `OK`（`LocalStatusRunning`） |
| 工具结果，失败 | `失败` | `BAD`（error） |

**展开能力由整行点击承担**，不在 tag 上重复。这也顺带删掉了 `ToolCallRow` /
`ToolResultRow` 的 `expanded` 形参——它原本只用于在 tag 上切换「详情/收起」。

**由此确立的一般规则**：tag / 徽标 / 角标这类**短标签**只放「是什么状态」，
不放「点了会发生什么」。操作提示交给图标（chevron）或可点击的整行。

## D83 · 几何断言假失败时，先查语义合并与节点选择

**背景**：写 `PermissionBadgeClipTest` 验证「待批角标伸出圆钮」时连挂三次，三次都是**测试
自己的问题**，不是产品代码的问题：

1. `onNodeWithText("2")` → 命中的是**合并后的圆钮**（根 `Box` 带 `clickable`，Compose 把
   子节点语义合并进去），bounds 恒等于 32dp，怎么改产品代码都不会红。
2. 加 `useUnmergedTree = true` → 量到的是 `Text` 而不是角标容器，内边距把 bounds 缩进 1dp
   （`right = 31 < 32`），断言仍然假失败。
3. 改 `onNodeWithTag(...)` 但仍挂 → **finder 也必须带 `useUnmergedTree = true`**。
   报错原文直接提示了：`Are you missing useUnmergedNode = true in your finder?`

**决策**：

- 断言「某个**非合并节点**（角标、装饰、内层容器）的几何」时，必须
  `onNodeWithTag(tag, useUnmergedTree = true)`；
- 给这类节点加 `testTag` 时，tag 要放在 **`offset` 之后**——否则量到的是偏移前的位置，
  「有没有伸出去」这类断言全无意义；
- 一个几何断言连续假失败时，**先怀疑自己量错了节点**，不要先改产品代码。
  这是 D80 的同族问题：测试的观测方式错了，比产品代码错了更常见。

## D84 · 可复制的默认交互是「长按选择」，常驻复制按钮只给代码块

**背景**：R029 第 ⑥ 条用户说的是「对话界面应该要可以复制，并且一些代码块也应该要有独立的
复制按钮」。我把它实现成了**每条消息底部一个复制图标按钮**（助手与用户各一个），单测与设备
验收都过了。用户随后指出（m01082）这不是他要的：「我希望的是，用户可以长按复制界面中的内容，
而只有代码块才会显示复制按钮，其他的文本不需要增加复制按钮」。

**判断**：这不是用户改需求，是我当初把「可以复制」读成了「有一个复制按钮」。两者的差别是实质的：

| | 常驻按钮 | 长按选择 |
|---|---|---|
| 能力 | 整条复制 | 可只选一句/一段 |
| 占位 | 每条消息右下角常驻一个热区 | 无 |
| 手感 | 应用自定义 | 系统原生（选择手柄、复制/全选/朗读菜单） |
| 消息里的路径、报错 | 要复制得先整条复制再自己裁 | 直接框选 |

消息正文里最常被复制的是**片段**（一行报错、一个路径、一句结论），不是整条。所以「长按选择」
才是对的主形态；代码块是唯一整段就是复制目标的场景，才值得一个按钮。

**决策**：

- 消息正文用 `SelectionContainer` 包住，走系统选择交互；**不再给消息加复制按钮**。
- 只有代码块（`CodeBlockView`）保留独立复制按钮，用图标不用文字（沿用 R029 的 `CopyIconButton`）。
- 工具调用 / 工具结果卡传 `selectable = false`：它们展开体是几千字原始参数，包进选择容器
  会让长按先选中一堆 JSON，且卡片头部本身要能点开。
- 判断「某条消息是否可选」的测试判据是 `RequestFocus` 语义，**不是** `CopyText`：
  实测 compose-foundation 1.12.1 的 `SelectionContainer` 只挂 `Focused` + `RequestFocus`，
  子树里没有任何 `CopyText`，按后者写断言恒为 false。

**教训（与 D80/D83 同族）**：审查把 `SelectionContainer` 换成裸 `Box`（等于删掉功能），
`assertExists()` 那三条测试**全绿**。凡是「某个组件是否存在」的断言，都要问一句
「换成任意同类容器还成立吗」——成立就说明它没在守任何东西。这一轮的修法是断言组件
独有的语义动作，而不是断言 tag。

## D85 · 目标与任务是两条独立的线，任务胶囊不跟随目标状态变色

**背景**：用户 m01601 提出「似乎当目标暂停时，对话还会继续输出，所以我认为这是独立的，
但是实际还是要去找 dsh 的相关逻辑」。

**查证**（`app.asar` 客户端 bundle）：

- `runMode: plan?.active ? "plan" : goal?.goal.phase === "active" ? "goal" : "default"`
  —— 只决定这一轮以什么模式跑，且仅作埋点字段，**不是运行开关**。
- `goals/pause` / `resume` / `clear` 只是「路由到 Host GoalService 排队一条模型可见的
  goal 上下文消息」；整个 bundle 里 goal 与 `cancel` / `interrupt` / `abort` **零关联**。
- `activation`（armed / disarmed）是**进程本地**状态，与 `phase` 独立。

**决策**：目标暂停 = 不再自动注入「继续目标」的触发消息；当前轮照常跑完、任务照常推进。
因此任务胶囊**不跟随目标变色**，两者各自渲染自己的状态。`goal.phase === "complete"` 时
DSH 的 `GoalBar` 直接 `return null`，本 App 同口径（`Goal.visible`）。

**教训**：用户对第三方产品的「直觉判断」值得先当真去查证，而不是按自己的想象设计联动。
这条如果按「目标暂停 → 任务也暂停」实现，会让用户以为任务卡住了。

## D86 · 目标 / 任务 / 排队三块用枚举做互斥展开，不用两个布尔

**背景**：任务面板展开约 196dp，排队列表展开最多约 210dp，两个都展开时总高可达 548dp。
800dp 的机型减掉顶栏与目标横幅只剩约 480dp，消息区会被压没。

**决策**：`var expandedDock by remember { mutableStateOf(DockTarget.None) }`，
`enum class DockTarget { None, Tasks, Queue }`。从类型上就不存在「同时为真」的状态。
展开状态用普通 `remember` 而**不是** `rememberSaveable`——用户 m45632 明确要求
「状态不做记忆，重新打开对话依旧为展开状态」。

## D87 · 键盘让位的判据是 IME 高度，例外是「正在行内编辑的那一块」

**背景**：用户要求「输入框展开显示输入法时应不显示任务胶囊和排队列表」。首版实现直接
`if (imeVisible) { 三块全不渲染 }`，独立审查 P1-1 指出：行内编辑时键盘**必然**弹起，
于是「点编辑 → 编辑框立刻被销毁」，编辑功能事实上不可用。

**决策**：抽出单一判据函数

```kotlin
internal fun dockVisible(imeVisible: Boolean, editing: Boolean): Boolean = !imeVisible || editing
```

三处调用各传自己的 `editing`（`goalEditing` / `queueEditing`）。判据本身带 `internal`
是为了让 `ImeDockVisibilityTest` 能直接测真值表，不必在 Robolectric 里伪造 IME inset
（本工程在模拟器上 IME inset 恒为 0，伪造一帧真键盘做不到）。

**为什么不用焦点判据**：焦点在但键盘没弹（外接键盘、或用户手动收起键盘）时不该隐藏。

## D88 · 第三方 RPC 的 wire 形状必须逐端点实测，不能按族类推

**背景**：`goals/*` 与 `session/updateQueue` 都是 DSH 的 typert 网关端点，但参数形状与
chat 族（`{request:{sessionId,…}}`）**完全不同**：

| 端点 | args |
|---|---|
| `goals/create` | `{agentId, request:{objective, maxGoalRounds}}` |
| `goals/pause` / `resume` / `clear` | `{agentId, ref:{id,revision}}`（无 request） |
| `goals/edit` | `{agentId, ref, request:{objective}}` |
| `session/updateQueue` | `{request:{sessionId, itemId, action:{kind}}}` |
| `session/create` | `{request:{workspaceId \| cwd, title}}`（两者只能传一个） |
| `session/rename` | `{request:{sessionId, title}}` |

**决策**：每接一个新端点，先用 curl 直接打桌面端 `/remote/api/<ns>/<method>` 确认形状，
把服务端的报错原文抄进 KDoc 当证据，再写实现。

**教训**：首版照 chat 惯例写 `{request:{sessionId, ref}}`，真机点暂停直接弹
`gateway/arguments-invalid: … missing "agentId", "ref"; unexpected "request"`。
网关的报错信息非常精确（会逐字列出缺失与多余字段），照它改比猜快得多。

## D89 · 解析第三方投影时，单测样本必须逐字抄真实报文

**背景**：`projections.values.goal` 线上是**双层**包裹
（`{"goal":{"goal":{…id…},"roundsStarted":0,…}}`），首版解析器读外层当本体 → 恒 null →
真机横幅**从来没渲染过**；而单测喂的是自己手写的扁平样本 `{"goal":{"id":…}}`，恰好命中，
18 条测试全绿。设备验收一打开会话就暴露。

**决策**：凡是解析第三方数据的地方，测试样本一律从真实报文复制粘贴，不手工简化。
解析器对「已经见过但形状不同」的层级用兼容写法（内层优先、扁平兜底），并在 KDoc 里
同时列出两种形状。

**教训（与 D80/D83 同族）**：自己造的样本只证明「解析器能解析自己造的样本」。

## D90 · 任务进度的实时来源是 `todo/write` 事件，不是快照

**背景**：任务胶囊首版只从 `session/follow` 的快照里读 `todos`，进入会话后 n/m 再不变化，
必须退出重进才更新。

**查证**：DSH 客户端 bundle 里 `todo/change`、`todos/change` **均为 0 命中**，
真实事件名是 **`todo/write`**，形状 `{type:"todo/write", seq, time, data:{todos:[{content, status}]}}`
（与 `projections.values.todos` 同形状，可直接复用同一个解析器）。

**决策**：`ChatReducer` 对 `todo/write` 单独一条分支；快照只在订阅/重连时用。
凡是「进入会话那一刻准、之后不变」的表现，都要怀疑缺了一条事件通道，而不是怀疑解析器。

## R032 的四条决策

### D91 · 底部 dock 脱离 Scaffold bottomBar，改浮动 overlay

**决策**：任务胶囊、排队条、输入框三块不再由 `Scaffold(bottomBar = …)` 承载，改为 content 区里的 `Box` overlay（`Alignment.BottomCenter`），消息 `LazyColumn` 的 `contentPadding.bottom` 用 `onSizeChanged` 实测的 dock 高度撑出留白。

**理由**：用户 m04197 第 1 条 + 追问澄清原话「应该是存放输入框和任务胶囊的容器的背景，这个背景不应该是有颜色的，而是透明的…因为我想要的效果是浮界面上，而现在有背景的效果是有一个面板盖在界面上」。`bottomBar` 会占布局高度，把消息区顶上去，于是那块区域永远是页面底色、消息永远滚不到输入框下面——这正是「面板感」的来源，单纯改 `containerColor` 或去掉某个 `background(...)` 都改不掉。只有让 dock 不占布局、叠在消息之上，才能真的「浮」起来。

**代价**：需要自己测高度（`onSizeChanged` → `dockHeightPx`）、`ScrollToBottomFab` 与 `ChatScrollbar` 都要跟着抬高、overlay 的留白会漏点击穿透（已用空 `detectTapGestures` 收口）。审查 P2-1 抓到的滚动条外露就是「没跟着抬高」的直接后果。

### D92 · 排队列表的 splice 必须「先插后删」，`start` 是 target 段内下标

**决策**：`applySplice` 遍历时对同 target 的条目取 `indexInTarget = seenInTarget++`，**先**在 `indexInTarget == splice.start` 处插入，**再**判 `indexInTarget ∈ [start, start + removedCount)` 决定删不删。

**理由**（这是 R032 第 2 条的根因）：旧实现只在「落在删除区间内」时才插入，纯插入（`removedCount == 0`）走末尾兜底 `if (!inserted && seenInTarget <= splice.start)`。首条排队消息的 splice 是 `{start: 0, inserted: [A]}` 且**没有 `removedCount` 字段**（解析后为 0），此时队列里已有 1 条本地回声 → `seenInTarget = 1`，`1 <= 0` 为假 → 服务端条目根本没进去；随后 `filterNot { rpcId in confirmedRpcIds }` 又把本地回声按 rpcId 摘掉 → 队列空 → 整条排队区消失。发第二条时服务端侧 A 已在下标 0、B 在下标 1，`1 <= 1` 成立 → 只插入 B，A 永远缺失 → 界面只剩第二条。退出重进走快照才恢复，与用户描述的三个现象逐一吻合。

**附带约定**：`start` 越过该 target 段末尾时，插到**该段末尾**（`out.indexOfLast { it.target == splice.target }`）而不是整个列表末尾——否则 `next-turn` 的新条目会排到 `next-step` 后面。段为空且 target 是 `next-turn` 时，插到第一条 `next-step` 之前（`parseInbox` 的拼接顺序就是 next-turn → next-step）。

### D93 · 「轮次已用完」判据放客户端，用 `roundsStarted >= maxGoalRounds` 而不是看 `phase`

**决策**：`Goal` 新增 `roundsStarted` 字段与派生属性 `roundsExhausted = maxGoalRounds != null && maxGoalRounds > 0 && roundsStarted >= maxGoalRounds`；`GoalBanner` 在 `!canPause && roundsExhausted` 时把「开始」按钮置灰（色 `onSurfaceVariant @ 0.38f`）、contentDescription 加后缀「（轮次已用完）」，但**不禁用点击**；`ChatViewModel.setGoalPhase` 在该状态下本地早退并写 `goalError`。

**理由**：用户 m04197 第 4 条要求「此时让继续按钮置灰，用户点击会有轮次已用完的反馈」——不禁用是硬要求，禁用了就点不到、也就没有反馈。判据用 `roundsStarted >= maxGoalRounds` 而非 `blockedReason.code == "round-limit"`，因为服务端 `GoalsService.resume` 的拒绝条件就是 `currentState.roundsStarted >= current.maxGoalRounds`（原文 `goal "…" exhausted N goal rounds; increase maxGoalRounds before resuming`，`GOAL_INVALID_TRANSITION`），两者同口径、不会出现「按钮亮着但点了必失败」；而且用户可以事后调小 `maxGoalRounds`，用 `>=` 才覆盖得住。

**不做**：不发那条注定失败的 RPC 再显示服务端英文报错——本地拦掉能给出中文可行动文案「桌面端调大 maxGoalRounds 后才能继续」。

### D94 · 展开态的小圆圈补「扩散动效」，与收起态同节奏

**决策**：`PhaseDot` 从静态 5dp 实心圆改成 `Canvas` 画的脉冲环（实心点半径 `maxRadius * 0.45` 保持原视觉尺寸 + 外扩光环随 `pulse` 变化），仅在 `phase == ACTIVE` 时跑；节奏沿用 `GoalChip` 的 `rememberInfiniteTransition` + `tween(2600, LinearEasing)` + `RepeatMode.Reverse`。

**理由**：用户 m04197 第 3 条「目标收起后如果在运行，小圆圈应该有扩散动效，但是目标展开的时候小圆圈也应该对应运行方式展示动效」——收起态（顶栏 `GoalChip`）本来就有 0.55↔1 的 alpha 呼吸，展开态却是一个静止圆点，同一个状态两种表现。共用节奏是为了让「收/展」切换时动效不跳拍。

**注意**：`rememberInfiniteTransition` 必须写在 `if (pulse)` 分支内（Compose 允许条件调用 Composable，但不能让同一槽位在两次组合间换类型）；审查确认当前写法合规。

## D80 · mux 心跳放宽到 30s，而不是改 App 或换传输

**问题**：App 打开长会话频繁 EOFException（建连成功/失败 46/46）。根因是网关
`RemoteStreamMuxServer` 心跳 2s × 允许丢 2 次 = 6s 无 pong 即 `terminate()`，
而首帧是单条 3-4MB 的 ws 消息，4Mbps 上行要传 14s，期间读不到 ping。

**为什么不在 App 侧修**：App 是 ws 客户端，能做的只有「更快读」——但读的瓶颈是
带宽，不是客户端调度；也无法主动插 pong（pong 由 OkHttp 自动回，前提是它读到了 ping）。
把 App 改成「先收后拼」也救不了，因为帧没到齐就是没到齐。

**为什么不换传输/加压缩**：换传输改不了「一条 ws 消息 > 6s 传输时间」这个事实；
压缩对已压缩的 JSONL 快照收益有限，且要动协议两端。

**为什么放宽心跳而不是禁用**：完全禁用会让真死的客户端永久占连接；30s×3=90s 的
回收窗口在「移动端断网」场景下可接受，且仍能清理僵尸连接。

**代价**：半开连接回收从 6s 变 90s；服务端 `connections` 集合在弱网下会多留几个。

**替代方案（若日后要更严格）**：网关改成「发 ping 前先看 `socket.bufferedAmount`，
积压超阈值就跳过本轮计数」——治本但需改上游包，本次不动。

### D95 · 会话抽屉改成 318dp 浮起面板，而不是铺满 360dp

**决策**：`HomeDrawerSheet` 传 `modifier = Modifier.fillMaxHeight().width(318.dp)`，`drawerShape = RoundedCornerShape(topEnd = 20.dp, bottomEnd = 20.dp)`，`drawerContainerColor = surface`，`drawerTonalElevation = 0.dp`，另加 1dp `outline @ 0.45f` 描边与 12dp 投影。

**理由**：改造前抽屉是一整块 `surface` 色铺到屏幕边缘，与页面底色几乎同色，视觉上「和页面糊在一起」，这就是用户说的「风格有比较大的出入」。留出 42dp 遮罩 + 圆角 + 描边 + 投影，面板才「浮」在内容之上。

**为什么是 318dp 不是 320/300**：material3 1.4.0 的 `DrawerSheet` 内部修饰符链是 `sizeIn(min = MinimumDrawerWidth(240dp), max = NavigationDrawerTokens.ContainerWidth(360dp))`，外部宽度会被夹在 [240, 360]，所以 318dp 有效；选 318 是为了在常见 360dp 屏上留出 42dp 遮罩（正好盖住顶栏左侧的菜单按钮区域，视觉上能看出「后面还有内容」），同时不做成 300dp 以免长会话标题被挤掉。

**代价**：320dp 窄屏上抽屉会几乎铺满（留 2dp），退化成接近全宽。这是有意的取舍——面板宽度是一个常量，不按屏宽自适应，避免在小屏上把标题挤成一串省略号。

### D96 · 抽屉头部加统计胶囊，搜索框只做视觉占位

**决策**：头部三枚 `DrawerStatPill`（会话 / 置顶 / 归档），替代原来挤在副标题里的「共 N 条 · 顶层 M · 已归档 K」；搜索框渲染成 34dp 胶囊占位，**不接任何 RPC**。

**理由**：一行 10sp 的半透明小字里塞三个数字，扫视时读不出来；拆成三枚可扫视的胶囊是纯视觉收益。搜索框不接 RPC 是因为 `DshEndpoints.SESSION_SEARCH` 常量虽然早在 `DshEndpoints.kt:24` 就存在，但全工程零实现，`session/search` 的 wire 参数名从未实测过——按 D88（第三方 RPC wire 形状必须逐端点实测）不该在一个美化任务里顺手猜一个参数形状。

**注意**：搜索框现在是「看着能点、点了没反应」的形态。这是明知的不完整，已记进测试记录 T060-3 未覆盖项；如果用户要真接，先按 D88 实测 `session/search` 的参数与返回形状。

### D97 · 「已归档」做成抽屉内的聚合只读入口

**决策**：抽屉主列表滚到底有一条 `DrawerArchivedEntry`（ArchiveIcon + `已归档 N` + `查看`/`收起` + chevron），点击把 `LazyColumn` 切到归档聚合视图（`hdr-archived` + 各归档会话行 + `返回会话列表`），由 `var archivedOpen by rememberSaveable` 控制。

**理由**：归档的会话在改造前**在 App 里完全看不到**——主区 `WorkspaceRow` 展开后有「已归档 N」段，但抽屉没有，用户归档一条会话后它就从视野里消失了，只能去桌面端取消归档。数据本来就有（`state.snapshot.archivedSessionIds` 是跨工作区全局集合 + `state.sessions.items`），补一个聚合入口不需要任何新 RPC。

**为什么是「切换列表」而不是「底部弹层」或「另一个抽屉」**：抽屉本身就是一个 `ModalDrawerSheet`，再叠一层弹层会引入第二个 Popup/Scrim 层级；切换同一个 `LazyColumn` 的内容最轻，且能复用现成的 `DrawerSessionRow`（归档行的菜单首项会自动变成「取消归档」，因为 `archived = sessionId in archivedIds` 是数据推导的）。

**为什么是只读**：归档视图里能做的只有「取消归档」（菜单里就有）和「打开会话」。不做「批量取消归档」或「删除」，因为 `workspace/archiveSession` 是按工作区批量语义，批量反操作要再发一轮请求，网络失败会制造第二个不确定状态。

### D98 · 「归档」措辞改软成「移入归档」+ AlertDialog 二次确认，而不是 Snackbar 撤销

**决策**：菜单项文案 `移入归档`，点击后先 `onDismiss()` 收菜单，再弹 `AlertDialog`（标题「移入归档？」+ 会话上下文卡 + 「它会从会话列表里移走，可以从「已归档」里找回。」+ 取消/确认移入）。确认按钮文案是 **「确认移入」**，不与菜单项同名。

**理由**：用户原话要求「需要二次确认」。用 Snackbar 撤销的方案被否掉，因为 `archiveSession` 是按工作区批量语义的写操作，撤销要再发一个反向请求，网络失败时会制造第二个不确定状态（用户以为撤销了，实际还在归档里）。弹框在发请求之前就能拦住误触，代价只是多一次点击。

**为什么确认按钮不叫「移入归档」**：首跑实测 `Failed to inject touch input. Reason: Expected exactly '1' node but found '2' nodes that satisfy Text contains '移入归档'`——菜单收起与弹框弹出两个 Popup 的生命周期有重叠瞬间，两个同名节点会让测试与无障碍都歧义。改文案是最干净的修法。

**为什么先 `onDismiss()` 再设 `confirmingArchive = true`**：`DropdownMenu` 与 `AlertDialog` 都是 Popup，同时展开会在层级/z-order 上竞争；先收再弹保证只有一个 Popup 在屏幕上。

### D99 · Archive / Pin 图标手绘，不引入 material-icons-extended

**决策**：新增 `ui/home/HomeIcons.kt`，手绘 `ArchiveIcon`（Material `archive` 字形）与 `PinIcon`（Material `push_pin` 字形），24×24 viewport + `path(fill = SolidColor(Color.Black))`，由 `Icon(tint = …)` 覆盖颜色。

**理由**：`androidx.compose.material:material-icons-core:1.7.8` 只有 49 枚字形（`AccountBox`…`Warning`），没有 Archive/PushPin；`material-icons-extended` 十几 MB，为两个图标引入整个包不划算。这也沿用 R031 `ChatIcons.kt` 的既有做法（`SteerIcon`/`GoalIcon`/`PauseIcon` 都是这么画的）。

### D100 · 配对页三入口分段互斥，而不是三张卡同屏

**决策**：`internal enum class PairEntry(val label: String) { Scan("扫码"), Link("链接"), Manual("手工") }` + `PairEntryPicker`（`Row` 包三个等高 34dp 的 `Surface(onClick, weight 1f)`，选中态 `surface` 底 + 主色字）。同一时刻只渲染一个入口的内容。

**理由**：改造前三件事（扫码 / 粘贴链接 / 手工登记）在一屏里上下堆叠，手工卡里还同时有「配对链接或 token」「服务器地址」「设备 id」三个输入框。真机上踩过：用户把 token 填进了第 1 格（配对链接那栏），配对直接失败——因为这三件事的动机完全不同（扫码是 accept 一个 token；链接是解析既有二维码内容；手工登记是跳过 accept 直接用已有 deviceId），平铺时没有任何线索告诉用户该填哪个。

**为什么用 `Surface(onClick)` 而不是 `TabRow`**：`TabRow` 带 indicator 动画与语义 `Role.Tab`，语义上要求配套的 pager 或内容切换容器；这里只是三选一的本地状态，用一个轻量的分段控件更贴合，也不会在 Robolectric 里引入 `Role.Tab` 的断言复杂度。

### D101 · 取景框用 `aspectRatio(1f)` + 四角标 + 扫描线，且必须用 `BarcodeView` 而不是 `DecoratedBarcodeView`

**决策**：`Box(Modifier.fillMaxWidth().aspectRatio(1f).background(Color.Black, RoundedCornerShape(14.dp)))` 内放 `AndroidView(factory = { BarcodeView(ctx) })` + `ViewfinderBrackets()`（Canvas 画四角 L 形臂）+ `ScanLine()`（`rememberInfiniteTransition` + `tween(2200, LinearEasing)` + `RepeatMode.Reverse`，`Brush.horizontalGradient`）。

**理由**：用户原话「扫码窗口不是正方形，有些难看」——改造前是 `fillMaxWidth().height(220.dp)`，360dp 屏下 336×220 的横矩形。`aspectRatio(1f)` 让它随屏宽变化，任何宽度下都是正方形。

**`BarcodeView` 这条是设备验收才发现的真缺陷**：首版沿用 R031 的 `DecoratedBarcodeView`，它自己在相机预览之上叠了一层半透明遮罩、一个中央方框和左下角状态字（`请将条码置于取景框内扫描。`）。与我们新画的四角标叠加后，屏幕上出现两个「取景框」和一句来路不明的提示。`DecoratedBarcodeView` 是「带取景 UI 的成品控件」，`BarcodeView` 才是「只有相机预览」的裸控件（`BarcodeView extends CameraPreview`，`pauseAndWait()` 由父类提供，所以 `DisposableEffect` 里的调用照旧合法）。

**教训**：zxing 这两个类名很像，语义差一个「装饰」；自己画取景框时用错就得到两层框。

### D102 · 探测结果从 `String` 改成结构化 `PairProbe`，失败不再复用全局错误条

**决策**：`PairViewModel` 新增 `data class PairProbe(val ok: Boolean, val headline: String, val lines: List<String> = emptyList())`，`PairUiState.probe` 类型从 `String?` 改为 `PairProbe?`。成功 → `headline = "地址可达"`，失败 → `"连不上这个地址"` / `"地址格式不对"` / `"这个地址不能用"`，且**失败不再写进 `state.error`**。

**理由**：改造前 `probe` 是一个拼好的字符串（`"已连通；桌面端当前无配对设备\n局域网地址：…"`），UI 只能把它当一段纯文本渲染，成功与失败没有视觉差异。更糟的是失败路径写 `state.error`，与「配对失败」「登记失败」共用同一个红色错误条——用户点「探测地址」失败，看到的错误条与配对失败长得一样，分不清是哪一步出的问题。

**为什么拆成 `headline` + `lines`**：`headline` 是「结论」（一句话），`lines` 是「细节」（配对状态 / 公网地址 / 局域网地址）。成功用绿色描边显示结论，失败用红色描边，细节统一列在下面。`PairStatus` 里能拿到的结构化事实只有 `paired` / `requirePairingForLan` / `publicUrl` / `lanAddresses` 四个字段，原型图里那行「version 0.9.4 · 4 个工作区 · 125 个会话」是示意，实现时没有凭空显示。

### D103 · 手工登记的两张卡只是视觉分组，状态提到 `PairScreen`

**决策**：`manualBaseUrl` / `manualDeviceId` 两个 `remember` 写在 `PairScreen` 里，经参数下发给 `ServerCard` / `DeviceIdCard`；两张卡自己不持有状态。

**理由**：这是单测写出来才暴露的缺陷。首版让每张卡自己 `remember { mutableStateOf(...) }`，`onManual(baseUrl, deviceId)` 从各自的闭包里取——结果地址卡拿不到设备 id、设备 id 卡拿不到地址，点「登记」永远缺一半。`PairScreenRenderTest` 的 `手工登记拆成两步且共用同一对值` 守这条：在设备 id 格 `performTextInput`，断言地址格的值没被改写、回调收到 `"717de5"`。

**教训**：拆卡是视觉决策，不能顺手把 state 一起拆下去；一个表单的字段只要在一次提交里同时用到，它的状态就必须有共同的所有者。

### D104 · 应用图标不要用 `painterResource(R.mipmap.ic_launcher)`（adaptive-icon 在 Robolectric 下必崩）

**决策**：抽屉头部 30dp 的应用标记改成自绘 `DrawerAppMark()`（`Box` + `Brush.linearGradient` + `Icon(Icons.Default.List)`），不引用任何 mipmap。

**理由**：R031 做的是 `<adaptive-icon>`（`mipmap-anydpi/ic_launcher.xml` 三层）。`painterResource` 读到 XML 时抛 `IllegalArgumentException: Only VectorDrawables and rasterized asset types are supported ex. PNG, JPG, WEBP`——**只在 Robolectric 里炸**，真机走 BitmapPainter 路径不炸。首版因此红掉 5 条抽屉渲染测试。

**替代方案（若日后真要在 UI 里放应用图标）**：只能引用位图（`mipmap-*dpi/ic_launcher.png`），不能用 `mipmap-anydpi` 的 XML。

## R033 审查后修复的决策

### D105 · 切到归档聚合视图时主动把 `LazyListState` 拉回顶部

**决策**：`SessionDrawer` 里在原有的 `LaunchedEffect(hasDrawerRows)` 之外，再挂一个 `LaunchedEffect(archivedOpen) { listState.requestScrollToItem(0) }`，进、出两个方向都回顶。归档视图与常规三段继续复用同一个 `listState`，不拆两个。

**理由**：审查 P1。归档入口固定在常规列表末尾——用户必须滚到底才能看到它、点它；切到归档视图后 item 从几十条骤减到个位数，`LazyColumn` 只能把 `firstVisibleItemIndex` 钳到末项，于是放在顶部（这是 R033 特意挪到顶部的）的「返回会话列表」落在了视口外。更糟的是 `archivedOpen == true` 时那个底部入口本身已不再渲染，屏幕上没有任何回去的路——**这是功能级死胡同，不是观感问题**。源码注释当时已经写明「返回入口必须在顶部，否则就是一个死胡同」，但实现只挪了按钮位置、没挪视口，注释与实现互相矛盾。

**为什么不拆两个 `LazyListState`**：拆开要重建列表、丢滚动位置，且两套状态在 `rememberSaveable` 下更容易出现「切回来位置不对」；把视口拉回顶部既符合用户预期（这是一次视图切换，不是列表内的导航），也只需要一行。

**代价**：从归档视图返回时列表回顶，用户会丢掉之前滚到一半的位置。这是有意的取舍——返回路径的可达性比「记住滚到哪」重要。

### D106 · 裸 token 能否配对取决于「本机有没有上次用过的地址」，预览结论必须与之一致

**决策**：`previewOf(parse, fallbackBaseUrl: String? = null)` 在 `PairLink.BareToken` 分支上判 `fallbackBaseUrl`：为空时 `ok = false` + 「还缺服务器地址」；非空时 `ok = true` + 「将用上次的地址 <host> 去配对」。「开始配对」按钮的启用判据仍是 `preview?.ok == true`，不额外加条件。

**理由**：审查 P2。`PairingCoordinator` 对 `BareToken` 是 `fallbackBaseUrl?.let(normalizeBaseUrl) ?: throw PairingException(...)`——全新安装、或刚 `unpair()` 之后，`PairViewModel.lastBaseUrl` 就是 null，此时按钮亮着、点下去必失败。而 `PairScreenRenderTest` 里那条用例名写的是「裸 token 会被认出来**但不能**直接配对」，断言却是 `assertTrue(preview.ok)`——测试名和行为互相打脸，说明当初就没想清楚这两种情形。

**为什么不在按钮上另加条件**：两处判据会分叉。让预览结论成为唯一真相来源，按钮只看 `ok`，就不会出现「卡说不行、按钮说行」的组合。

### D107 · 扫码的「已消费」闩用 `scanEpoch` 显式复位，而不是自动重开

**决策**：`ScanCard(enabled, scanEpoch, onRescan, onScanned)`；`scanEpoch` 变化时 `LaunchedEffect` 复位 `consumed`，并把 `AndroidView` 包进 `key(scanEpoch)` 重建底层控件。扫到一次后，若配对没成功（`consumed && enabled`），卡片上出现「重新扫描」按钮，点它才 `scanEpoch++`。

**理由**：审查 P2。`BarcodeView.decodeSingle(callback)` 本身是单发；原来的 `consumed` 只是把这个事实钉死在 Compose 侧。配对失败（token 过期、桌面端不可达）后界面停在扫码页，扫描线继续走、但再扫没有任何反应——用户唯一能自己摸索到的复位方式是切到「链接」再切回来，这不合理。

**为什么不做自动复位**（例如 `LaunchedEffect(enabled)` 在 `enabled` 变回 true 时自动清 `consumed`）：那样会在「配对请求刚失败、相机还在取景」的窗口里自动重开，用户可能没注意到卡片、而二维码还贴在镜头前，于是连着发第二次失败请求。显式按钮把「再试一次」变成一个用户动作。

**代价**：多一个 `scanEpoch` 参数穿透三层；重建控件会重新初始化相机（黑屏一瞬间）。

### D108 · 探测结果的颜色用 `LocalStatusRunning`，测试只守文案不守颜色

**决策**：`ProbeResultCard(probe.ok)` 的主题色改为 `LocalStatusRunning.current`（深色 `0xFF4ADE80` / 浅色 `0xFF15803D`），不再硬编码 `Color(0xFF4ADE80)`。相应地 `PairScreenRenderTest` 里那条原打算守「两张不同形态的卡」的用例改成守**文案不会串**，KDoc 里写清颜色差异只能靠设备验收。

**理由**：审查 P2 指出这是 R017 已经收掉的洞的重开——`Theme.kt` 里明确记录了「三处手写 `0xFF4ADE80` 在浅色下偏灰」。Robolectric 的语义树里拿不到 `Surface` 的实际填充色，硬要断言颜色只能靠像素级截图比对，成本远高于收益；把「颜色来自主题令牌」这件事交给代码审查与设备验收更诚实。

**顺带**：同一族的问题——`maskToken` 的阈值原来写 `<= 8` 整段打码，但真实 token 是 32 位，9~16 位时按首尾各 4 位只遮掉一两个字符，等于没遮。阈值改成 16，并在测试里钉住三个断点（8 位、16 位整段打码；17 位才露首尾各 4 位）。

## R035 第二份审查后修复的决策

### D109 · 归档聚合视图的会话必须 `distinctBy`，因为 `session/list` 会给出重复条目

**决策**：`SessionDrawer` 里 `archivedSessions` 的管道固定为 `items.filter { it.sessionId in archivedIds }.distinctBy { it.sessionId }.sortedByDescending { it.updatedAt }`，`distinctBy` 不能省。

**理由**：第二份审查 P1。`SessionListParser.summaries()` 只做 `mapNotNull`，`SessionListResult.items` 原样保留重复；`SessionGroupingTest` 里「recentSessions 对 sessionList 里的重复条目只保留一条」这条用例证明这个数据形态是真的会出现的，不是防御性编程。后果不是「多一行」——`items(key = "archived-${sessionId}")` 撞 key 抛 `IllegalArgumentException: Key "archived-X" was already used`，**LazyColumn 直接崩，整个抽屉打不开**。而抽屉是首页唯一的会话入口。

**为什么同一份数据只有这里漏了**：另外三条链（`recentSessions` 的 `distinctBy`、`group()` 的 `sessionIds.distinct()`、`pinnedSessions` 的 `associateBy`）都是 R003 之后被真实崩溃教过一遍才补上的；归档聚合视图是 R033 新写的第四条链，写的时候照着「过滤 + 排序」写，没有回头看那三条为什么长成那样。

**代价**：无。`distinctBy` 保留首次出现的那条，与 `recentSessions` 的语义一致。

### D110 · 探测结果自己带地址回显，而不是靠「改输入框就清卡」

**决策**：`PairProbe` 新增 `baseUrl: String`，`ProbeResultCard` 在结论行下面用等宽字体显示被探测的地址；同时 `probe()` 用 `probeJob` 保存并取消在途请求，`clearProbe()` 一并取消。

**理由**：审查 P2。原来的保护只有「用户改地址 → `clearProbe()` 清卡」这一层，它挡不住**在途请求**：地址 A 探测很慢、用户改成 B 又点了一次，A 的后到结论会覆盖 B 的，界面贴着一个 A 的绿卡待在 B 的输入框下面。`clearProbe()` 只清了「已经显示出来的」，清不掉「还在飞的那个」。

**为什么既取消又回显**：取消解决「结论错配」，回显解决「结论对不上号时用户能否自己看出来」。只做取消，一旦某次取消没生效（协程已进入不可取消的 `withContext` 阻塞段），界面就又回到「绿卡贴着没探过的地址」；回显让这种状态在界面上自证。两道保险各管一段，不是冗余。

**为什么不改成「探测时不显示旧卡」**——那是最省事的做法。但用户连点两次探测时，第一张卡消失、转一圈、结果回来，中间那段空白会让人以为点击没生效。

**代价**：`PairProbe` 多一个字段、卡片多一行；`probeJob` 需要配合 `catch (CancellationException) { throw e }`（见 D111）。

### D111 · 加了取消就必须在兜底 `catch` 之前重抛 `CancellationException`

**决策**：`PairViewModel.probe()` 的 `viewModelScope.launch` 里，`catch (e: PairingException)` 与 `catch (e: Exception)` 之间插一个 `catch (e: kotlinx.coroutines.CancellationException) { throw e }`。

**理由**：这是 D110 的直接后果，也是我这轮**自己引入又自己抓到**的缺陷。`catch (e: Exception)` 会接住 `CancellationException`（它继承 `Exception`），于是「取消」被写成一张红卡「连不上这个地址」——用户只是改了个输入框，界面自己报网络不通，而且无从解释。

**为什么没有单测**：`PairViewModel` 的构造依赖 `AppContainer`（内部建 `KeystoreCredentialStore`、`DshCache`），工程里没有为它建假容器的先例；为这一条引入一整套可注入依赖，成本高于收益。所以这里靠的是约定 + 代码审查，证据是工程里同款写法已经存在两处：`core/cache/DshCache.kt:243`、`core/events/RemoteEventsClient.kt:220`。

**代价**：无。这条是 `kotlinx.coroutines` 的通用约定，不是本工程的发明。

### D112 · 探测与配对共用一个 `busy` 是错的，拆成 `probing`

**决策**：`PairUiState` 新增 `probing: Boolean`，探测只置它；`busy` 只表示「正在配对/登记」。相应地 `ScanCard(enabled = !busy)` 不再被探测禁掉，`ServerCard` 的按钮文案在探测期间变「探测中…」。

**理由**：审查 P2。实测过：在「手工」入口点「探测地址」，整页顶部冒出「正在配对…」——用户以为登记已经提交了；同时扫码那一格的相机被无理由禁掉。三个入口本该互不干扰，共用一个状态位就把它们绑在一起了。

**代价**：状态多一个布尔；两处 `enabled` 判据要同时看两个字段（已有 KDoc 写明）。

### D113 · 抽屉里置顶/归档必须带 `stateDescription`，3dp 色条标 `clearAndSetSemantics`

**决策**：`DrawerSessionRow` 的 `Row` 挂 `.semantics { if (pinned) stateDescription = "已置顶" else if (archived) stateDescription = "已归档" }`；左侧 3dp 状态条挂 `.clearAndSetSemantics {}`。

**理由**：审查 P2。原实现只用「3dp 竖条颜色 + 标题透明度」表达状态：读屏用户听到的行和普通行一模一样，色弱用户在 3dp 窄条上分不清 `#5AA2FF` 与 `#F2C14E`。3dp 条本身不承载任何独立信息，留着语义只会被重复念一遍。

**代价**：每个置顶/归档行多一个语义节点属性；Robolectric 语义树里能断言，但 **uiautomator dump 不带 `state-desc` 字段**，所以设备验收时看不见它——只能靠单测守（`assertCountEquals(3)`：置顶段 1 + 两个工作区段 2）。

### D114 · 抽屉小字 alpha 按 AA 4.5:1 反推，不按「观感淡一点」

**决策**：分组标题 0.45 → 0.7、分组计数 0.3 → 0.55、归档行标题 0.5 → 0.62、行副标题 0.45 → 0.65。全部是 `onBackground` 的 alpha。

**理由**：审查 P2。浅色主题下 `background = #F4F7FB`、`onBackground = #182430`，按 WCAG 相对亮度公式折算：alpha 0.45 只有 ≈2.7:1、0.3 只有 ≈1.8:1，11sp 小字的 AA 下限是 4.5:1。强光下这几处基本看不见。

**为什么不是全部拉到 1.0**：层级靠对比度差表达是这套设计的既有语言（`DrawerSectionHeader` / 副标题 / 归档行本来就该「退后」）。0.7 / 0.55 / 0.62 / 0.65 是同一观感下能达标的下限。

**代价**：视觉上比原来「实」一些；没有做像素级对比度测量（见 `测试记录.md` T062-3）。

## R036 返工对齐原型 + 搜索会话的决策

### D115 · 搜索会话走客户端本地过滤，不调 `session/search`

**决策**：抽屉的搜索框自己实现 `searchSessions()`（`ui/home/SessionFilter.kt`），只匹配会话标题、工作区名、模型名；不调用 `session/search`。

**理由**：这个部署的会话全文索引是关着的。实测调用返回

```
gateway/internal: session search failed: SessionQueryError: session search is disabled:
this deployment configures the session-query index with openAt "never"
```

asar 里 `session-query-sqlite` 的注释解释得很清楚：全文搜索是 opt-in，`openAt: never` 时 `ctx.sessionQuery` 仍然挂着（精确读取、标题、血缘可用），但**每次搜索调用都失败**、SQLite 永远不打开；而且——这条最关键——**桌面端 Web 侧边栏的搜索也只匹配标题与工作区名**。

所以两条路：改桌面端配置（给 `session-query-sqlite` 加 `openAt: first-search` + 持久 `path`），或者做和桌面端一样的事。选后者，因为：

1. App 是桌面端的**客户端**，不是它的配置管理面。为了一个搜索框去改用户 `cordis.patch.yml`、还要建一个 SQLite 索引文件，代价与收益不成比例；
2. 本地过滤**零延迟**（数据已经在内存里）、**离线可用**（缓存数据也能搜）、**没有新的失败面**（不用处理索引未建好、索引损坏、索引与列表不一致）；
3. 用户的实际诉求是「我记得有这么个会话，标题大概是……」——这正是标题匹配能解决的。

**代价**：搜不到消息正文。这一点必须显式告诉用户，不能让他以为是 bug——所以在无结果时同时显示两句：命中的是什么（「没有会话名、工作区或模型匹配「R03」。」）和**不搜什么**（「这里只匹配会话标题、工作区名与模型名，不搜消息正文。」）。后一句是这条决策的界面契约。

**何时该重新考虑**：如果桌面端哪天默认打开全文索引（或用户在设置里开了），那 App 侧再换成 `session/search` 就是纯增量改动——`searchSessions` 的签名与 `SearchHit` 形状正好是那个 RPC 的返回形状（`{items:[{sessionId, snippet}]}` 的本地版）。

### D115b · 搜索必须排除子代理会话

（并入 D115 的同一节，这里单独成条是因为它是审查阶段抓到的，与「用不用 RPC」是两件事。）

**决策**：`searchSessions` 在 `distinctBy` 之前加 `.filterNot { it.isSubagent }`。

**理由**：`session/list` 实测 125 条里 **73 条** `origin == "subagent"`——这台机器跑过大量审查、探针、验收子会话，它们全都进了列表。抽屉的三段（置顶 / 最近 / 按工作区）都以 `topLevel` 或工作区 `sessionIds` 为骨架，天然不含它们；搜索却遍历 `sessions.items`，于是会给出「列表里根本没有的行」。

**代价**：用户在 App 里搜不到子代理会话。这是对的——它们在抽屉里本来就不可见，也没有「查看子代理」的入口。

### D120 · `httpFailure` 先看 JSON 里的 `code`，再看纯文本 body

**决策**：`PairingApi.httpFailure()` 在兜底分支之前插一条 `code != null -> refusalMessage(code)`，即「只要响应体是 JSON 且带 `code`，就用 `refusalMessage` 翻译」，纯文本 body 的判定（`forbidden` / `rate-limited` / `unauthorized`）保持在前面。

**理由**：设备验收时踩到——拿一个已被消费的 token 点「开始配对」，界面显示

```
HTTP 404: {"ok":false,"code":"invalid"}
```

一句用户不可能读懂的原始报文。根因是服务端对「token 未知 / 已过期 / 已停止」只回 `{ok:false,code:'invalid'}` 且**状态码是 404**，而 `httpFailure` 只特判了 `forbidden` / `rate-limited` / `unauthorized` 三种，其余全落到 `HTTP $status：${body}`。

**为什么要把 `code` 判定放在纯文本判定之后**：同一个 403 可能是 JSON（服务端 `{"code":"forbidden"}`，说明是 trustedHosts 问题）也可能是纯文本（反向代理或路由层的 `forbidden`，不能断定是 trustedHosts）。先判纯文本，能让前者保留「改桌面端 trustedHosts」这句指路牌，后者退成保守的「桌面端拒绝了此地址」。

**代价**：`refusalMessage` 的映射表成了用户可见文案的唯一出口，加新 code 时要同步改它——但那本来就是它的职责。

### D121 · 圆形徽标里的数字必须自己钉死行高 + `LineHeightStyle.Trim.Both`

**决策**：`Box(contentAlignment = Center)` 里放小字号 `Text` 时，必须用 `TextStyle` 显式给出 `fontSize`、与字号相同的 `lineHeight`，以及 `LineHeightStyle(alignment = Center, trim = Both)`。配对页的序号提成 `internal val StepNumberStyle` 作为这一模式的样板。

**理由**：`Box` 的 `contentAlignment` 居中的是**行框**，不是字形墨迹。只写 `fontSize = 9.5.sp` 时行高从主题 `bodyLarge` 继承成 24sp，24sp 行框里上升部与下降部的留白不对称，数字的重心落在圆心下方。1080×2400 / 480dpi 实测偏 **8px**（圆环中心 1475、墨迹中心 1483），肉眼一眼可见——用户就是这么发现的。

**为什么不能只在 `Text` 上传 `lineHeight`**：`Text` 的可选参数里有 `lineHeight`，但没有 `lineHeightStyle`（Compose 1.x 的 `Text` 签名里没有这个参数），而只压行高不裁两端行距，行框仍带着字体默认的上下留白，偏下会减轻但不消失。必须走 `style = TextStyle(...)`。

**为什么提成常量、并把 `StepList` 改成 `internal`**：这条缺陷**在 Robolectric 上测不出来**。实测把 `lineHeight` 设成 9.5sp / 12sp、`includeFontPadding` 开与关，四种组合的 `TextLayoutResult.getBoundingBox(0).center.y` 完全一样（`deltaFromBoxCenter` 恒 9.0）——Robolectric 没有真实字体度量，字形框是假的。所以「靠渲染层断言偏移量」这条路走不通；只能退一步断言**样式字段本身**（`fontSize` / `lineHeight` / `lineHeightStyle.alignment` / `.trim`），以此挡住「有人把它改回继承行高」。要断言这些字段，样式就必须是 `internal` 可见的常量，而不是内联在 private 组件的参数里。

**代价**：字号、行高、对齐策略三处要跟着改（改字号忘了改行高会重新引入偏差）。已在 `StepNumberStyle` 的 KDoc 里写清三者必须同进同退。

**这是可复用的判断**：任何「圆形/方形小容器 + 单个短字」的居中，都要问一句「我居中对象是行框还是墨迹」；字号越小、继承行高越大，偏差越明显。反例是正文段落——那里用行高换行距是刻意的，不能裁。

### D122 · 「未命名对话」是空会话，应该在列表层的入口处过滤，而不是改显示名

**决策**：`SessionListResult` 新增派生属性 `visible = items.filterNot { it.isSubagent || it.blank }`，`topLevel` 改为基于 `visible`；四条列表链（`group` / `recentSessions` / `pinnedSessions` / `searchSessions`）与归档聚合视图各自补 `blank` 过滤；`items` 本身不动。

**背景**：用户看到抽屉里一堆「未命名会话 xxxxxxxx」，点进去空白，桌面端却找不到它们。取证结果是 125 条里有 14 条 `blank = true`、`turns = 0`、`turnOutline` 为空、`lastPromptAt` 为 null——就是「建了但一句话没发过」的空会话。桌面端点「新建会话」会立刻建一个，关掉页签后侧栏不再显示它，但记录留在磁盘上。

**为什么不改显示名**（比如显示成「空会话」或直接隐藏标题）：显示名是 `title.ifBlank { "未命名会话 ${sessionId.takeLast(8)}" }`，它服务的是**所有**没有标题的会话，包括有内容但没命名的那种。把「空」这件事压进显示名，会让两个不同的事实（没起名 / 没内容）挤进同一个字符串，以后想区分就得再解析文案。

**为什么过滤放在 `SessionListResult` 而不是各 UI 调用点**：这次要改的地方是六处（三条分组链 + 搜索 + 归档视图 + 计数）。六处各自写 `filterNot { it.blank }` 意味着下次再有人加一条列表链，他很可能不知道要加——而漏掉一处的后果不是「少过滤一行」，是 `LazyColumn` 的 key 撞车直接崩（R033 的 `archived-` 链就踩过）。把「什么算可显示」收成一个名字（`visible`），新代码从 `visible` 出发就自动正确。

**为什么不动 `items`**：按 id 查单条会话仍要能在全量里找到——打开聊天页、`session/follow` 的摘要、`workspaceOf(sessionId)` 的归属查询都依赖全量。过滤只发生在「列表该显示什么」这一层，不是「这个会话不存在」。

**`group()` 里为什么是 `blank -> Unit` 而不是 `missing += id`**：`missing` 的语义是「`workspace.sessionIds` 里有这个 id，但 `session/list` 没给我这条摘要」，UI 上会挂一个红色的「读不到 N」。空会话是**读到了但不该显示**，记进 `missing` 会让每个含空会话的工作区头上多一个红色错误标记。设备验收专门核了这一点：工作区头没有红标。

**代价**：`visible` 每次访问都重新过滤一遍（`items` 最多百来条，可忽略）；六处调用点要记得用 `visible` 而不是 `items`——这一点只能靠 KDoc 和这次留下的注释约束。

**可复用的判断**：拿到的数据里出现「用户说找不到的东西」时，先分辨它是**坏数据**、**别人的数据**、还是**本来就不该显示的数据**。三者修法完全不同：坏数据要修来源，别人的数据要加归属校验，只有「不该显示」才在列表层过滤。这次是第三种。

### D123 · 「缓存故障不崩 UI」这个契约必须有一条真的走到外部依赖上的测试兜底

**决策**：凡是有「异常吞成 null、静默兜底」的层（`DshCache.guard` 是第一个），必须配一条**不使用替身、真的打开那个外部依赖**的测试；替身测试（假 DAO / mock）只用来测逻辑分支，不能用来证明配置正确。

**背景**：R039 给 `DshDatabase` 加 `CachedDraft` 实体（新表 `drafts`）时忘了把 `version` 从 1 提到 2。Room 打开库时比对 `room_master_table` 里的身份哈希，不一致就抛 `IllegalStateException: Room cannot verify the data integrity`；`version` 没变，`fallbackToDestructiveMigration` 不触发重建。而 `DshCache.guard` 按既定契约把这个异常吃成 `null`（「缓存故障不崩 UI」），于是失败**完全静默**：不崩溃、不打日志、输入框照常能打字，只是退出后一切归零。

**为什么单测全绿**：`DshCacheTest` 用手写 `FakeDao`（决策 D21：不引入 Robolectric 测 DAO）。假 DAO 是 `CacheDao` 接口的普通 Kotlin 类，**完全没有 Room 的 schema 校验逻辑**——它能证明「映射对不对」「兜底要不要生效」，但永远证明不了「库能不能打开」。`guard` 的静默兜底恰好把「库打不开」翻译成「没有缓存」，于是所有用例照样通过。

**修法**：`DshDatabase.version = 2`，并新增 `DshDatabaseSchemaTest`（`@RunWith(RobolectricTestRunner::class)`，真开文件数据库）：先正常建库写一条草稿 → `degradeToPreviousVersion()`（把 `user_version` 退一格 + 把身份哈希写成 `stale-hash-from-old-schema`，正是「加了实体忘了改 version」在设备上的样子）→ 再打开，断言能重建且新表可用。

**为什么这个测试必须自己退化库**：Robolectric 每个用例都是全新的空目录，正常路径永远是「首次创建」——直接开两次库都成功，什么也证明不了。只有手工把库改成「旧代码建出来的样子」，才能复现真实升级路径。

**可复用的判断**：一条**静默兜底**（catch → null / 降级 / 空集合）在把错误变安静的同时，也把「配置写错了」伪装成「这个功能我没做」。区分这两者的成本，等于「有没有一条测试真的走到那个依赖上」。凡是新加兜底，问一句：**如果这个依赖整个坏掉，我靠什么知道？** 答案不能是「用户会告诉我」。

**代价**：`DshDatabaseSchemaTest` 需要 Robolectric（工程已有依赖，`@Config(sdk = [36])`），单条用例约 1–2 秒；它只守 schema 版本这一件事，不影响其它 DAO 测试继续用假 DAO。

### D124 · 会话列表的增量事件必须走「窄口」写缓存，绝不能复用全量替换路径

**决策**：`$events` 推来的 `api-session/added` / `status` / `removed` 落缓存时，走 `DshCache.upsertSession` / `deleteSession`（只动目标那一行，不删孤儿），**不经过** `writeSessions` → `replaceSessions`。

**背景**：审查 P1。`applySessions(items)` 原先无条件 `store.writeSessions(ownerId, items)`，而 `writeSessions` → `replaceSessions` 是「`deleteSessions` 全删 + 全量插入 + `deleteOrphanMessages` + `deleteOrphanDrafts`」的破坏性替换。增量路径传进去的 `items` 是**内存里当前那份列表**，冷启动时它可能只有一条（`session/list` 还没回来）——于是这一条增量会把磁盘上其它所有会话连同它们的消息缓存与草稿**一起删掉**。

**为什么这条特别危险**：它不是「多删一行」。`deleteOrphanDrafts` 会把 `sessions` 表里已不存在的 sessionId 的草稿一并清掉，而草稿正是同一轮 R039 刚做的功能（用户 m17042 第 2 条）。两个缺陷叠在一起时表现是「草稿功能完全没生效」，排查方向会全部错在草稿代码上。

**为什么不在 `applySessions` 里加 `persist: Boolean` 开关**：开关靠调用方自觉，下一个人加第三条增量链时多半不会想起来传 `false`。窄口 API（`upsertSession` / `deleteSession`）让「只改这一行」成为默认，写错要显式写错。

**代价**：`DshCache` 多两个方法；`applySessions` 按事件类型分流（`Added` 走 upsert、`Removed` 走 delete、`Status` 走 upsert 更新后的那一条）。

### D125 · 通知总线不能用 `StateFlow`，因为它是「事件」不是「状态」

**决策**：`RemoteEventsClient` 的会话转发事件用 `Channel<SessionNotification>(capacity = 64, onBufferOverflow = DROP_OLDEST)` + `receiveAsFlow()`，不用 `MutableStateFlow`。

**背景**：审查 P1。`MutableStateFlow` 是**合流（conflate）**语义，只保证「订阅者最终看到最后一个值」。同一会话的 `api-session/added` 紧跟 `api-session/status` 时，两帧之间收集方还没有恢复，`added` 就被 `status` 覆盖掉了。而 `status` 走 `patchRunning`，对未知会话**必须原样返回**（凭一条 status 造不出完整摘要）——于是这条会话永远不会出现在列表里，正是用户报的「桌面端新建会话后 App 不出现」。

**为什么 `patchRunning` 不能顺手补一条假摘要**：`status` 帧只带 `[sessionId, running]`，没有 title、没有 updatedAt、没有工作区归属。凭空造出来的行会显示成空白标题 + `1970`，比不显示更糟。

**为什么用 `Channel` 而不是 `SharedFlow(extraBufferCapacity=…)`**：`handle()` 不是 `suspend` 函数（它跑在收帧线程上），只能用 `tryEmit`/`trySend`。`SharedFlow` 在缓冲区满时 `tryEmit` 返回 false，**静默丢弃**——这又回到了折叠问题。`Channel` 配 `DROP_OLDEST` 的丢法是确定的：丢最老的一条，而最新的状态变更总能留下，且 `activity`（会触发全量重读）永远在数组尾部。

**为什么 capacity 是 64**：单个摘要最大约 14KB（1 781 676 B / 125 条约等于此）。64 条 ≈ 900KB 上限，远小于一次 `session/list` 的响应体；再大就没有意义，因为 `activity` 本身会触发全量重读兜底。

**代价**：单消费者（`HomeViewModel` 独占）。若将来第二个订阅者出现，`receiveAsFlow()` 会把事件分流而不是广播——那时应换成带 `replay` 的 `SharedFlow` 并重新论证缓冲策略，不能让两个消费者抢同一条流。

### D126 · 会话详情的上下文数据必须维护「累加器 + 增量帧 + 全量读」三条路，且全量读是权威快照

**背景**：侧栏要画七段圆环、堆叠条、费用与耗时，这些数字来自六个投影键（`contextTimeline` / `contextBreakdown` / `contextTokenUsage` / `costUsage` / `contextPressure` / `sessionStats`）。它们在 `session/control` 里是**逐个增量**到达的，每个帧只有一个 key。

**决策**：ViewModel 里维护一个只含这六个键的 `contextValues` 累加器，两条写入路径：
1. **增量帧**（`applyContextProjection`）：走 `mergeContextValue`，`null` 表示「这个键没了」；
2. **全量读**（`refreshContext`，打开侧栏时一次 + 生成中 3s 轮询）：走 `rebuildContextValues`，**从空重建**。

**理由**：服务端对「键不再存在」的表达方式是**缺席**，不是 null。全量读若合并进旧累加器，插件在运行期被卸载时旧值会永远留着，`ContextDetailLevel` 停在 `DETAILED`，侧栏显示早已不存在的数据（R040 审查 P1）。反过来，增量帧不能重建，因为一帧只有一个键，重建会把其余五个键抹掉。

**附带决定**：只存这六个键，**绝不**把 `contextHeaders`（实测 70 KB）之类塞进累加器——否则一次长会话能把这个常驻对象涨到几 MB。`rebuildContextValues` 的白名单同时也是这条约束的执行点。

**代价**：档位只在这六个键齐了之后才升到 `DETAILED`，所以打开侧栏到数字出现之间有一次 RTT（160–266 ms）。

### D127 · 刷新在飞期间的增量帧必须攒起来补放，不能丢弃

`refreshContext` 有重入守卫（`contextJob?.isActive`），刷新期间到达的 `session/control` 帧原先是直接 `return` 掉。问题在于 `session/control` 只在**变更时**推帧、丢了不会重发：全量读的快照在请求发出时就已生成，回包前到达的那一帧比快照**更新**却永久丢失，侧栏要等下一次变更才追上（R040 审查 P2）。

**决策**：攒进 `pendingContext`，全量读落地时 `replayPendingContext` 盖到快照上再清空；读失败时也清空（否则下一次成功会用上更旧的帧）。

**为什么不做「帧到了就取消全量读」**：那样每次生成中都会被帧打断，3s 轮询永远跑不完；而且全量读是**自愈**手段（增量流断过一次就靠它补回来）——两者是互补关系，不是竞争关系。

**代价**：`pendingContext` 只在主线程读写（`viewModelScope` 默认 `Main.immediate`），没有加锁；将来若把这段挪到别的 dispatcher，必须换成并发容器。

### D128 · HTML 预览用假域名 + `shouldInterceptRequest`，且必须拒绝盘符绝对路径

**背景**：工作区文件只存在于桌面端，要经 `workspaceFiles/readBytes` 一个文件一个文件地取；没有可用的 `file://` 或 `content://` 地址。而原型 HTML 常引用同目录资源（`<img src="R031-app-icon.png">`），`loadDataWithBaseURL(null, …)` 下这些相对路径无处可去。

**决策**：给页面挂假域名 `https://dsh-file.local/`，把文件所在目录拼在它后面当 baseUrl；`shouldInterceptRequest` 把落在这个域名下的请求翻译回工作区相对路径去取字节；非该域名一律返回空响应并提示。

**理由**：假域名是唯一能同时满足三件事的写法——相对路径能解析、资源读取可拦截、外链可一刀切拦住。用 `file://` 会放开本地文件访问；用 `content://` 需要逐文件建 provider（工作区文件是虚拟的，没有真实 fd）。

**安全约束（R040 审查 P2-2 补的）**：`htmlAssetPath` 在 `normalizeRelative` 之后必须再拒绝盘符前缀。服务端的工作区层认 Windows 绝对路径，页面里一句 `<img src="/C:/Users/x/.dsh/.credentials.yaml">` 就能把工作区之外的文件读进预览，而这个 WebView **JS 是开着的**（用户要求）。

**为什么不禁 JS**：用户 m21945 明确要 JS 常开，原型 HTML 靠它做交互演示。所以只能在**读路径**上收口。

**代价**：`readHtmlAsset` 必须 `runBlocking`（`shouldInterceptRequest` 是同步 API），每个资源最多阻塞 3s；桌面端掉线时靠超时兜底，不让加载线程被永久挂住。

## D91 · 跨分支存活的 UI 状态按「所属实体」复位，不按「App 生命周期」

**背景**：R041 把侧栏的三个状态（开合 / 页签 / 目录）从 `ChatScreen` 的 `remember`
提到 `AppRoot` 的 `rememberSaveable`，因为「侧栏点文件 → 跳文件页 → 返回」会让聊天分支
整个离开组合，本地 `remember` 全丢、侧栏被关（用户 m24881 第 ③ 条）。

**问题**：提升之后它们跨会话存活了。从会话 A 的「文件」页签下钻到 `docs/dev`，返回首页
再进会话 B，B 的侧栏一打开就停在 A 的目录上；B 的 cwd 往往没有 `docs`，列出来是空的，
用户看到的是「文件页签坏了」——一个比原 bug 更隐蔽的状态污染。

**决策**：状态提升到共同祖先之后，必须同时明确它的**归属实体**，并在「离开该实体」的
每一处复位。侧栏的归属是「某个会话的一次查看」，不是「这个 App 的一次查看」，所以在
`onOpenSession` / `onBack` / 会话级 `BackHandler` 三处调 `resetSidebar()`。

**判据**：问「这个状态在换掉 X 之后还有意义吗」，X 是它描述的那个对象。侧栏目录换会话
后无意义（cwd 变了）→ 复位；消息滚动位置换会话后也无意义 → 同样不该跨会话。

**教训**：`remember` → `rememberSaveable` 提升不是纯粹的「让状态活得更久」，它同时扩大了
状态的适用范围；不跟着划定边界，就是把局部状态变成了全局污染。这一条与 D86（互斥展开用
枚举而不是两个布尔）同族：**状态的形状要能表达它的边界**。

## D92 · 显示用的百分比按「渲染后的值」判档，不按原始值

**背景**：窗口构成图例要把七段占比渲染成百分比。`formatPercent` 首版按原始值分档：
`>= 10f` 整数档、`>= 1f` 一位小数、其余两位小数。

**问题**：9.99% 落在一位小数档、渲染成 `10.0%`；而 10% 落在整数档、渲染成 `10%`。
同一个数字出现两种写法，读者会以为是两个不同的值。单测
`percentBoundariesSwitchPrecision` 第一次跑就红。

**决策**：三档只决定**精度**，渲染完再去掉多余的小数零（`10.0` → `10`、`1.00` → `1`、
`6.40` → `6.4`）。这样档位切换处不会产生视觉跳变，也不会有一个数字两种形态。

**为什么不去调阈值**：把 10f 改成 9.999f 只是把抖动挪到另一个数字上，任何固定阈值都有
一个「刚好跨过去」的邻域。去尾零是从表示层消除差异，与阈值位置无关。

**教训**：格式化的正确性不是「算得对」，而是「同一个值在所有档位上长得一样」。同类断言
应该写成 `assertEquals(formatPercent(a), formatPercent(b))` 这种**双值互等**，而不是
只断言某一个值的字面串——后者换个阈值也绿。
## D93 · 缓存的失效交给事件，不交给「打开动作」

**背景**：R042 用户要求文件页签加缓存（进子目录、看完文件退回都不该再转圈），同时问「有没有更新
文件的事情可监听」。

**问题**：加缓存最容易顺手写成「每次打开都重新拉一次，但先把缓存显示出来」。这看起来兼顾了
速度与新鲜度，实际是**用一次网络请求换一次不转圈**——用户抱怨的是「每次都要等」，不是「看不到
转圈」，代价没省掉。

**决策**：缓存命中就**不发请求**。新鲜度由两条路保证：`workspaceFiles/changes` 的流式监听（变化时
自动重拉），以及用户主动的刷新按钮 / 下拉刷新。

**为什么不是「打开即刷新」**：文件页签是常驻侧栏，用户来回切换页签的频率远高于目录真的变化。
按打开动作刷新，等于把「变化」和「打开」当成同一件事，而它们无关。

**教训**：缓存的第一问不是「存多久」，是「什么事件让它失效」。答不上来就别急着加缓存——那只是
把延迟藏起来。

## D94 · 流式监听不可用时的降级要静默，但必须留下手动出口

**背景**：`workspaceFiles/changes` 在后端 `fs.watch` 不可用时抛 `workspace-file/watch-unsupported`。

**决策**：`watchCurrentDirectory()` 的 `catch` 里**不弹错误、不设 `filesError`**，直接放弃监听；同时
刷新按钮常驻、下拉刷新可用。

**为什么静默**：监听是**增强**不是**功能**——它失败时用户仍然能正常浏览文件，弹一条「实时更新不可用」
只会让一个本来没问题的界面显示成故障。这与 R038 的 `blank` 会话过滤同一条原则：**不要把内部
降级说成用户可见的错误**。

**为什么必须留手动出口**：静默的前提是「不静默也能自救」。如果监听失败又不给刷新，用户就只能
关掉侧栏重开——那正是 R042 要消灭的动作。**静默降级必须伴随一个仍然可用的手动路径，否则就是
把故障藏起来。**

**教训**：判断一个降级该不该提示，看它有没有替代路径。有替代路径的降级应当静默；没有替代路径的
降级必须显式报错，因为用户除此之外无能为力。
## D95 · 轮次结局只在「不正常」时落卡，正常结束不产条目

`turn/end` 的 `reason.kind == completed` 占 466/646，若也落卡，每条会话会多出几十行「第 N 轮结束」
噪声。反过来若全都不落，错误原文就永远看不见（这正是 R043 之前的状态）。
所以判据是「`outcome is Completed` → 不产条目」，其余六种结局都产 `ChatItem.TurnResult`。

## D96 · 重试按钮由 `error.code` 决定给不给，不看「有没有失败」

`QUOTA_EXCEEDED` / `MISSING_CREDENTIAL` / `AUTH` / `NO_ADAPTER` / `HTTP_413` / `CLIENT_ERROR`
这六类重试必然同样失败。给一个点了还是失败的按钮，比不给更糟——用户会以为「再试一次也许行」，
而真正要做的是去桌面端处理额度/登录/换模型。所以 `NON_RETRYABLE_CODES` 里的一律不渲染主按钮，
hint 直接说「重试解决不了，需要在桌面端处理」。

## D97 · 命令一律落进输入框，不提供「选中即执行」

桌面端的行为也是「选中命令 → 落进编辑器 → 用户回车」。App 若做成选中即发，会把「点错命令」
变成一次不可撤回的服务端调用（`/export` 这类有副作用）。代价是少一次点击，换的是可撤回。

## D98 · `@path` 引用拼在正文末尾，不新增协议字段

`session/prompt` 只吃 `text` + `attachments`，没有「附带引用列表」这种参数；桌面端的 `@`
是在编辑器里当文本处理的。所以 App 侧同样拼成文本。副作用是用户手打同名 `@` 会重复，
但服务端会把两处都当引用，重复不影响语义（见 R043 审查「判为不改」第 1 条）。

## D99 · 结局卡的错误原文默认折 3 行但不删

上游 `error.message` 动辄几百字符（`RATE_LIMIT` 的原文里带完整 response body）。全展开会把
一屏消息挤走，全折叠又等于没显示。取 `COLLAPSED_ERROR_LINES = 3` + 点击展开 + 「展开全文」按钮，
并在卡片上保留「复制」——排查问题时用户要的是能拷走这段原文。

## D100 · `TurnResult` 参与折叠的 `independent` 判定

`foldChatItems` 会把「同一条助手消息里的工具卡」折进一个分组。结局卡若也折进去，用户要展开
两三层才看见「这轮为什么失败」。所以 `TurnResult` 与 `ChatItem.Notice` 一样自成一列。
