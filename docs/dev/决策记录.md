## D11 · 改动文件卡片：推断 + 权威摘要，两条路都做（Q10）

**日期**：2026-10-13 · **状态**：已接受（用户 m00811「接受建议」）

**决策**：
- **路 A（实时推断）**：解析 `tool/call` 的 `name ∈ {write, edit, str_replace_editor}` 与 `arguments`（**是 JSON 字符串**）取出 `file_path`，渲染可点文件行。
- **路 B（权威摘要）**：出现 `workspace/changes` 事件时，用其 `seq` 调 `GET /remote/api/changes.summary?sessionId=&seq=` 拿 `+added/-deleted` 权威统计。

**理由**：摘要只活在**同一 Host 进程内的会话**生命周期里，Host 重启后旧轮次返回 404；只做路 B 会空白。反之只做路 A 会丢行数统计。

**限制（必须写进 UI 文案）**：
1. Host 重启后旧轮次没有卡片与 diff（404）→ 降级为路 A。
2. 非 git 仓库里，纯 shell 命令改的文件不会出现在卡片里（只统计文件工具改动）。

## D17 · 传输层不依赖 `/remote` 之外的前缀

**日期**：2026-10-13 · **状态**：已接受（自主决策）

**决策**：所有业务请求统一走 `/remote/api/<namespace>/<method>`，WebSocket 走 `/remote/api/remote.mux?device=<id>`。

**理由**：插件 `/remote` 通道是唯一的**无 cookie** 入口，且它把请求以进程自身凭证重新签发到 `127.0.0.1`。直接打 `/api` 会被 harness 的 Host 围栏 + 浏览器 cookie 拦成 401（已实测：`POST /api/session.list` → `401 unauthorized`）。

## D18 · 依赖版本按 AAR 的 `minCompileSdk` 实测选定，不取 latest

**日期**：2026-10-13 · **状态**：已接受（自主决策）

**决策**：`gradle/libs.versions.toml` 里的版本以**实测的兼容矩阵**为准，锁定在 compileSdk 36 / AGP 8.13.2 可用的上限，而不是 maven 上的 latest。

**采用值**：AGP 8.13.2 / Gradle 8.13 / Kotlin 2.2.21 / core-ktx 1.18.0 / lifecycle 2.10.0 / activity-compose 1.13.0 / compose-bom 2026.06.01（ui 1.11.4、material3 1.4.0）/ okhttp 5.4.0 / kotlinx-serialization-json 1.9.0 / coroutines 1.10.2。

## D21 · 不引入 Robolectric，Room 用假 DAO 做 JVM 单测

**日期**：2026-10-14 · **状态**：已接受（自主决策）

**决策**：M4 引入 Room 后，**不引入 Robolectric**，也不为单元测试开 `unitTests.isIncludeAndroidResources`。
Room 的测试策略改为：`CacheMappers` 是纯函数（直接测）；`DshCache` 的 DAO 依赖用**手写假 DAO**（一个实现 `CacheDao` 接口的普通 Kotlin 类，把行存在内存 `MutableList` 里）注入；真实的 SQLite 建库、DDL、事务、WAL 行为**靠模拟器手工验收**。

**理由**：
1. Robolectric 会在测试期拉 `android-all` 系列 jar，本工程的构建约定是 `--offline`（D19 把缓存放 F 盘，离线是常态）——一个测试依赖需要联网下载会破坏这条约定。
2. 需要 `unitTests.isIncludeAndroidResources = true` 与额外的 `testOptions`，会拖慢所有单测。
3. 真正需要验证的**业务语义**（整体替换而非累积、ownerId 隔离、`trimMessages` 裁剪、磁盘故障退化成 null、`CancellationException` 原样上抛）**全部落在 `DshCache` 这层编排逻辑上**，与 SQLite 本身无关；而 SQLite 的 DDL/事务正确性由 Room 编译器与模拟器验收覆盖。

**代价**：单测**不覆盖**真实 SQL 语句、外键与事务边界；`CacheDao` 的注解若有误，编译期能发现（KSP 会报错），但运行期的约束冲突只能在模拟器上暴露。
已用 `dsh-cache.db` + `-wal` 的实际落盘与诊断页读数（T021）作为代偿证据。

**记录**：`测试记录.md` T021；本决策与 D04（离线缓存：做）配套。

## D22 · 缓存库不落 deviceId 原文，用指纹作分区键

**日期**：2026-10-14 · **状态**：已接受（自主决策）

**决策**：本地缓存库（`dsh-cache.db`）的所有表主键都包含 `ownerId`，而 `ownerId = SHA-256(baseUrl + '\u0000' + deviceId)` 的前 8 字节十六进制。**不**把 `deviceId` 明文写进 SQLite。

**理由**：「已配对设备 = FULL-CONTROL 凭证」（`remote-api.ts:1-27` 的机制：插件用进程自身的浏览器鉴权 cookie 代发请求）。而 `dsh-cache.db` 是**明文 SQLite**，落在 App 私有目录但可被 root / 备份 / `run-as` 读出。凭证本身已经由 Keystore AES-GCM 加密保管（D16），缓存库不该成为第二个更容易读的泄露点。

**代价**：诊断页里 `ownerId` 显示为一串 16 位十六进制（`ea79c5642ad8aa2f`），排查问题时无法直接对上桌面的设备列表——**这是有意的**，需要对照时用「设备 id 打码」（`204a48…7ea2`）即可。重新配对会产生新的 `ownerId`，旧缓存行自然不匹配（换设备语义），另由 `pruneOtherOwners` 清理。

**记录**：`core/cache/CacheMappers.kt` 的 `ownerIdOf`；`测试记录.md` T021。

## D23 · 缓存只缓存「已确认」的事件，不缓存 assistant-stream 帧

**日期**：2026-10-14 · **状态**：已接受（自主决策）

**决策**：`ChatViewModel.persist(envelopes)` 只落库**事件信封**（`session/follow` 的 `event` 帧 / 快照里的 `records`），**瞬时 `assistant-stream` 帧不缓存**。

**理由**：`assistant-stream` 的 `chunk` 是**未提交**的增量猜测——官方的权威性只在 `end` 帧的 `outcome.kind == 'committed'` 时才成立（未提交即 `abandoned`）。若把半成品落库，下次冷启动会把一段从未被服务端确认过的文本当成历史渲染出来，而重连后权威快照一到达又把它抹掉，用户会看到「消息闪一下又变了」。
冷启动时若已有事件落库，`ChatReducer` 会按同样的规则从事件重建，流式部分自然从「没有 live 帧」的干净状态开始。

**代价**：断线瞬间正在流式输出的最后半句话**不会**出现在离线缓存里（这是正确的——它本来就不确定会不会被提交）。

**记录**：`ChatViewModel.kt` 的 `persist`；`测试记录.md` T021。

## D24 · 展示路径与查询路径分成两个字段，且 KDoc 必须写明「不得用于查询」

**日期**：2026-10-14 · **状态**：已接受（自主决策，源自 R006 P1-5 与 R005 P1-A 的同一根因复发）

**决策**：凡是「给用户看」的路径字符串与「拿去查」的路径字符串，**必须是两个不同名字的字段**，且展示字段的 KDoc 必须显式写「仅用于显示，不得用于查询或作为 key」。

**理由**：这个坑在本工程**连续两次**出现，换了调用点、换了层：

- R005 P1-A（M3.5）：改动文件卡片把 `display`（桌面端裁短的展示路径）当 `path` 传给 `FileTarget` → `indexOfFirst { it.path == path }` 恒为 -1 → `hasDiff = false`，本轮 diff 与「在电脑上打开」入口一起丢失。
- R006 P1-5（M4）：同一个 `display` / `path` 混淆在**另一个**调用点重演。

两次都不是「写错一行」，而是**两个字段长得很像、语义不同，而类型系统完全无法区分**（都是 `String`）。只靠「下次小心」没用——事实已经证明它会在新代码里再犯。

**代价**：字段数略增；每次新增路径字段都要多想一步「这个字段会被拿去查吗」。

**记录**：`代码审查记录.md` R005 P1-A / R006 P1-5；`core/changes/ChangesModel.kt` 与 `ui/chat/ChatCards.kt`。

## D25 · 状态一律由 reducer 单一真相源推导，禁止私有台账

**日期**：2026-10-14 · **状态**：已接受（自主决策，源自 R006 P1-4 与 M3 冷启动的同一根因）

**决策**：`ChatUiState` / `HomeUiState` 里任何「待办/已请求」集合，**只允许从 `StateFlow` 的当前值推导**，不得在 ViewModel 里另存一份私有 Set/Map 台账。

**理由**：同一个根因在本工程出现第三次：

- M3 冷启动空列表：`WorkspaceRepository` 的 `.scan(WorkspaceSnapshot())` 种子在 reducer 之外产生了第二份状态。
- R005 P1-B：`requestedChanges` 私有 Set 与快照裁剪不同步 → 重连后卡片永久空白。
- R006 P1-4：同一处台账在 M4 的接线里再次漂移。

三次的共同形状：**状态有两个表示方式，它们必然漂移，而漂移方向总是「旧的覆盖新的」**（`distinctBy` 保首、`.copy` 覆盖、裁剪只裁一边）。

**代价**：推导式代码比直接查台账略绕；有时需要把「谁在加载中」这种信息显式搬进 state（R006 正是这么修 `changesLoading` 的）。

## D26 · 去重标记与被去重的副作用必须是同一批操作

**日期**：2026-10-14 · **状态**：已接受（自主决策，源自 R006 P1-1）

## D27 · 重入守卫必须放在它声称要保护的那批操作之前，且必须覆盖全部入口

**日期**：2026-10-14 · **状态**：已接受（自主决策，源自 R007 P1-2）

## D31 · 屏幕级 VM 的 key 必须包含它所绑定的连接身份，不能只用业务 id

**日期**：2026-10-14 · **状态**：已接受（源自 R007 后续的设备验收缺陷 A）

**决策**：`viewModel(key = ...)` 的 key 除了业务 id（sessionId），
**还必须包含该 VM 所绑定连接的身份**（这里是 `credential.deviceId`）。

**理由**：`rememberScopedViewModelStoreOwner()` 只保证「离开组合时 clear store」，
但 owner 是 `remember` 在 `when` 分支里的。当解绑与重连发生在**同一帧**、分支没有离开组合时，
旧 store 会被原样交回来，里面的 VM 绑定着**已关闭的旧连接**，`viewModelScope` 已取消，
`state` / `carrier` 两个 StateFlow 冻结——界面停在旧错误上，且**冷启动才好**，
现场完全看不出是客户端缺陷（首页已连接、诊断页已建立连接、别的会话完全正常）。

只带 `sessionId` 的 key 在这里不够：deviceId 变了而 sessionId 没变，命中的却是旧 VM。
把 deviceId 拼进 key 之后，重连必然拿到新 VM，旧 store 里的死 VM 随 owner 一起被 clear。

**代价**：key 变长；重连后同一会话的 VM 确实是全新的（上一会话的 live 预览、generating 状态丢失）——
但这正是期望语义，因为旧 VM 的协程已经死了，留着它只会显示冻结状态。

## D32 · 「服务端会 append 到会话日志」的字段必须同时接实时事件，不能只读快照投影

**日期**：2026-10-14 · **状态**：已接受（源自用户验收反馈 T4）

**决策**：`ChatUiState` 里由**快照投影**填充的字段（当前是 `model`），必须在

## D36 · 服务端不回执的状态，客户端必须做本地回声；回声只能挂在独立的、无 seq 的槽位

**日期**：2026-10-14 · **状态**：已接受（源自用户 m20380 反馈）

**决策**：当一次用户操作在服务端**没有可查询的回执**时，客户端必须自己做本地回声（optimistic echo），
且回声只能放进**独立的、没有 `seq` 的槽位**，绝不与权威列表混存。

**理由**：用户发现一条早前打进 App 的消息在会话生成时「没有任何反应」，直到当前轮结束才被执行。
根因是 `session/prompt` 的结果**只有 `{accepted: true}`**（`typert.host.js:803-805`），
`session/follow` 快照投影里**没有任何 queue 投影**（`typert.remote-client.js:222-341` 逐行读完），
SDK 的 `pendingSubmissions` 只是进程内客户端的本地回声（`client.js:1684-1707`）。
**走 wire 的远程客户端对「我的消息排到第几、能不能撤」一无所知。**

两条子决策：

1. **不做「撤回」按钮**。`session/updateQueue` 必须要 `itemId`（`typert.host.js:843-862`），
   而 itemId 在 prompt 返回值、快照投影、事件里**都拿不到** → 对纯远程客户端实际不可用。
   一个撤不掉的撤回按钮比不做更糟。
2. **回声绝不进 `state.items`、绝不进 Room**。它没有 `seq`，而 `ChatScreen` 用
   `key = { it.seq }` 渲染 `LazyColumn`，假 seq 会抛 `Key was already used`；
   同时会污染 `session/page` 的游标语义与 `distinctBy{seq}` 合并且逻辑。进 Room 则会让它
   在冷启动后复活——而服务端队列与本地状态无关，那时它本该消失。

**回声的生命周期由两个事件驱动**：`turn/start` 清空全部（服务端开始出队 = 队列已腾空），
`user/message` 摘掉最老一条（FIFO 对上）。**`when` 分支里 `turn/start` 必须排在 `item == null` 之前**——
轮次事件不占行、`item` 恒为 null，顺序写反这条分支永远走不到（首跑测试即此错）。

**代价**：多一个 `ChatUiState.queued` 字段与两条 reducer 分支；RPC 失败时要显式摘掉回声
（否则是一条永不被换掉的幽灵气泡），而 `CancellationException` 分支不能摘（服务端可能已收下）。

**记录**：`core/session/ChatModel.kt`（`QueuedMessage`）、`core/session/ChatReducer.kt`、
`ui/chat/ChatViewModel.kt`（`queuedEchoSeq`）、`ui/chat/ChatScreen.kt`（`QueuedRow`）；
`ChatReducerTest` 45→52、`QueuedRowRenderTest`（新，4 项）；`docs/dev/测试记录.md` T034。
