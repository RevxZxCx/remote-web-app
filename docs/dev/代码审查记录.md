### 发现与修复

**P1-1 · WebSocket 握手 403 未映射为 `unpaired`，未配对引导永远不可达**
插件对未配对/已撤销设备的 WS 升级回裸 `HTTP/1.1 403 Forbidden`（`src/remote-api.ts:226-243`），OkHttp 只抛 `ProtocolException("Expected HTTP 101 response but was '403 Forbidden'")`——没有 code。而 `HomeViewModel.retryWhen` 只认 `TypertException.isUnpaired`，于是设备被撤销后界面永远停在「重连中…」。M1 唯一在跑的数据通道就是这条 mux，所以 `开发流程.md` 要求的 403 引导实际不可达。
**修复**：`RemoteStreamMux.onFailure` 不再丢弃 `response`，新增 `handshakeFailure(t, response)` 按状态码补出 `TypertException`（403→`CODE_UNPAIRED`、401→`CODE_FORBIDDEN_UNAUTH`、其他→`CODE_TRANSPORT`）。

**P1-2 · 每次重连先发空快照，把工作区列表清空**
`WorkspaceRepository.snapshotFlow` 的 `.onStart { emit(WorkspaceSnapshot()) }` 位于 `retryWhen` 上游，重试重新订阅时会再发一次空快照，`collect` 把它写进 `_state.snapshot`，于是每次断线重连都清空列表并短暂显示「这个桌面端还没有工作区。」，违反「重连不清空 UI」。
**修复**：删掉该 `onStart`，首帧空快照的职责交给 `HomeUiState.snapshot` 的默认值。

**P1-3 · 「探测地址」未规范化且只捕获 `PairingException`，手输 `192.168.1.5:19387` 会崩**
`PairViewModel.probe()` 把原始输入直接交给 OkHttp，`Request.Builder().url()` 对无 scheme 的输入抛 `IllegalArgumentException`，而只 catch 了 `PairingException` → 异常逃出 `viewModelScope.launch` → 进程崩溃。手动模式里「探测地址」和「登记」共用一个输入框，后者能用、前者崩。同时探测也会向非私有地址发明文请求，绕过了 HostPolicy。
**修复**：`probe()` 先 `normalizeBaseUrl` + `HostPolicy.rejectionReason` 校验（发请求之前），捕获放宽到 `Exception` 兜底。

**P2-1 · 旋转屏幕后工作区流被静默掐断，页面停在旧数据**
配置变更重建 Activity 时 `LaunchedEffect(Unit)` 再跑一次 `bootstrap()` → `installConnection` 关掉旧 mux 建新连接，但 `viewModel(key="home-<deviceId>")` 拿到的是被保留的旧 ViewModel，仍持有已关闭的连接。`RemoteStreamMux.close()` 不带 cause，callbackFlow 正常完成 → 既不报错也不触发 `retryWhen`。
**修复**：`installConnection` 在凭证未变时复用现有连接（`current.credential == credential` 直接返回）。

**P2-2 · HostPolicy 校验发生在 accept 请求之后，配对 token 可能已明文发出**
`pairWithLink` 先 `api.accept(...)` 再校验地址；manifest 的 `usesCleartextTraffic="true"` 已放开平台层，HostPolicy 是唯一代码级闸门。扫到 `http://<非私有主机>/pair-accept?pair=…` 时一次性 token 会先被明文 POST 出去。
**修复**：把地址规范化与 HostPolicy 校验整体提到任何网络调用之前（`baseUrl` 先算好并校验，再执行 accept）。

**P2-3 · mux 的 `socket` / `attempt` / `generation` 在 OkHttp 回调线程上无同步写入**
类注释声称线程安全，但回调线程直接读写这三个字段，协程线程经 mutex 访问同一批字段，且都不是 `@Volatile`。`close()` 与并发 `onOpen` 竞争时可能把新 socket 存进已关闭的 mux，此后无人关闭它（连接泄漏）。
**修复**：三个字段加 `@Volatile`，`Attempt.socket` 同样加；回调内不抢 mutex（同步回调加锁会与 `waitForSocket` 的 `ws.send` 形成死锁风险），改为以 `@Volatile` 保证可见性并在类注释中写明理由。

**P2-4 · 二维码失效时展示服务端内部码 `invalid`**
`refusalMessage` 只映射 `expired`/`unknown`/`stopped`/`already-paired`/`bad-payload`，但 `src/pairing.ts:452-456` 对「token 未知/已过期/已停止」统一返回 `code:'invalid'`（有意不区分，避免有效性预言机），routes 以 404 原样回写。用户会看到「配对被拒绝（invalid）」。
**修复**：补 `"invalid"` 分支 → 「二维码已失效或已过期，请在桌面端重新生成」；其余分支保留为防御。

### 发现与修复

**P1-1 · 抽屉列表存在重复 key，`LazyColumn` 会直接抛异常（部分成立，已修）**

审查者给出的论证（「置顶段 key `pin-x` 与最近段 key `recent-x` 冲突」）**不成立**——三段各自带不同前缀，不会跨段冲突。但它指出的**根因方向是对的，只是命中点不同**：真正会崩的是
`SessionDrawer` 里「按工作区」段的 `key = { "drawer-${it.sessionId}" }`，而**同一个会话可以同时出现在两个工作区的 `sessionIds` 里**——这一点由 M2 自己写的单测 `同一会话出现在两个工作区时两边都显示` 明确断言过，两条 `items` 会产出同一个 key，Compose 在 subcompose 阶段抛 `IllegalArgumentException: Key ... was already used`。

同时确认了审查者提到的另一处**真实重复显示**（不是崩溃）：置顶会话会同时出现在「置顶」段和「最近」段，用户看到同一条会话两次。

**修复**：
- `HomeScreen.kt` 工作区段的 key 改为 `"drawer-${workspaceId}-${sessionId}"`；工作区标题 key 加索引前缀。
- `HomeScreen.kt` 工作区段与 `SessionGrouping.recentSessions` 都排除置顶会话。
- `SessionGrouping.group` 对 `workspace.sessionIds` 加 `.distinct()`，`recentSessions` 加 `.distinctBy { it.sessionId }`——服务端若重复下发同一 id，重复行会让 key 冲突直接抛异常，在源头去掉比在 UI 兜底可靠。
- 新增 3 项单测：`recentSessions 排除置顶会话避免抽屉里重复显示`、`sessionIds 里重复的 id 只产生一行`、`recentSessions 对 sessionList 里的重复条目只保留一条`。

**P1-2 · `loadSessions` 被取消时 `sessionsLoading` 永久卡住，且重入保护会永久挡住后续加载（成立，已修）**

`_state.value = copy(sessionsLoading = true)` 在 `try` 之前，而复位只写在 `try` 成功分支与 `catch (Exception)` 里；`retry()` 与 `onCleared()` 都会 `sessionJob?.cancel()`，取消抛的是 `CancellationException`，**既不进成功分支也不进 `catch (Exception)`** → `sessionsLoading` 永远停在 `true`，抽屉永久显示「正在读取会话…」。更严重的是 `sessionJob` 被取消后 `isActive` 仍可能为 true，紧随其后的 `loadSessions()` 会被 `if (sessionJob?.isActive == true) return` 静默丢弃，会话列表再也刷不出来。

**修复**：
- `loadSessions` 的复位移入 `finally`（取消时也复位）。
- `retry()` 显式 `sessionJob = null` 并清 `sessionsLoading`/`sessionsError`。
- `start()` 里用**局部变量** `firstSnapshot` 替代读全局 `_state.value.loading`——后者在重连时已被置 false，会导致 retry 之后会话列表不再自动补拉；并在 `retryWhen` 重连成功时把 `firstSnapshot` 置回 true，让断线期间的变更被补回来。

**P2-1 · 抽屉数据刷新时无条件回顶，会把正在浏览的用户弹回顶部（成立，已修）**

`LaunchedEffect(pinned.size, recent.size, groups.size) { scrollToItem(0) }` 在三个尺寸任意变化时都回顶；而 `recent.size` 在每次 `refreshSessions()`、每次重连补拉、任意会话活动导致排序变化时都会变。T009 要修的只是「首次数据到达时新段被顶到可视区之上」。

**修复**：改为只在会话数据**首次**到达时滚一次（`state.sessions.items.isEmpty` 作为 key + `restoredForSessions` 标志）。真机复验：抽屉内下滑到「按工作区」段中部 → 关闭抽屉 → 点「刷新」→ 再开抽屉，**滚动位置保持**（截图 `_r3.png`）。

**P3-1 · 相对时间只在重组时计算，长时间停留显示过时文案（成立，已修）**

`TimeText.relative(..., System.currentTimeMillis())` 直接读系统时钟，没有任何定时重组来源：抽屉打开后静止 30 分钟，「5 分钟前」不会变成「35 分钟前」。

**修复**：新增 `rememberNow()`（`produceState` 每 30 秒推进 `now`），把 `now` 逐层传给 `WorkspaceRow` / `SessionRowItem` / `DrawerSessionRow`。

**P3-2 · `drawerOpen` 状态与抽屉实际开合不同步，`setDrawerOpen` 从未被调用（成立，已修）**

KDoc 声称「抽屉开关由 ViewModel 状态驱动，这样『返回键关抽屉』也能走同一条路径」，但 `drawerState` 实际由 `ModalNavigationDrawer` 的 `open()`/`close()`/手势直接改，`setDrawerOpen` 在全仓库没有任何调用点，`state.drawerOpen` 恒为 false。

**修复**：删掉 `HomeUiState.drawerOpen` 字段、`setDrawerOpen` 方法与那段错误的 KDoc，让抽屉开合完全由 `drawerState` 持有（`ModalNavigationDrawer` 本身已处理手势与返回键）。

### 发现与修复

**P2-1 · 「生成中」窗口内没有中止按钮**

`ChatReducer` 的 KDoc 声称「`turn/start` 置真」，但 `SessionEventParser.toChatItem` 从未映射 `turn/start`，而 `onEvent` 在 `item == null` 时直接 `return state` → **`send()` 成功到首个 `assistant-stream` Start 帧之间 `generating` 恒为 false**，`ChatScreen` 的中止按钮不渲染，用户无法取消这一轮。

修复：① `send()` 成功后乐观置 `generating = true`；② `ChatFrameParser` 的 `Event` 帧携带 `eventType`/`seq`/`turn`/`step`（从信封直取，不依赖 item 是否解析得出）；③ `ChatReducer.onEvent` 不再在 `item == null` 时无条件返回，轮次边界事件一律可以翻转 `generating`。

**P2-2 · 基线预览的 (turn, step) 靠猜 → 同一条消息渲染两遍**

`ChatReducer.replayBaseline` 用 `items.lastOrNull { it is Assistant }?.turn ?: 0L` 猜 turn、step 固定 0；清 `live` 的唯一条件是与落盘事件的 `(turn, step)` 相等。猜错时**预览永不清除**，`LazyColumn` 同时渲染 `items` 气泡与 `item(key="live")` 预览 → 同一段文字出现两遍 + 永久「正在生成…」。上游 `ChatFrameParser.snapshot()` 读了 `activeAttempt.stream` 却没读它的 `turn`/`step`/`nextIndex`/`attemptId`。

修复：`ChatFrameParser` 读出 `activeAttempt` 的 `attemptId`/`turn`/`step`/`nextIndex` 放进 `Snapshot`；`ChatReducer` 用它们 seed 预览，不再猜。

**P2-3 · 空 content / 缺 turn 的 `assistant/message` 被整条丢弃 → 结束信号丢失**

`SessionEventParser.assistantItem` 在 `event.data.long("turn") ?: return null` 与 `if (blocks.isEmpty()) return null` 两处丢弃事件。取消后服务端可能回 `interrupted:true` 且 content 为空的 `assistant/message` → reducer 拿不到结束信号 → 预览与生成状态一起永久残留。

修复：清 `live` 改为**按帧上的 `(turn, step)` 判定**（帧字段从信封直取，即使 item 解析不出仍然可用），不再依赖 item 是否存在；`turn/end` 无条件清。

**P2-4 · committed End 不记 committedSeq**

`onLive` 的 `committed` 分支什么都不做，把清除责任完全交给未来的落盘事件；若紧接着断线重连且重放窗口未覆盖该 seq → 预览永久残留。

修复：`ChatUiState` 新增 `committedSeq`，`End(committed)` 写入；`onEvent` 在 `seq == committedSeq` 时兜底清，并在 `committedSeq in 0 until seq` 时归 -1 防残留；快照到达时归 -1。

**P3-1 · `loadingMore` 复位不在 `finally`**

`ChatViewModel.loadMore()` 的 `loadingMore = false` 只写在 try 成功分支与 `catch (Exception)` 里，协程取消抛的 `CancellationException` 是 `Exception` 子类但那两条分支都不覆盖该路径 → 顶部「加载更早」转圈行永久停留。与 R003 P1-2 同类（`HomeViewModel.kt:225` 已有注释记载）。

修复：复位移入 `finally`，并 `pageJob = null`。全仓复查：`loadSessions()` 的 `catch` 也补了 `if (cause is CancellationException) throw cause`（见 T015）。

**P3-2 · `advance()` 对 `index < 0` 也自增**

与自身 KDoc 矛盾（基线回放统一传 -1，不应推进计数）。当前只影响记账。修复：`if (index >= 0L && index.toInt() == attempt.nextIndex)`。

**P3-3 · 滚动跟随算错行数**

`liveLength` 只取 `state.live?.text?.length`（纯 reasoning / 纯 toolArgs 增长时不触发跟随）；`scrollToItem(itemCount - 1)` 在有 `live` 行或「加载更早」行时指不到真正末尾。修复：`liveLength` 改为 text+reasoning+toolArgs 总长；滚动目标改为 `itemCount + (loadingMore?1:0) + (live!=null?1:0) - 1`。

**P3-4 · `onEvent` 全程不写 `error`**

只有快照会清 `error`。重连后若服务端只补事件、不再发 snapshot → 错误横幅 + 重试按钮永久停留。修复：`onEvent` 成功消费到 item 时 `error = null`。

**P3-5 · 死字段 / 死代码 / 未兑现的 KDoc**

- `ChatUiState.lastRawFrame` 无写入方 → 删除。
- `SessionEventParser` 末尾三个 internal 扩展经 grep 确认无调用方 → **改造**为全仓库共用的宽容取值器（`asObjOrNull`/`longOrNull`/`stringOrNull`/`booleanOrNull`/`objectOrNull`/`arrayOrNull`），并删掉 `ChatFrameParser` 里重复的一份，消除「同一判断写两遍」的隐患。
- `ChatRepository.prompt()` 返回 requestId 但调用方直接丢弃（KDoc 承诺的「失败可重试」未实现）→ 在 `ChatViewModel` 保留为可重试凭据。

**N-2 · 多步轮次是常态，`assistant/message` 在每个 step 落盘（远早于 `turn/end`）**
