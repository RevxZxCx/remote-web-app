# 开发流程

> 本文件是**强制流程**，每个阶段都必须走完。目的是：即使对话被压缩、上下文丢失，也能凭仓库里的文档恢复全部开发记忆。

---

## 0. 总原则

1. **文档先行**：任何代码之前，先把「要做什么」写进文档。文档是唯一可信的记忆载体。
2. **小步提交**：一个阶段一次提交，提交信息写清楚阶段号与验证结论。
3. **无测试不合并**：阶段完成 → 先测试 → 测试记录落盘 → 再代码审查 → 审查通过 → 才提交。
4. **失败也记录**：踩过的坑必须写进 `测试记录.md` 或 `开发进度.md` 的「已排除方案」，避免重复踩。

---

## 1. 每个阶段的固定循环

```
① 计划    → 更新 docs/dev/开发进度.md：本阶段目标、验收标准、涉及文件
② 实现    → 写代码（遵守 决策记录.md 里所有已拍板决策）
③ 自测    → 编译 + 静态检查 + 单元测试 + 可行的真机验证
④ 记录    → 把测试过程与结论写进 docs/dev/测试记录.md（含失败项）
⑤ 审查    → 走第 3 节的代码审查清单，结论写进 docs/dev/代码审查记录.md
⑥ 修复    → 审查发现的问题必须修完并回归，再回到 ④
⑦ 提交    → git commit（信息格式见第 4 节），更新 开发进度.md 状态为「已完成」
```

**禁止跳过 ③⑤**。若某阶段无法自动化测试（例如必须真机扫码），要在 `测试记录.md` 里写明「无法自动化，已由用户手动验证」并附用户确认。

## 2. 文档职责划分

| 文件 | 职责 | 何时更新 |
| --- | --- | --- |
| `需求文档.md` | 要做什么、接口契约、验收判据 | 需求变化时（需用户确认） |
| `决策记录.md` | 已拍板的决策 + 理由（ADR） | 每次拍板/推翻决策时 |
| `开发进度.md` | 当前阶段、已完成、待办、已排除方案 | 每阶段开始与结束时 |
| `开发流程.md` | 本文件，流程本身 | 流程变化时 |
| `测试记录.md` | 每次测试的命令、结果、失败原因 | 每次测试后 |
| `代码审查记录.md` | 每次审查的范围、发现、结论 | 每次审查后 |
| `环境与构建.md` | SDK/JDK/代理/构建命令等环境事实 | 环境变化时 |

## 3. 代码审查清单

每个阶段提交前逐项核对，结论写进 `代码审查记录.md`：

### 3.1 正确性
- [ ] 与 `需求文档.md` 的接口契约逐字对照，**方法名、参数名、字段名完全一致**（Typert 是严格 schema，拼错就是运行时报错）
- [ ] 错误分支已处理：`{ok:false, error:{code,message,details}}` 信封、HTTP 401/403/404/415/500
- [ ] 未配对（403 `unpaired`）有明确的用户引导，不是白屏

### 3.2 协议一致性
- [ ] unary 请求体是 `{type:"client-request", rpcId, method, payload}`，`method` 必须与 URL 路径推出来的 endpoint 一致（否则服务端报 `method "X" does not match endpoint "Y"`）
- [ ] `rpcId` 是 RFC4122 v4 UUID，且校验响应里的 `rpcId` 与请求一致
- [ ] 流式帧只使用 `open` / `item` / `end` / `cancel`（客户端）与 `item` / `end` / `error`（服务端），其他帧会导致服务端以 **4002** 关闭
- [ ] WebSocket 用 `?device=<id>` 传凭证（握手不能带自定义头）

### 3.3 安全
- [ ] 设备凭证不以明文落盘（见 D16）
- [ ] 日志不打印完整 deviceId / token（只打印前 8 位）
- [ ] 不把 `/api/pair/*`、`/api/update/*`、`/api/plugin-manager` 当作可用路径（服务端硬性拒绝）

### 3.4 生命周期与并发
- [ ] WebSocket 断线有指数退避重连（1s→2s→4s→…上限 30s），重连不清空 UI
- [ ] `session/follow` / `session/control` / `workspace/follow` 的流在离开页面时被取消，不泄漏
- [ ] 所有协程有明确作用域，不在 `GlobalScope` 里裸跑

### 3.5 质量
- [ ] 无 `!!` 强解包（除非已证明非空并注释原因）
- [ ] 公开 API 有 KDoc，说明参数与返回
- [ ] 没有复制粘贴的重复协议解析逻辑（统一走协议层）

## 4. 提交规范

```
<阶段号>: <一句话做了什么>

- 关键改动点 1
- 关键改动点 2
- 测试：<命令> → <结论>
- 审查：<结论>
```

示例：

```
M1: 协议层 TypertClient + 配对 + 凭证存储

- 实现 unary POST /remote/api/<ns>/<method> 与 mux WebSocket
- 实现扫码配对与 Keystore 加密凭证存储
- 测试：gradlew test + 真机 workspace/follow → 通过
- 审查：代码审查记录.md #1 → 通过
```

**只提交仓库内的文件**。`local.properties`、`build/`、`.gradle/`、`*.apk` 一律不提交（见 `.gitignore`）。

---

## 5. 阶段划分（与需求文档 M1–M5 对应）

| 阶段 | 目标 | 验收 |
| --- | --- | --- |
| **M1** | 协议层 + 配对 + 凭证存储 | 真机配对成功，能调通 `workspace/follow` 拿到数据 |
| **M2** | 工作区列表 + 会话列表 | 首屏 ≤500ms，能下拉刷新与切换工作区 |
| **M3** | 聊天：快照 + 流式 + 发送 + 中止 | 能收发消息，流式增量上屏 ≤200ms |
| **M3.5** | Markdown 渲染 + 工具卡片 + 改动文件卡片 + 文件查看页 | 回复有富文本，能点开文件看 diff |
| **M4** | 缓存、重连、断线补齐、调试页 | 断网重连不丢消息，冷启动 ≤1.5s |
| **M5** | 打磨（可选） | 主题、通知、附件、模型切换 |

每个阶段内部按第 1 节的七步循环执行。
