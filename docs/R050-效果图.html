为什么是这一版（而不是贴边手柄）：
① 贴边手柄会被内容压住：首页工作区列表是可滚动的，手柄浮在最右侧会盖住每行的状态胶囊（1 进行中 / 11 会话），48 个会话就会遮 48 次。
② 顶栏是唯一「系统级入口」的位置：会话列表（☰）在左、连接状态在右，洞察与它们同层，用户找入口时只会看顶栏，不会去边缘找。
③ 右滑手势照旧保留，所以按钮只是「可发现性」的补充 —— 老用户继续用滑的，新用户看按钮。

圆点什么时候亮：距离上次打开洞察后，若新增了会话或费用有变化就亮；打开抽屉即清除。不显示百分比、不显示数字（顶栏放不下，也没人要看）。

无障碍：按钮 contentDescription = "总上下文洞察"，圆点亮时补一句「有新数据」。抽屉展开后 TalkBack 焦点直接进抽屉头部，Esc / 右滑收起。

三块都用圆环的理由：原来 token 是色块列表、花费是四行数字、耗时是五行数字 —— 三块三种视觉，用户要分别学。现在统一成 R040 的圆环：一眼看出比例，图例读绝对值，且和单会话侧栏完全同构，从首页进和从会话进看到的图形是一回事。

每块的圆心与合计：圆心写「总量 + 名字」，圆环下方一条分隔线写口径或明细。token 环的合计行是四类 token 的拆分（缓存读 / 未缓存输入 / 输出 / 其中推理），花费环的合计行是未计价警示 + 总计，耗时环的合计行解释「未归类」是什么。

为什么保留 未归类 这一段：六段实测之和只有墙钟的 79.2%，缺的 20.8%（33.4 h）是 step 之间没埋点的间隙。补成一段写明白，比让圆环只填五分之四、留个缺口不说话要好 —— 缺口会被误读成「渲染 bug」。

为什么 正文生成 只有 0.9%：这是真实值。39.3 亿 token 绝大部分是缓存读取，模型吐字本身很快（1.5 h），时间全花在工具执行（52.9 h，33.0%）和推理（30.4 h，18.9%）上。

统计范围三档：近 7 天 / 近 30 天 / 全部。切换只重算本地聚合，不发请求。

没抄插件的部分：日期区间自定义（要日历控件，手机放不下）、技能加载统计与文件活动（要逐会话读 contextActivity，32 次请求）、赠送/充值余额（账户接口，App 无鉴权通道）。

结论：session/list 一次返回 186 条、合计 5.91 MB（每条约 32.5 KB） —— App 已经在拉这份数据（R039 缺陷1 的经验：不能靠轮询它，只能靠 $events 的 api-session/* 增量维护）。
所以总览页的正确做法是：在已有的 HomeViewModel 内存列表上做纯函数聚合，不新增任何请求。用户切「近 7 天 / 近 30 天 / 全部」也只是对同一份 SessionSummary 列表重新 filter + sum，零 IO。
早先的一处误判已纠正：「模型名」原以为拿不到（modelSelection 曾判为空）。实测 32 / 32 全有值，形状是 {"lastUsed":{"provider","model","reasoningEffort"},"next":{…}} —— 取 lastUsed.model 即「当前用的模型」，与 costUsage.byModel（历史累计用过哪些）是两件事。
两个选项：（A）会话行第二行改显示花费最高的那个模型（本文推荐，语义是「主要花的钱去哪了」）；（B）不显示模型名，改显示该会话的费用。我选 A，因为它回答了「这个会话为什么贵」。
