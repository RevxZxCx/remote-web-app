✱ 先回答你的第 4 点：目标暂停 ≠ 对话停止

你让我去查 DSH 源码确认「目标暂停后任务还跑不跑」。结论：两者独立，你的直觉是对的。证据（F:\DSH\resources\app.asar 里的客户端 bundle）：

① goal 有两个互相独立的维度
phase（durable，持久层）∈ active / paused / blocked / complete； activation（进程本地，不是会话状态）∈ armed / disarmed。源码里判断「该显示暂停还是继续」用的是两者的组合：
const showResume = goal.phase === "paused" || goal.phase === "active" && activation === "disarmed";

② goals/pause 只改持久状态，不取消任何正在跑的轮次
文档原文：四个变更（edit / pause / resume / clear）都是路由到 Host GoalService，由它排队一条「模型可见的 goal 上下文消息」。整个 bundle 里 goal 与 cancel / interrupt / abort 零关联——没有「暂停即中止」这回事。

③ 目标只影响「下一轮要不要自动继续」
runMode 的取值 plan.active ? "plan" : goal.phase === "active" ? "goal" : "default" 只决定这一轮以什么身份跑，且它只被用作埋点字段（send_button_click 的 run_mode）。它不是运行开关。

结论（落到 UI）
· 目标暂停 → 不再自动注入「继续目标」的触发；当前这一轮对话继续输出完，任务列表照常推进。
· 所以任务胶囊不跟随目标变色——它只看 todos[].status。目标暂停时胶囊仍是旋转圈（如果确实还有 in_progress 的任务）。
· 反过来也一样：任务全部完成不代表目标完成；目标 complete 时横幅直接不渲染（DSH 的行为：goal.phase === "complete" → return null）。

注意：这里只借用了「语义关系」，布局一律按你的提示词来——目标是顶部横幅、任务胶囊在排队条上方、排队条贴输入框。DSH 桌面端其实把三者都排在输入框上方（dock 顺序 todo:0 / goal:10 / queue:20），但那是桌面端的布局，不搬到手机上。

为什么是这个顺序
  • 排队条贴身：它是「即将发出的内容」，紧贴输入框符合「我刚打的东西排在这」的直觉。这条是用户 m21177 定的，不变。
  • 任务胶囊放在排队条外侧：它描述的是「这个会话的宏观进度」，属于比排队更外层的上下文。放在排队条下面会让两者看起来是同一层信息。
  • 目标横幅在顶部：它是会话级元信息（这个会话为什么存在），与底部「当前在做什么」形成头尾呼应，不抢输入区。
  • 都不挡消息：三者都有明确的最大高度，且消息区是 flex:1 自适应收缩，不会出现「底部把内容挤没」。
双端同步（第 4 条注意事项）
  • 目标：`session/follow` 快照的 projections.values.goal 是唯一真相；实时变化走 goal/change 事件（已核实 operation ∈ create / resume / pause / edit / complete / clear，goal.phase ∈ active / paused / complete）。手机端点暂停 → 调用 update_goal 工具或等价 RPC → 服务端广播 goal/change → 桌面端与手机端都从同一条事件更新，不存在两端各自维护状态。
  • 任务：projections.values.todos + tool/call 的 todo_write。手机端只读，不提供编辑——避免两端同时写导致覆盖。
  • 排队：projections.values.inbox（快照）+ agent/inbox/spliced（增量）。删除/编辑/插队都走 session/updateQueue，服务端确认后通过 splice 事件回来，两端同源。本地不做乐观删除——删了但服务端拒绝会导致「一端有、一端没有」。
  • 所有三个都有 revision 或 seq 可比对，客户端必须以服务端为准，本地只做「请求中」的临时态（≤2s），失败则回滚。

规则细节
  • 判据：`WindowInsets.ime` 的可见高度 > 0（或 `imeVisible == true`）。不用焦点判据——焦点在但键盘未弹出（外接键盘）时不该隐藏。
  • 动画：三者一起 shrinkVertically(Motion.FAST) 收起，与键盘动画同向；不要用 expand 的 MEDIUM，会显得拖沓。
  • 恢复：键盘收起后，目标横幅按它原来的收起/展开状态恢复（默认展开）；任务胶囊与排队条一律回到收起态——它们不该记得上次是不是展开的（与「不记忆」一致）。
  • 正在行内编辑时弹键盘：编辑中的那一行不隐藏（否则用户没法输入）。只有「没在编辑」时才隐藏。这是唯一例外。
  • 目标横幅：键盘期隐藏后，顶栏那枚 .goalchip 也不显示——键盘期不提供目标操作，避免误触。
